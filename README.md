# TyraX

An editor for the [Tyra](https://github.com/h4570/tyra) PlayStation 2 game engine. C++20 + Dear ImGui (docking) + GLFW + OpenGL 3.3.

![The TyraX editor: the Project panel (scenes, objects, layers, assets) on the left, the 3D viewport with a checkerboard terrain, scene objects and camera-entity frustum wedges in the center, the Properties panel on the right, and the build Output docked below.](docs/img/editor-overview.png)

## Quickstart

```powershell
# 1. Install prerequisites (skip what you already have)
scoop install mingw cmake ninja       # editor toolchain
# + Docker Desktop (running) and PCSX2 in Program Files\PCSX2 (with BIOS configured)

# 2. Build and run the editor (clones deps + configures + builds)
./build.ps1 -Run
```

`build.ps1` handles everything: clones `vendor/` dependencies on first run, finds the scoop mingw toolchain even when it's not on PATH, configures CMake and builds. Flags: `-Run` launches the editor after building, `-Clean` rebuilds from scratch.

Then in the editor:

1. `File > New Project` (`Ctrl+N`) — pick a name, location and the flat terrain size, hit **Create**.
2. The *Viewport* shows the terrain preview (drag to orbit, scroll to zoom).
3. Press **Build & Run** (`F5`) — the first build downloads the `h4570/tyra` Docker image and compiles the engine inside the container (a few minutes, one time). Subsequent builds take seconds. PCSX2 boots your ELF automatically.

## Features (MVP)

- **New project** (`File > New Project`, `Ctrl+N`) — name, location (defaults to the folder set in `Edit > Preferences > New projects`, otherwise `~/TyraProjects`), flat terrain size (width × depth in world units) and a game template: **Terrain orbit** (camera circles the terrain), **FPP walkthrough** (walk with the left analog stick, look around with the right one; the scene starts with a spawn point) or **FPP showcase** — a fresh copy of every feature in one scene: a .obj house, a physics ball, a pillar to jump on, a HUD crosshair and a starter flow graph (Circle toggles the box, walking up to the house logs a greeting). Use showcase for experiments instead of wrecking a shared sample. Generates a complete Tyra game project: `Makefile`, `Dockerfile`, `docker-compose.yml`, C++ sources rendering the scene (StaticPipeline, no asset files needed) and the single `<name>.tyra` project file.
- **Open project** (`Ctrl+O`) — pick the project's `<name>.tyra` file.
- **Spawn point** — a special scene object (marker with a direction arrow, no geometry in the game). In the FPP template the player starts at the first spawn point, facing its Y rotation.
- **Scene objects** — insert simple 3D primitives (box, sphere, cylinder, cone) via the *Scene* menu or the buttons in the *Project* panel. Each object has a name, position, rotation, scale and color, editable in the *Project* panel and saved to its own `objects/<id>.json` file (one file per object, keyed by a stable id). Objects render both in the editor viewport and on the PS2 (scene data is regenerated into `inc/scene_data.hpp` on every build).
- **Decals** (signs, posters, text on walls, fake shadows) — insert a *Decal*, assign a material whose `map_Kd` PNG has transparency, and it draws as an alpha-cutout image. A flat decal is a simple quad you stick on a flat surface; tick **"Project onto surfaces"** and it instead **wraps onto the receiver geometry** (angled/curved walls, models, terrain) so wall text and fake blob shadows conform to what they cover. The projection is computed entirely on the host at build time and baked to static geometry — it draws through the normal pipeline with **zero extra PS2 CPU cost** (no runtime projection or clipping).
- **Mirror objects** — `+ Add object > 3D Object > Mirror` inserts a rectangle that fakes a real mirror the PS2 way: the game **re-draws a hard list of objects** (picked in *Properties > Mirror*) a second time, reflected across the glass plane — no render-to-texture, no stencil, just a reflection matrix over the same vertex arrays on VU1, so moving objects and even **animated models reflect their live pose** for free. An optional **Reflect player** switch mirrors the third-person avatar (an FPP player has no body — vampire rules). The glass itself is a color-tinted quad with an **opacity** slider that blends over the copies. The copies are *real geometry on the far side of the plane*, so build the mirror into a wall (or give it a backing) — the wall hides the mirror world outside the frame, exactly like the classic PS2/PS1 mirror rooms. The editor viewport previews the whole illusion live.
- **Raytraced reflections (VU0, experimental PoC)** — check *Properties > Mirror > Raytraced* on a Mirror and its reflection is **actually ray-traced on a VU0 microprogram**, per pixel, every frame: listed **static models reflect as real, TEXTURED triangle meshes** (decimated to a 36-triangle budget at build, re-transformed live — rotation included — with the kernel returning barycentrics and the EE sampling the model's texture in RAM), **animated models reflect LIVE** (a fixed medoid-picked vertex-index mesh reads the skinned buffers every frame, so the glass plays the clip), flat objects as axis-aligned slabs, everything else as sphere proxies, against the scene's sky gradient — into a texture the glass samples, re-uploaded over PATH3 each frame at a per-mirror **Reflection resolution** of 32–512 (cost scales with the square — 128 still holds a frame rate, 256/512 are photo modes). The kernel is branchless VU0 microcode (saturation-arithmetic step masks, rational nearest-hit comparisons, per-model bounding-sphere early-outs) fed row-by-row through VU0 data memory by the EE, which mirrors the camera across the plane (Householder), packs the returned texels and textures the triangle hits. Budget one per scene. See [docs/raytraced-reflections.md](docs/raytraced-reflections.md).
- **Live texture feeds (CCTV + mirror streams)** — any surface can show a **live feed** via *Properties > Texture feed*: a Camera entity with **Render to texture** renders its view (sky/terrain + an explicit object list) into a dedicated 128×128 VRAM target every frame — security monitors and billboards, the classic 2002 set piece — or a **raytraced Mirror's traced image streams onto any other object** as an emissive screen. Real second render through the env-map redirect bracket, live camera transform (a flow graph panning the camera pans the feed), one feed camera per scene. See [docs/texture-feeds.md](docs/texture-feeds.md).
- **Portal objects** — `Insert > Gameplay > Portal` inserts a linkable surface: point two portals at each other (*Properties > Portal*, one click makes the pair two-way) and each shows a **live view through to the other end** — a real second render from a virtual camera kept in lockstep with the player camera, drawn **in-place at full resolution** through the normal VU1 pipeline and carved into the scene with the z-buffer (the GS has no stencil), so the opening is pixel-for-pixel as crisp as the world around it — correct parallax, no render-to-texture, no visible seam. **Walking into the front face teleports you to the target with position, view angle and vertical velocity carried through the same mapping** — what you see through the surface is exactly where you arrive, so crossing is seamless: smooth teleporters between distant parts of the map. Physics objects can ride along (per-portal switch). Budgeted the era-honest way: up to four live views per frame (nearest first; the rest draw as tinted energy surfaces) and an explicit per-portal list of objects visible through, like the Mirror's — or the experimental **All objects in view** switch, which submits the whole scene into the through-view and lets the virtual camera's frustum culling + draw distances trim the cost. See [docs/portals.md](docs/portals.md).
- **Transform gizmos** (ImGuizmo) — click an object in the viewport to select it, then drag the gizmo to move / rotate / scale it. Switch tools with the buttons in the viewport corner or the `W` / `E` / `R` keys; `Delete` removes the selected object. Left-drag on empty space or right-drag orbits the camera, wheel zooms.
- **Window layouts** (`Layout` menu) — named docking arrangements saved per project and switched with one click. Three ship built-in: **Default** (Project / Properties / Output + Debug around the Viewport), **Director** (Viewport + the Cutscene Director dopesheet), and **Material Designer** (the Material Editor filling the window). Edit any layout by simply rearranging windows; *New layout…* saves the current arrangement under a new name, and *Reset to built-in arrangement*, *Rename…* and *Delete* round out the menu. Even the built-ins can be deleted per project — a project just always keeps at least one.
- **Project file, window layouts & undo history** — the project is a `<name>.tyra` **manifest** (project-wide settings, HUD, menus, sequences, save data, plus editor-side state — selection, active tool, view mode — and the named window layouts above, so your arrangements are restored per project) alongside an `objects/` folder holding **one file per scene object** (`objects/<id>.json`); the manifest lists each scene's objects by id in order. This layout keeps git merges painless for teams: two people editing different objects touch different files (see **Multi-user collaboration** below). The undo history (up to 100 snapshots) lives in a sidecar `<name>.history` file, so undo/redo survives editor restarts; it is gitignored in generated projects. The `<name>.tyra` + `objects/` are the source of truth — if edited outside the editor, the stored history is discarded automatically. (Projects from older editor versions used a single monolithic `.tyra`; they load unchanged and migrate to the split layout on the next save, or in bulk via `--resave`.)
- **Multi-user collaboration** — each new project is scaffolded for team work: because scene objects are split one-per-file, editing/moving/recoloring *different* objects never conflicts in git. A generated `COLLABORATION.md` explains the workflow, and a `.gitattributes` marks the files that *can't* be auto-merged — terrain heightmaps and imported `res/` assets — as `lockable`, so a team can `git lfs lock` them before editing (it uses only Git LFS's lock registry — no LFS storage or special server — and is inert until `git lfs install`, so it never disturbs a solo/non-LFS workflow).
- **Live collaboration sessions** (`Session` menu) — real-time multi-user editing on top of the git story: one editor **hosts** its open project, others **join over the LAN** with the host's `IP:port` + a 6-digit code, and everyone edits at once — objects, scenes, terrain sculpting, menus, cutscenes, preferences all stream live with per-object last-write-wins (the host orders every edit, so all editors converge). The whole project transfers on the first join; re-joins fetch **only what changed** (a content-hash cache under `%LOCALAPPDATA%\tyra-editor\remote-cache`). You see everyone else's **selections as colored outlines** in the viewport (and dots in the object list), the Session window lists participants (with Kick for the host), and the toolbar shows a SESSION/JOINED chip. The **host is the only one who saves and commits** — a client's Save is disabled (`[joined]` in the title bar) and its synced copy is still a full, real project: local Docker builds, PCSX2 runs and Live Link all work. Full guide: [docs/collaboration.md](docs/collaboration.md).
- **Copy/paste** — duplicate scene objects with `Ctrl+C` / `Ctrl+V` (the copy lands next to the original with a unique name).
- **AI flow-graph generation** — *Flow Graph* window → **Generate with AI...**: describe the logic in plain language and the configured backend (Claude CLI, GitHub Copilot CLI or the OpenAI API — pick the backend, a model from the dropdown (or *Custom...* to type any model id) and a *Thinking* toggle in `Edit > Preferences > AI assistant`) builds the graph. An existing graph is sent along automatically, so "make the timer 5 seconds" or "also play a sound" **edits it in place** — the model returns the complete updated graph, unchanged nodes keep their ids and positions. The reply is validated against the live node registry (including your custom `.flownode` nodes) and applied as one undo step; a spinner + **Cancel** cover the wait. Also headless: `--ai-graph`. [docs/ai-flow-graph.md](docs/ai-flow-graph.md).
- **AI-agent CLI** — the editor exe doubles as a headless toolbox for AI assistants and scripts: `--dump` (project summary), `--list-nodes` (node catalog), `--dump-graph`/`--apply-graph` (validated graph I/O), `--refresh-gen` (regenerate game sources without Docker). [docs/ai-tools.md](docs/ai-tools.md).
- **AI support in projects** — the **New Project** dialog (and later `Project > Preferences > AI support`) can install assistant guidance into the game project: Claude Code skills + `CLAUDE.md` and/or `.github/copilot-instructions.md`, teaching an AI assistant the project structure, the ownership markers, flow graphs, custom scripting and the CLI above. Refreshable with the same delete-the-marker-to-own rule as generated sources. [docs/ai-support.md](docs/ai-support.md).

## Shortcuts

| Shortcut | Action |
| --- | --- |
| `Ctrl+N` / `Ctrl+O` / `Ctrl+S` | New / open / save project |
| `F5` | Build & run in PCSX2 |
| `Ctrl+Z` / `Ctrl+Y` | Undo / redo |
| `Ctrl+C` / `Ctrl+V` | Copy / paste the selected object |
| `W` / `E` / `R` | Move / rotate / scale tool (viewport) |
| `Delete` | Delete the selected object (viewport) |
- **3D terrain preview** — *Viewport* window with a checkerboard terrain grid (matching what the PS2 renders), scene objects with a selection outline, world axes and an orbit camera (mouse drag = rotate, wheel = zoom).
- **Textures (PNG)** — per-object textures (*Set...* in object properties; the object color modulates the texture, white = plain) and a tiled terrain texture (*Preferences > Rendering*). UVs are generated for all primitives, `vt` is read from .obj models. Tyra loads PNG natively: 32/24bpp or palletized 8/4bpp (fastest on the PS2); keep sizes power-of-two.
- **Material Editor & texture painting** (*Tools > Material Editor*) — authors the `.mtl` materials the whole pipeline consumes (color × brightness + `map_Kd` texture, saved on every change, scene viewport updates live). A **Reflection** section makes a material shiny the way PS2 racers did it: pick a small **sphere map** PNG (a sky gradient with a bright horizon works great) — or **`<dynamic - live sky>`**, which re-renders the scene's sky into the map every frame, GT3-style, so reflections follow script retints — plus a strength, a **Rounded normals** toggle and a project-wide **Reflection probe: aim along the reflected ray** preference (the env camera renders from the point your view ray hits the reflective surface, along the reflected direction — smoothed; what the chrome under your crosshair actually mirrors, instead of the classic level-forward approximation) (flat faces sweep a gradient of the map instead of one uniform sample — the curved-lacquer look for walls and monoliths); the game draws the surface a second time with additive blending, sampling the map by camera-space normals **computed on VU1**, so the highlight slides over the paint as the camera moves at zero EE cost; the viewport and the Material Editor preview mirror the effect live. Stored as the standard `refl` statement in the `.mtl`. Full guide: [docs/reflective-materials.md](docs/reflective-materials.md). The preview shows a unit primitive **or any of your `.obj` models** (the open file acts as the model's material override, exactly like in the game; drag orbits, wheel zooms). **Duplicate** copies a material together with its referenced textures (repaint-safe), **Delete...** removes one from the project (confirmed, objects fall back gracefully). **Paint** draws straight onto the preview mesh through its UVs, on a **layer stack** (Background + layers with Normal/Multiply/Add/Overlay blend modes, opacity and visibility; the stack persists in an editor-only sidecar) — with a soft color brush, an eraser, or a **brush image**: project-global PNGs under `res/brushes/` (*Import brush from PNG...*) stamped GIMP-style (the PNG's alpha is the dab shape, its RGB the paint) at a configurable **Spacing** (low = a continuous line, 100%+ = separate stamps), with per-dab **rotation** (a fixed Angle for orienting bricks, or Random for organic scatter), per-dab **opacity variation** (Vary — hand-worn strokes instead of a uniform coat) and a **Live dab** ghost that previews the stamp under the cursor before you click. Every stroke saves the flattened PNG, which is exactly what the PS2 loads (no separate bake; brushes and layer sidecars never ship). The window keeps its own undo: **Ctrl+Z while it's focused** (or the Undo button) steps back through strokes, layer ops and material edits without touching scene undo. *Texture > New paintable texture...* creates a blank pow2 canvas next to the `.mtl` for texturing a model from scratch. The preview also offers **display modes** (wireframe overlay, a generated **UV checker**, and **PS2 CLUT** — the texture palette-quantized live through the exact median-cut quantizer the build ships, with a Floyd–Steinberg/ordered/none **dithering comparison**, the surviving palette as swatches and a **memory budget line** like `128x128 4-bit = 8.0 KB + 64 B palette`), a **UV layout panel** with two-way hover sync (hover a face in 3D → its texture region lights up; hover a UV triangle → it outlines on the mesh) a **UV validator** (overlapping islands, out-of-range/flipped/degenerate triangles, texel-density outliers — findings click-to-highlight in both views) and a one-click **automatic UV unwrap** (smart-project: normal-clustered charts, uniform-density packing, rewrites the `.obj` in place — unwrap before texturing). A **Bake maps** block runs a progressive **raytraced UV-space baker** (BVH + cosine hemisphere sampling, deterministic, multithreaded): ambient occlusion, bent normals, thickness, curvature, position and object-space normal maps in one pass, optional **high-poly cage projection** for baking dense-mesh detail onto game meshes — with a live preview on the mesh while you drag the sliders, one-click **"Bake & add AO layer"** (lands as a multiply paint layer) and a six-map PNG export. On top of the bake sit **smart masks** — procedural layer generators (edge wear and cavity grime from curvature, dirt from occlusion, height streaks, world-space Perlin/Worley that flows across UV seams, bricks) with a remap window and noise breakup, regenerating live as the bake refines — and **material presets** that save a mask stack as a reusable recipe applied to any other asset's own bake. Full guides: [docs/material-painting.md](docs/material-painting.md), [docs/material-baking.md](docs/material-baking.md).
- **Terraforming** — the *Sculpt (4)* terrain brush: paint the terrain relief with a smooth brush (LMB raises, Shift+LMB lowers, Flatten levels to a target height, RMB orbits). Lives in the **Terrain Editor** window (below) together with the Paint brush; quick radius/strength sliders float in the viewport while the tool is in hand, **`[` / `]`** resize the brush, and the ranges **scale with the map** (a 2000×2000 world sculpts as comfortably as a 64×64 garden). The heightmap is stored in `terrain-<scene>.heights`, compiled into the game, and everything follows the relief: FPP walking, object physics, shading.
- **Terrain painting** (*Tools > Terrain Editor*, or the *Paint (6)* tool) — the terrain no longer wears a single tiled texture: add **terrain layers** (each an existing `.mtl`, so they inherit its texture, tint and tiling, plus a per-layer **Size**) and **paint their blend straight onto the terrain in the viewport** with the shared terrain brush (Shift or the Erase toggle removes). The Terrain Editor hosts both terrain tools — Sculpt and Paint as switchable modes — plus the layer stack (add/rename/pick material/reorder/remove, active-layer radio). The PS2 draws the blend the era-correct way: **two-pass GS splatting** — painted chunks draw one extra alpha-blended pass per layer, weights interpolated from the vertices, so layer textures stay **tiled at full resolution** on any map size, and unpainted chunks cost exactly what they always did. The editor viewport draws the same two passes live. Each layer (and the base) also has a **Stochastic tiling** toggle — build-time texture bombing that bakes a larger non-repeating supertile to break the tell-tale tiled-grid repetition (zero runtime cost, best on organic textures) — and a scene-wide **Variation** control adds large soft light/dark ground patches via world-noise baked into the vertex shade (infinite period, tints base and layers coherently). A scene with no layers is exactly the old single-material terrain. Full guide: [docs/terrain-painting.md](docs/terrain-painting.md).
- **View modes** — *Solid*, *Wire* (colored wireframe) and *Wire+Solid* (solid shading with a wireframe overlay); buttons in the viewport corner, the choice is persisted in the `<name>.tyra` project file. *View > Preview > Distance fog* toggles the editor's distance-fog preview off/on (handy for seeing distant geometry while authoring) — a viewport-only convenience that doesn't change the scene's fog or the generated game.
- **Scripts** — user C++ scripts live in `src/scripts/` (subfolders welcome — everything under it compiles) and that directory is **exclusively yours**: engine-generated sources live in `src/gen/`, so the *Scripts* list shows only your files and the editor never regenerates them. The primary, Unity-style flavor is the **object script**: a class derives from `ObjectScript` (see the generated `inc/scripts/script.hpp`), overrides `onStart`/`onUpdate`/`onUsed` and registers with `TYRA_OBJECT_SCRIPT(MyScript);` — it runs only when **attached to an object** (*Properties > Scripts*, attach the same class to any number of objects across scenes). Every attachment becomes its own instance at scene load with its own members and a `self` pointer to the object it hangs on — spin `self`, read its color, react to the player using it. Global scripts still exist for game-wide logic: derive from `Script` (`init`/`update`), register with `TYRA_SCRIPT(MyScript);` and they run every frame in every scene. The *Scripts* section in the *Project* panel lists the files, creates new ones from an attachable stub (**New script...**, also available straight from *Properties > Scripts*, which attaches the new class to the selected object) and opens the project in VS Code (**Open in VS Code**) with working IntelliSense — the generated `.vscode/c_cpp_properties.json` points at the bundled Tyra engine headers and the PS2SDK headers exported from the docker toolchain on first build. Each `ScriptContext` gives access to the engine (pad!), player/camera position, scene objects and the sky color, plus helpers like `padVibrate(ctx, big, small, seconds)` for controller rumble. New FPP projects include an example: walk up to the box and press X — the sky changes color and a message lands in the PCSX2 log. Full guide: [docs/object-scripts.md](docs/object-scripts.md).
- **Empty objects** — `+ Add object > Empty` inserts a pure transform (a small sphere marker in the editor, invisible and non-colliding in the game): an anchor to hang object scripts on, a waypoint for flow-graph logic; scripts read its position/rotation/scale/color.
- **Flow graph** — visual logic (CryEngine-style): wire triggers (On Start, On Button, Near Object, Every N Seconds) to actions (Set Sky Color, Set Object Visible, Move/Recolor Object, Play/Stop Sequence, Log) in the *Flow Graph* tab; the graph compiles into `src/gen/flow_graph.gen.cpp` on every build. Actions that used to come in show/hide pairs are now single nodes with a labeled exec pin per branch — **Set Object Visible** (show/hide/toggle), **Set HUD Visible**, **Set Text Visible**, **Set Layer Loaded** (load/unload) and **Animation** (play/stop). The **Raycast** node casts a ray from the player's eye along the view direction and outputs the hit position and the hit object — wire its object output into Set Object Visible / Set Object Color / Despawn Object for "what am I looking at" mechanics, its position output into Spawn Object / Set Position for aim-placed effects. **Get Position** doubles as a live position source (consumers read the target's current position) and, with its exec input wired, a **sampler**: the position latches the moment the exec fires and the "after" exec chains on — capture "where was it when X happened". **Set Depth Of Field** overrides, disables or restores the authored depth-of-field effect (see *Screen effects*). **Vibrate Pad** rumbles the DualShock (heavy-motor strength 0..1 + the on/off buzz motor) with an optional auto-stop after N seconds — impacts, explosions, heartbeat loops. Need an action the editor doesn't have? Define your own **custom node** in a `flow-nodes/*.flownode` text file — no editor rebuild. A quick node is a tiny header + an inline C++ snippet; a `call = fn` node runs a real function you write in `inc/scripts/flow_nodes.hpp` and can have **input and output pins of any kind** (object/position/bool/text) — e.g. a node that picks the object the player looks at and hands it to a built-in *Set Object Visible*. Copy the file (and its function) to reuse a node in other projects: [docs/custom-flow-nodes.md](docs/custom-flow-nodes.md).
- **NavMesh + NPC AI** — NPCs that find their own way: a navigation grid is **baked from the scene on the host at build time** (terrain slope + blocking objects, tunable in *Preferences > AI navigation*, previewed with *View > Nav mesh overlay*) and the PS2 only runs **A\* on the EE** over the finished bitmap — budgeted at one pathfind per frame, with string-pulled paths so NPCs walk straight lines instead of stair-stepping the grid. Four flow nodes make enemies without a line of code: **Patrol Waypoints** (walks the objects named `wp1`, `wp2`, … in order, pausing at each), **Chase Player** (repaths after the moving player, stops at attack range, optionally gives up), **Flee From Player** (runs until safe) and the **On Player Seen** trigger (vision cone + range + terrain line-of-sight; its bool output feeds the logic gates for "lost sight of the player"). One AI state per object — a Chase interrupts a Patrol; **Stop AI Movement** returns to idle. Agents snap to the terrain and turn to face their motion, so a walk clip on an animated model lines up for free. Scenes without AI nodes carry zero nav data or code. See [docs/navigation-ai.md](docs/navigation-ai.md) and [examples/nav-ai](examples/nav-ai).
- **Cutscene Director** (*Tools > Cutscene Director*) — a keyframe **timeline sequencer** for cinematic cutscenes on the PS2, with a dopesheet UI: one lane per animated object plus a camera lane, keyframes as draggable diamonds (click to select, drag to retime, right-click for easing/delete, double-click a lane to drop a key), a click-scrubbed time ruler with zoom (a *Zoom* slider or **Ctrl + mouse wheel** over the sheet), and a playhead that previews the whole scene live in the viewport. A *sequence* poses scene objects (position/rotation/scale/color/visibility) **and the game camera** over time with per-key easing (linear / smooth / step). Every camera key is a *shot* that films from a **Camera entity** (`+ Add object > Gameplay > Camera` — a film-camera marker with an FOV frustum wedge in the viewport): the shot uses the entity's live pose + FOV, so keyframing the entity itself in an object track gives dolly/crane moves, and Step easing between two cameras is a hard cut. (Place and aim the cameras in the scene, then the camera lane just says *which* camera films *when* — no separate "free" camera to keep in sync.) Shot FOV drives the **real PS2 projection** (restored when the cutscene ends), per-shot **camera shake** adds handheld energy, and each sequence can be **skippable (START)**, **fade in/out from black**, **hide the third-person player avatar** for the duration (so the camera flies free without the body in shot) and mask the frame with **widescreen bars** (Cinema 2.39:1, Wide 16:9, Pillarbox, Frame) that composite over the HUD with per-sequence slide-in/out times (0 = they appear/vanish instantly, like the fades). Fire it from the flow graph with the **Play Sequence** / **Stop Sequence** nodes (e.g. On Used → play a cutscene); the camera track takes over the game camera for the duration and hands it back when the sequence ends. Compiles into `src/gen/sequences.gen.cpp` (a runtime player) on every build. Authoring workflow: while paused, **selected objects keep their real transform** (the preview doesn't fight the gizmo — pose, then snapshot), optional **Auto-key** drops a keyframe at the playhead when a gizmo drag ends, *+ Add object track* opens an object picker with **Add selected**, and the viewport can **look through any Camera entity** (*View:* control in the viewport corner, or *Look through* in the camera's Properties) with one click back to the free camera — the camera you look through hides its own model so it doesn't fill the frame. Turning **Preview in viewport** off still animates the scene (a Camera entity dollies along its track) but leaves the viewport on the free camera, so you can watch the move from outside. **Space** toggles play/stop while the window is focused.
- **Phone camera takes** (*Cutscene Director > Import take...*) — record a real 6DoF camera move on a phone (ARKit world tracking, e.g. the [CamTrackAR](https://fxhome.com/product/camtrackar) iPhone app) and import it **into a chosen Camera entity** — its transform track + FOV are baked from the recording, so the camera dollies along the path (two cameras in one scene each get their own move): "walk around a room looking around" becomes a PS2 cutscene camera move. Reads CamTrackAR `.hfcs` exports and an app-agnostic CSV (spec in [docs/camera-takes.md](docs/camera-takes.md)); the import modal maps the take into the scene (scale "1 m = N units", extra yaw, origin placement at the preview camera, start-at-playhead) and **decimates** the 60 Hz recording with an error-bounded tolerance slider (a 6.6 s take → ~12 keys) so the compiled PS2 keyframe table stays small. After importing, the whole path can be re-positioned and re-oriented (start point + start yaw) without re-importing. Imported shots are ordinary editable keys — scrub, retime or delete them like hand-authored ones. The acquisition/bake split is ready for phase 2: live pose streaming from the phone into the same pipeline.
- **Physics** — rigid-body objects (*Physics* checkbox + per-object Mass/Bounciness/Friction/Tumble/Sleep-after): full 3D velocity, restitution bounces off terrain slopes (real heightfield normals), friction slides, tumbling, body-vs-body momentum exchange, resting on / bouncing off static solids, and player shoves. A thrown body **wakes the sleeping bodies it hits** (the impulse pass trades momentum, so crates knock crates around); tumbling boxes and models **contact the ground through their rotated bound** (they ride on their corners instead of sinking in like spheres) and **settle flat onto their nearest face** as they come to rest. Near-rest bodies sleep after a per-object **Sleep after** delay (default 3 s), so a settled scene costs nothing; the solver's vector math runs on VU0 (`Tyra::Vec4` macro-mode ops) and **moving bodies render through a per-object model matrix on VU1** — geometry bakes once in local space and flies/tumbles with zero per-frame EE rebuild cost (a 28-body scene went 14 → 156 FPS in the vsync-off bench). Scripts get `velocityX/Y/Z` + `spin`, the flow graph gets an *Apply Impulse* node. Plus FPP player physics: gravity, jumping on X, collision with scene objects (a rotated primitive blocks along its real, rotated faces — box collision honors the object's yaw; mesh-collision models block in any orientation — wall steepness is judged in world space, so a physics model resting on its side still has solid walls — and fast steps can't tunnel through into the mesh), walking on top of them.
- **Player entity** (`+ Add object > Gameplay > Player`) — a controllable player that becomes the game camera, in one of three **modes**: **Walk (FPP)** (first-person, gravity + jump + collision), **Noclip (fly)** (free 6DoF, X up / Square down) and **Third person** — an orbit camera that rides a boom behind a **visible avatar**. The avatar is simply the Player's own **animated `.glb` model**: it renders through the exact same skeletal pipeline as NPC animated models, so no new asset workflow. Its clips map to locomotion states — pick an **idle**, **walk** and (optionally) **run**/**jump** clip and the runtime auto-selects and cross-fades them from the player's *actual* planar speed, scaling playback so the feet don't slide. Drop in a model, name three clips, and you have a fully animated character walking/running/idling — **zero scripting**. The escape hatch keeps it flexible: a script or flow-graph **Play Animation** on the Player fires any one-shot (wave, attack) that plays to the end before locomotion resumes, and attached scripts see the avatar as `self`. The third-person camera rides a **spring arm**: the boom is raycast every frame and the camera stops at the first wall/prop/terrain in the way, with side **whisker casts** that see walls coming and ease the boom in ahead of the hit (a hard clamp still guarantees it never clips through; it eases back out when clear), so approaching cover reads as a smooth dolly-in, not a snap. Per-mode tunables (walk/look speed, jump, eye/body height) plus the third-person camera rig live in *Properties*: **distance** (back), **height** (up) and **shoulder** (sideways) are the rig offset in the camera's own frame — set *shoulder* to ~0.6 for a classic **over-the-shoulder** shot (negative = left shoulder; the avatar slides off-center as eye and aim point shift together), plus a **turn rate** for how fast the avatar turns to face its movement. A **camera style** picker widens third person beyond the chase cam: **Orbit (behind)** is the classic free-look rig, while **Top-down**, **Isometric** and **Fixed angle** pin the camera to a set **angle** (elevation above the horizon) and **direction** (world heading = which way is "up" on screen) for camera-locked games — Zelda-style top-down, Diablo-style isometric. Top-down and Isometric are just presets of Fixed angle (picking them seeds the angles, which stay fully editable), the left stick keeps moving the avatar relative to the camera heading, the spring arm still keeps the boom out of geometry, and an optional **Right stick rotates** switch lets the player orbit the pinned view (the elevation stays locked). The Player also carries the camera **Flashlight** (additive spot cone, optional toggle button, flippable from the flow graph). The first Player in a scene drives the camera.
- **Two-player games** (*Preferences > Multiplayer*) — local co-op on one console: **shared screen** (one camera frames both avatars, boom stretching with their separation) or **split screen** (P1 top / P2 bottom, each player's own camera — no projection tricks, a per-half raster bracket in the engine fork). Player 2 is simply the scene's **second Player object** (own spawn, speeds, avatar); they can **join and leave mid-game** — Start on pad 2 (hot-plug friendly) or a ready-made **Player count (1P/2P)** menu option block, both kept in sync. Full guide: [docs/multiplayer.md](docs/multiplayer.md).
- **Custom .obj models** — `+ Model` imports a mesh into `res/models/`; it renders in the viewport and is compiled into the game (≤3000 tris per model). Models behave like any scene object (gizmos, physics, scripts, lighting).
- **Tree Generator** (*Tools > Tree Generator*) — procedural low-poly trees, so you stop hunting for tree models: dial one in against a **live turntable preview** (drag orbits, wheel zooms, *Wireframe* shows the tessellation) and **Add to scene** bakes `.obj` + `.mtl` + a tileable bark PNG + an alpha-cutout leaf card into `res/models/trees/` and drops an ordinary **Model** object in. Nothing new reaches the PS2 — a generated tree is just a static mesh with two materials, so leaves ride the alpha test the static pipeline already does. Presets (**Oak / Birch / Spruce / Poplar / Dead tree / Bush**) plus knobs for trunk (height, flare, taper, gnarliness), branching (1–4 levels, children per level, tilt, ratios), leaves (count, size, foliage style: broadleaf / needles / single blade), bark style and colors. Everything is **deterministic in the seed**, and each branch draws from its own stream, so nudging a slider adjusts the tree instead of reshuffling it — "five oak variants" is five seeds, not a mesh library (**Roll** re-seeds; a preset keeps your seed). Explicit **poly-budget** levers interpolate detail from trunk to twig, with a live triangle count (the presets land at 437–943 tris); the practical limit is instance count, since models don't join static batching. Full guide: [docs/tree-generator.md](docs/tree-generator.md).
- **Animated models (.glb, .fbx)** — import a skinned/rigged model (*Project > Assets > Import model...*, then *+ Add object > Model > your file `(animated)`*): **glTF Binary** from Blender, or **FBX** straight from Blender/Maya/3ds Max (read by the vendored [ufbx](https://github.com/ufbx/ufbx); axes/units auto-normalized, so a centimeter Maya rig imports at the right size; FBX animation curves are resampled and keyframe-reduced into the same runtime data, take names like `Armature|Walk` shorten to `Walk`, and textures referenced as separate files are copied into the project on import). A real skeletal runtime plays named clips on the PS2 — EE pose evaluation, VU0 macro-mode skinning, rendered through the same static pipeline as everything else — with crossfade blending between clips and per-object *start clip / autoplay / loop / speed / color / box collision*, plus an optional **`.mtl` material override** (on top of the file's built-in materials, resolved by part name and baked into the model — the same override a static `.obj` takes; the Material picker's **+ New material from this model** extracts the model's own materials into an editable `.mtl` you then edit/paint in the **Material Editor** previewed on the model itself). Trigger clips from the flow graph (the **Animation** node's play/stop pins, **On Animation Finished**) or from scripts (`playAnimation` / `stopAnimation` / `animationFinished`). Clip length is nearly free (~150 KB for a 1500-vertex character with three clips); three stacking LOD levers keep crowds under the frame budget — per-object **draw distance**, project-wide **animation LOD** (distant instances re-pose every 2nd/4th frame) and **mesh LOD** (build-baked decimated variants). Full guide: [docs/animated-models.md](docs/animated-models.md).
- **Texture atlasing** (*Preferences > Build > Texture atlasing*, off by default) — small clamp-safe material textures pack into shared **256×256 pages** at build: one GS VRAM allocation (+~8 KB overhead) per page instead of per texture, fewer texture switches. Conservative eligibility (model UVs checked against the real mesh; tiled terrain, emitters, decals, sphere maps and quality-pinned textures keep their own files); model UVs remap through a `# tyra-uvrect` hint in the baked `.mtl`, primitives remap in the generated builders — sources in `res/` are never touched. Palettized projects share one 256-color CLUT per page, the era-authentic trade. The boot log prints what was packed. Full guide: [docs/texture-atlasing.md](docs/texture-atlasing.md).
- **Static batching** (*Preferences > Rendering > Static object batching*, on by default) — the generated game merges non-moving primitive objects that share a material into combined draw bags at scene load. On real hardware every separate object costs ~1 ms of fixed per-submit EE overhead regardless of size (PCSX2's fast EE hides it), so a map decorated with dozens of small boxes/pillars pays for its object *count* — batched, a cluster pays once. Objects with physics, scripts, flow-graph references, mirror/portal view-list references, save-state or a streaming layer stay individual, and a batched object edited at runtime (Live Link, Raycast-driven actions, scripts) drops back to its own bag automatically — batching is a pure optimization, never a behavior change. The boot log prints `Static batching: N objects in M batches`.
- **Directional lighting** — light direction + ambient/diffuse in preferences, baked into vertex colors; identical shading in the viewport and on the PS2.
- **Baked ambient occlusion (contact shadows)** — soft shadows where geometry meets: terrain self-shadowing (ravines, foot of hills) and darkening where objects touch the ground and each other. Baked at build into **per-pixel AO textures** (a terrain map + a per-scene primitive lightmap atlas) drawn as extra blended passes — smooth, no visible triangle edges. Scene-wide strength/radius live in *Tools > Ambience Editor* (enabled by default for new projects); **which objects cast is per object** — *Properties > Cast shadow*. Previewed live in the viewport. Imported/animated models cast but don't receive (their per-vertex bake read as triangulated shading — parked until a lightmap unwrap exists). See [docs/ambient-occlusion.md](docs/ambient-occlusion.md).
- **Sky** — gradient dome (horizon/zenith colors) or flat clear color; scripts can retint it at runtime.
- **HUD from images** — `+ Image (PNG)` imports into `res/hud/`; position/size editable with a live preview over the viewport; rendered in-game as 2D sprites. The built-in **USE prompt** is a pinned entry in *Tools > UI Editor*: reposition/resize it or replace its sprite with a custom PNG (reset to the built-in anytime).
- **Fonts** — *Tools > Font Manager*: the project's typefaces, each an entry (name + a TTF imported into the project or a stock Windows font). Everything that draws text — HUD texts, menus, loading screens, *Display Text* nodes — picks one **by name**, so restyling a project is one edit here. The first entry is the default every unset reference falls back to; replace it to restyle everything at once. No TTF ever reaches the PS2: static text is rasterized to sprites at build, and only a font a *Display Text* node uses additionally bakes a glyph atlas.
- **On-screen texts** — *Tools > UI Editor > Texts*: named texts (font, size, color, multi-line, drop shadow) baked to sprites at build — the PS2 engine has no font. The *Set Text Visible* flow node's show/hide pins trigger them at runtime, with an optional auto-hide after N seconds: subtitles, tutorial hints, pickup toasts. The string is frozen at build.
- **Runtime text** — the **Display Text** flow node draws a string that is only known while the game runs (a score, a save value, a timer), so it cannot be a pre-baked sprite. Wire any text source into it (*Get Save Text*, *Get Int As Text*, *Position To Text*, ...), give it a font, screen position and size, and drive its **show** and **hide** pins; a static prefix ("Score: ") sits in front of the wired value. It draws glyph by glyph from the font's baked atlas, and that atlas only reaches VRAM the first time the text is actually on screen — a font nobody displays costs nothing.
- **Screen effects** — *Tools > UI Editor* composites the whole screen as one reorderable **screen stack**: the built-in **bloom** (+ color grading) and **film grain** effects and the HUD sprites, dragged into the order they draw (e.g. bloom under the HUD so it doesn't blur the crosshair, grain over everything). A **depth of field** effect blurs the image past a focus distance — per-pixel, following real scene depth (the blurred frame is composited back through z-tested sprites). It is authored as its own pinned stack entry (*Amount* / *Focus* / *Range*, per-scene overridable in *Scene > Preferences > Post effects*) that always composites right after the 3D scene, under the whole HUD — sprites stamp depth across their full rectangle, so compositing DoF above them would punch sharp boxes into the blur; pinned underneath, the HUD always stays crisp. At runtime the *Set Depth Of Field* flow node overrides it (custom focus / range / amount, or wire a position to keep an object in focus), switches it off, or restores the scene's authored values (*Scene setting* mode). Need an effect the editor doesn't have? Define your own **custom screen effect** in a `screen-effects/*.screenfx` text file — no editor rebuild. There are no pixel shaders on the PS2, so an effect is written **low-level** (a small manifest + raw GS-blit C++, the same way bloom/grain are built); it appears as a positionable stack entry with numeric parameters. Copy the file to reuse it in other projects: [docs/custom-screen-effects.md](docs/custom-screen-effects.md).
- **Game menus** — *Project* panel, *Menus*: panels baked to sprites at build (title, entry rows, fonts, images, accent) and driven by the dpad in-game. Entry actions: close, switch scene, open the save menu, open a submenu, set/add a save value, fire a flow event — plus stateful **Toggle** and **Choice** rows bound to a save value (the current option label renders right-aligned on the row; Cross / dpad left/right cycle it, flow graphs react via *Value At Least* → *On Condition*).
- **Options menus** — the Menu Editor scaffolds settings screens: **+ Options menu** builds an *OPTIONS* root that opens *AUDIO* / *CONTROLS* / *DISPLAY* submenus (categories are plain submenus, so all styling applies), and **+ Option block** drops a ready-made row bound to a built-in engine setting — music / sound volume, controller deadzone, aim response curve, display mode (480i/480p/1080i/480i field rendering/full-height PAL 576i) and widescreen (4:3/16:9). Each block is a normal Toggle/Choice row you can restyle and relabel; the generated game applies the chosen option to the engine every frame, no flow wiring needed (persisted in the save value like any stateful row). The display-mode row's options are picked from a **dropdown of the engine's scan modes** (offer any subset, in any order, with a free-text label), including a **Default (project)** entry that maps to whatever mode the game booted in on the player's console (the region + PAL-picture default, or the project's fixed mode) — so a typical row is DEFAULT / 480p / 1080i and "default" always means the right thing per region, and an **Apply video mode** row makes it stage-then-commit: while one exists anywhere in the project, cycling the display option only stages the choice and the screen switches when the player picks APPLY (with the keep-or-revert prompt); without one the row keeps the classic switch-on-change behavior. The scaffolded *DISPLAY* submenu includes the APPLY row.
- **Boot splash screens** — *Tools > Loading Screens > Boot splash screens*: images (studio / publisher / "presents" cards) shown in order at startup, after the always-present Tyra engine logo and before the loading screen, each for a configurable duration. Images only for now.
- **Loading screens** — *Tools > Loading Screens*: define named loading screens shown while a scene loads (also at boot). Each has a background color, image and text elements (baked like the HUD) and **progress bars** — *continuous* (a track with a fill that grows) or *quantized* (N segments that light up one per 1/N of progress; segments are colored rects or an optional PNG tinted on/off). The bar reflects **real** load progress: the game counts the work (streamed assets + objects + terrain chunks) and presents the screen every few units. Assign a screen per scene in *Scene > Preferences*, mark one the project default, or leave a scene unset to use the default; with none defined, the built-in `loading.png`-on-black is shown. The master toggle stays *Project > Preferences > "Loading screen between scenes"*. See [docs/loading-screens.md](docs/loading-screens.md).
- **Runtime scene** — scripts receive mutable `RuntimeObject`s (move/hide/recolor objects every frame); geometry rebuilds automatically.
- **Project preferences** (`Project > Preferences`, `Ctrl+,`) — game template, terrain size and detail (max grid cells), **video output** (target system NTSC/PAL/auto plus the scan mode: stock interlaced 480i/576i, interlaced with **true field rendering** — a fresh half-height 512x224 image every field, i.e. 50/60 distinct pictures per second at full speed for about half the fill and VRAM cost of whole frames, the classic PS2-era recipe — flicker-free **progressive 480p**, pillarboxed **1080i** — the two DTV modes need component cables on a real console and always run at 60 Hz — or full-height **PAL 576i**: a true 512-line PAL frame (the "full PAL" of European retail releases, ~14% more picture than the NTSC-sized modes), always a 50 Hz PAL signal regardless of the target system, at the cost of ~380 KB of GS VRAM. The region-following interlaced mode additionally has a **PAL picture** choice — *Letterbox* keeps the classic NTSC-size 448-line picture on PAL consoles, *Full-height 576i* promotes them to the true 512-line frame at boot (NTSC consoles always get 480i), so one build serves both regions the way the author intends; PCSX2 shows every mode — and a **Widescreen (16:9)** switch that widens the projection anamorphically for widescreen TVs), **triangle handling** (*Precise clipping on VU1* — the default: no holes at screen edges and no EE cost, triangles are clipped by the VU1 microprograms; *Precise clipping on EE* — the legacy CPU clipper, kept for comparison/fallback (projects saved before the VU1 default keep it automatically); *Fast culling* — fastest, large near triangles may vanish), sky color, FPP camera (eye height, walk/look speed) and orbit speed. The scan mode and widescreen can also be changed at runtime from the flow graph (**Set Display Mode** / **Set Widescreen**): Set Display Mode optionally shows a "keep video mode?" prompt that reverts automatically unless the player confirms with X in time — so a mode the TV can't display never strands anyone on a black screen. Stored in the `<name>.tyra` project file and baked into the generated `terrain_config.hpp` on every build; the viewport reflects sky color and terrain detail immediately. A **debug** build profile also enables on-screen overlays (*Show FPS*, *Show memory usage*, and a per-phase EE-time **frame profiler** — whole frame / scene / usable-highlight / particles; see [docs/profiling.md](docs/profiling.md)), all stripped from release builds.
- **Pickable objects** — check **Pickable** on any solid object and the player can press **USE** on it to pick it up (the on-screen prompt says **PICK UP** instead of USE — built-in `res/hud/pickup.png`, replace to customize): it hovers a short reach in front of the face and is **swept against the world every frame**, so it keeps colliding with walls and props — you can neither push it through geometry nor park it behind something. The carry reach follows the third-person spring arm's policy: a blocked reach **snaps in** (the object comes closer to the face, never into the wall) and eases back out when the wall clears; a **carry whisker** in the walker pushes the carrying player back from geometry the object no longer fits in front of, so you can't press face-first into a wall while holding something. It stops colliding only with its *carrier* (it can't wedge the player, and the third-person spring arm ignores it). USE again drops it exactly where it hovers — always a legal spot; give the object **Physics** and it's handed straight back to the rigid-body sim on release (it wakes, falls, bounces and rolls with its own mass/bounce/friction/tumble), while a non-physics object simply stays where you left it. An experimental **Can throw** option launches the carried object with **Circle** (`BTN_THROW`): a physics object is thrown *by the sim* — it arcs, bounces off walls and tumbles to a stop — and a non-physics one flies a simple swept arc that stops on the first hit. Reach, throw speed and the button live in `inc/controls.hpp`. A pickable object can also be *Usable* — the same press fires **On Used** (wire a grab sound) and picks it up; while your hands are full there is no use-targeting, USE means "drop".
- **Usable-object highlight** — objects marked *Usable* glow while the player is within a proximity distance (color / rim width / blur steps / opacity in *Preferences > Usable objects*, per-scene overridable). Drawn cheaply on VU1 as grown silhouette shells; opacity sets the strongest shell's transparency (the rest fade from it), and an experimental **Draw over object** toggle paints the glow *on* the surface instead of only a rim behind it.
- **Build & Run in PCSX2** (`F5`) — builds the ELF inside a Docker container (the `h4570/tyra` image with the PS2DEV toolchain) and launches it in PCSX2. Build logs stream into the *Output* window.
- **Live Link** — edit the **running** game: with the *debug* build profile, moving / rotating / scaling / recoloring objects streams into the game live (a gizmo drag moves the object on screen as you drag), and **adding / deleting objects works too** — new objects are instantiated through the game's runtime spawn pool (cloning a same-recipe authored object), deleted ones are hidden, undo restores them. Works in PCSX2 **and on a real PS2** — the snapshots travel over the same host filesystem the game loads assets from, so no extra transport exists. The toolbar **LIVE chip** shows the state (green streaming / amber "rebuild" when an edit can't be applied live — recipes changed, no template to clone, baked lights/decals/mirrors…) and **clicking it toggles Live Link per project** (also *Build > Live Link* and *Project > Preferences > Build*); off = the game is built without the poller, and release builds never carry it. **Texture hot reload** rides the same channel: repaint a texture in the Material Editor (or re-bake its AO layer) and the running game **re-uploads the pixels into the texture's existing GS VRAM allocation** within a fraction of a second — paint in the editor, watch it change on the console, no rebuild. See [docs/live-link.md](docs/live-link.md).
- **Graceful errors** — engine errors in the running game no longer take over the console screen. **Missing assets degrade instead of crashing**: a missing/broken texture shows an obvious magenta placeholder, a missing model/sound/animation is skipped, and the game keeps running. Genuinely fatal errors (a real assertion) halt the game with the last frame left on screen. Either way the editor tails the game log and pops the error in a **copyable** dialog (worded "kept running" vs "stopped"), flashing the editor window for attention. The same text is in the *Debug* window (*Game log*). Turn the popup off with *Pop up on errors* there (or in the dialog) to let errors go only to the console — the setting lives in `editor.ini`.

## CLI

Projects can also be created and built headlessly:

```powershell
tyrax-editor.exe --new <name> <parentDir> [width] [depth] [orbit|fpp]
tyrax-editor.exe --build <projectDir> [--run]
tyrax-editor.exe --resave <projectDir>        # load + save (runs format migrations)
tyrax-editor.exe --refresh-gen <projectDir>   # regenerate game sources (no Docker)
tyrax-editor.exe <projectDir|project.tyra>    # open GUI with a project loaded
```

`--resave` loads a project and writes it straight back out, running every
on-disk format migration in the process (e.g. stamping stable object ids on
older projects). Use it to batch-migrate existing projects to the current
format without opening the GUI.

A second family of commands targets AI assistants working inside a generated
project — `--dump`, `--list-nodes`, `--dump-graph`, `--apply-graph`,
`--ai-graph`, `--add-ai-support` — see [docs/ai-tools.md](docs/ai-tools.md).

## How Build & Run works

1. `docker compose up -d --build` in the project directory (the first run downloads the `h4570/tyra` image). Each project gets its own container (`<name>-compiler-1`).
2. The Tyra engine sources live **in this repo** (`vendor/tyra`, bind-mounted read-only at `/engine-src`). The Runner syncs them into the shared build volume (`tyra-engine-shared`, mounted at `/tyra`) with a checksum `rsync`; when anything changed, `libtyra` is rebuilt once and every game relinks against it — all projects share the result.
3. `rsync` project sources into the container volume (`/host` → `/src`).
4. `make` inside the container (`mips64r5900el-ps2-elf-g++` compiler).
5. `rsync` the `bin/` directory back to the host.
6. Launch `pcsx2-qt.exe -elf <project>\bin\<name>.elf`.

## Run on a real PS2 (network deploy)

With a PS2 connected to the LAN and running [ps2link](https://github.com/ps2dev/ps2link)
(one-time memory-card install), **Build > Build && Run on PS2** (`F6`) boots the
game on the console over ethernet: the ELF and every asset are served straight
from the project's `bin\` on this PC (no ISO, no SMB), and the console's log
streams live into the *Output* window as `[ps2]` lines. Set the console's IP
under `Edit > Preferences > Real PS2` (a machine-global editor setting, shared
by every project); headless: `--build <projectDir>
--run-ps2 [ip]`. The editor drives the console with a patched
[ps2client](https://github.com/ps2dev/ps2client) shipped in `tools/ps2client`
(see the README there — the patch fixes a Nagle/delayed-ACK stall that made
file serving ~100x slower).

## The in-tree Tyra engine

`vendor/tyra/engine` is a fork of the [Tyra engine](https://github.com/h4570/tyra) (Apache License 2.0, forked at `9273416`), maintained directly in this repo — edit it and the next Build & Run picks the change up automatically. The editor's modifications over upstream (marked `Modified by TyraX` / `TyraX guard band` in the sources):

- `planes_clip_algorithm.cpp` — Cohen–Sutherland outcodes: fully-visible triangles skip the 6-plane clipper, fully-outside ones are rejected instantly.
- `stapip_clipper.cpp`, `stapip_qbuffer.cpp` — static pools instead of per-call heap allocations.
- `render_bbox.cpp` — guard-band frustum margins; only near-plane-crossing geometry goes to the EE clipper, side overflow is left to the GS scissor.
- `vcl_sml.i` (`PerformClipCheck`) — VU1 guard band: XY accepted up to 3× outside the clip volume (the GS scissor trims pixels), with an explicit w ≤ 0 test for behind-the-camera vertices.
- `audio_song.cpp` — the song player reads the WAV header (PCM 8/16-bit, mono/stereo, standard rates, arbitrary chunk layout) instead of assuming 16-bit/22050 Hz/stereo with samples at a fixed offset.
- `pad.cpp` — `Pad::setActuators()`: runtime DualShock vibration control (the on/off buzz motor + the 0–255 heavy motor), driven by the *Vibrate Pad* flow node and the `padVibrate()` script helper.

Generated games additionally enable the real per-triangle clipper (`fullClipChecks` + `Precise` culling) and correct `PlanesClipAlgorithm::clipMargin` (the upstream default pushes the near clip plane ~10 units away from the camera).

Before each build the editor refreshes its generated files: `Dockerfile`, `docker-compose.yml`, `inc/terrain_config.hpp` and `inc/scene_data.hpp` are always rewritten from project data; `src/terrain_game.cpp` and `inc/terrain_game.hpp` are rewritten only while their first line still contains the `Generated by TyraX` marker — delete that line to take ownership of a file (scene objects will then stop syncing into the game code automatically).

- [examples/video-modes](examples/video-modes) — display-mode test bed: a VIDEO OPTIONS menu (opens at boot, Start reopens it) switches 480i / 480p / 1080i and 4:3 / 16:9 at runtime, with the keep-or-revert confirm prompt (see its [README](examples/video-modes/README.md)).
- [examples/custom-nodes](examples/custom-nodes) — [custom flow-graph nodes](docs/custom-flow-nodes.md): press Cross and a C++-backed node picks the nearest crate at runtime and feeds it to a built-in Set Object Visible; press Square and an inline-snippet node spins a crate (see its [README](examples/custom-nodes/README.md)).
- [examples/large-terrain](examples/large-terrain) — a 2048×2048 world that never fits in 32 MB at once, kept playable by chunked view-distance terrain streaming, ~1100 draw-distance-culled props and 80 skeletal-animated "wobblers" that stress the [animation/mesh LOD chain](docs/animated-models.md); ships in the debug profile so the on-screen FPS/MEM overlay is visible (see its [README](examples/large-terrain/README.md)).
- [examples/object-spawning](examples/object-spawning) — runtime object spawning driven entirely from a flow graph: **Spawn Object** clones an animated template at a marker on a timer and its object output feeds a **Despawn Object** that removes exactly that clone after a delay — the missing piece for GTA-style traffic (see its [README](examples/object-spawning/README.md)).
- [examples/physics-playground](examples/physics-playground) — the rigid-body physics stress scene: **28 high-bounce bodies** rain onto a terraced slope, ricochet off the terrace edges, tumble, roll downhill and fall asleep one by one; a flow-graph **Apply Impulse** kicks a ball every 3 s while logging its position. Ships debug + FPS overlay + vsync off, so it doubles as the physics perf bench (the VU1 fast path was measured on it: 14 → 156 FPS mid-flight; see its [README](examples/physics-playground/README.md)).
- [examples/nav-ai](examples/nav-ai) — [NavMesh + NPC AI](docs/navigation-ai.md): a guard patrols waypoints around a wall (A* detours it on its own), spots you in its vision cone and gives chase; a rabbit flees on sight — all wired in the flow graph, zero scripting (see its [README](examples/nav-ai/README.md)).
- [examples/reflections](examples/reflections) — a first-person **chrome showroom** for [reflective materials](docs/reflective-materials.md): an avenue of pedestals pairing **static sphere-map** chrome against the **dynamic `@sky` mode** (the sky dome re-rendered into the map every frame, GT3-style), a mirror monolith, car-paint spheres — and a flow-graph **sky cycler** that flips the sky to a sunset every 14 s so you can watch only the dynamic reflections follow (see its [README](examples/reflections/README.md)).
- [examples/portals](examples/portals) — **Portal objects**: a linked pair with a live view through the surface to the other end of the map, an unattended scripted walk-through that teleports the player exactly where the view promised, and the classic **infinite fall** — a physics cube endlessly dropping from a floor portal out of a ceiling portal, velocity carried through every pass (see its [README](examples/portals/README.md)).
- [examples/mirror-room](examples/mirror-room) — a working **Mirror object**: a wall built around an opening, the glass filling it, and the room's props + walls + **the third-person avatar** reflecting live on the other side — walk behind the wall to see the PS2-era trick from backstage (see its [README](examples/mirror-room/README.md)).

- [examples/probe-aim](examples/probe-aim) — a **crystal ball that shows what's behind you**: the *Reflection probe: aim along the reflected ray* preference in action — chrome ball + monolith with the `@sky` dynamic env map, colorful props behind the spawn reflecting in the middle of the chrome like in a real mirror (flip the preference off and rebuild to see the classic level-forward aim reduce them to distant smudges; see its [README](examples/probe-aim/README.md)).

- [examples/raytraced-mirror](examples/raytraced-mirror) — the **raytraced Mirror** PoC as a playable level: a glass wall whose reflection is **ray-traced per pixel on a VU0 microprogram** every frame — floating balls, a textured crate and an animated model all reflecting live (spheres, slabs, textured triangle meshes and skinned proxies), your own reflection following you, and a *Reflection resolution* knob from 32×32 up to a glorious slideshow at 512×512 (see its [README](examples/raytraced-mirror/README.md)).
- [examples/texture-feeds](examples/texture-feeds) — **live screens**: two monitors on a wall, one showing a **CCTV camera feed** (a Camera entity rendering the scene — terrain and all — into a texture every frame), the other **streaming a raytraced mirror's image** onto an ordinary box; the classic 2002 security-monitor set piece, both feed kinds live in one frame (see its [README](examples/texture-feeds/README.md)).
- [examples/material-lab](examples/material-lab) — the **material pipeline on one pedestal**: a stone altar whose texture is a live layer stack (base stone → **raytraced baked AO** → **smart masks**: cavity grime + noise-broken edge wear, all regenerable in the Material Editor), brick pillars and tiled orbs shipping inside a shared **texture atlas** (`Texture atlas: 3 textures in 2 page(s)` in the boot log), a big **paint canvas** wall wired for **live texture hot reload** (F5, paint, watch the console repaint itself — the canvas is deliberately too big for the atlas so it stays hot-reloadable), a reusable `worn-stone` **material preset** and per-material `# tyra-bake` parameters; opens with the Material Editor already docked, ships debug so the live loop works out of the box (see its [README](examples/material-lab/README.md)).
- [examples/two-players](examples/two-players) — **local co-op**: a title menu picks 1P/2P, the screen splits top/bottom into each player's own third-person camera (two cat avatars - ginger on pad 1, gray on pad 2), player 2 can hot-join with Start on pad 2 and the pause menu switches player count mid-game (see its [README](examples/two-players/README.md)).

## Structure

- `src/` — editor code (`app` UI, `viewport` GL preview, `project`+`templates` project generator, `flownode` custom flow-graph node loader, `aigen` AI flow-graph generation, `aisupport` AI-support installer, `runner` docker/PCSX2 pipeline, `gl_loader` minimal GL loader).
- `ai-support/` — source markdown for the AI assistant guides installed into projects (embedded into the exe at build time; see [docs/ai-support.md](docs/ai-support.md)).
- `examples/` — example projects: a general playground (`script-demo`), a large multi-feature `showcase`, and focused per-feature demos.
- `vendor/tyra/engine` — the in-tree Tyra engine fork (versioned; Apache License 2.0).
- `vendor/` (rest) — editor dependencies (not versioned; see `setup.ps1`).
- `tools/` — PS2 network-deploy tools (`ps2client` versioned, the rest fetched by `setup.ps1`) and the [VS Code extension](docs/vscode-extension.md) (`vscode-tyrax`) for `.flownode`/`.screenfx` files.
