# TyraX

An editor for the [Tyra](https://github.com/h4570/tyra) PlayStation 2 game engine. C++20 + Dear ImGui (docking) + GLFW + OpenGL 3.3. Runs on **Windows and Linux** from one source tree.

![The TyraX editor in its default Face buttons theme: the Project panel (scenes, objects, layers, assets) on the left, the 3D viewport with a checkerboard terrain, scene objects, a transform gizmo and camera-entity frustum wedges in the center, the Properties panel for the selected box on the right, and the build Output docked below.](docs/img/editor-overview.png)

## Quickstart

**Windows**

```powershell
# 1. Install prerequisites (skip what you already have)
scoop install mingw cmake ninja       # editor toolchain
scoop install ccache                  # optional; picked up automatically if present
# + Docker Desktop (running) and PCSX2 in Program Files\PCSX2 (with BIOS configured)

# 2. Build and run the editor (clones deps + configures + builds)
./build.ps1 -Run
```

From a plain `cmd.exe` (or a double-click) use `build.cmd` / `build.cmd run` /
`build.cmd clean` / `build.cmd dev` and `setup.cmd` instead — thin wrappers that forward
to the PowerShell scripts with the execution policy bypassed, so there is only
ever one implementation and one dependency list to keep current.

**The Windows toolchain is MinGW-w64 GCC — MSVC is not supported.** Opening the
folder in Visual Studio and building the default `x64-Debug` CMake preset does
not work and cannot be made to work by tweaking flags: `src/templates.cpp` holds
the PS2 project templates as raw string literals well past MSVC's hard
16380-byte cap per literal, so it fails with dozens of *C2026 string too big*.
(The `min` macro from `windows.h` colliding with `std::min` in `src/wire.cpp` —
C2589/C2660 — is the same build, and only the first symptom you happen to see.)
Build with `build.ps1`/`build.cmd`, or point Visual Studio's CMake settings at
the scoop MinGW kit rather than the MSVC one.

**Linux**

```bash
# 1. Install prerequisites (toolchain + X11/Wayland/GL headers + zenity + ccache)
./setup.sh --deps
# + Docker (running) and PCSX2 (package, flatpak or AppImage, with BIOS configured)

# 2. Build and run the editor (clones deps + configures + builds)
./build.sh --run
```

`setup.sh --deps` picks the package list for your package manager (apt / dnf / pacman / zypper) and installs it with `sudo`, falling back to `pkexec` when there is no terminal to authenticate in. It is the only part that needs root, which is why it is opt-in — plain `./setup.sh` just fetches `vendor/` and `tools/`. On a machine that already has a toolchain you can skip straight to `./build.sh`.

Both build scripts handle the rest: fetch the `vendor/` dependencies at their pinned commits on first run, check the toolchain (and name the exact install command when something is missing), configure CMake and build. Flags: `-Run`/`--run` launches the editor after building, `-Clean`/`--clean` rebuilds from scratch. The dependency lists live in one place per platform (`deps.ps1` / `deps.sh`), which both the setup and the build script read.

`-Dev`/`--dev` builds for **iteration speed instead of run speed** (`-O1`, into its own `build-dev/` so switching back and forth costs nothing): a clean build is roughly a third faster and a one-file edit rebuilds in a few seconds. The host bakes (GI, material raytracing, ambient occlusion, texture quantization) are genuinely slow in it, so it is for working on the UI and the model, never for a release or a benchmark. If **ccache** (or sccache) is on `PATH`, CMake picks it up automatically — which matters here because the repo is normally checked out in several git worktrees at once, each with its own build directory compiling the same translation units from scratch. `setup.sh --deps` installs it on Linux, `scoop install ccache` on Windows; because CMake caches the *miss*, installing it after a build directory already exists needs a `-Clean`/`--clean` (or a deleted build dir) before it takes effect. `-DTYRAX_COMPILER_CACHE=OFF` opts out.

Everything the two platforms disagree about — spawning child processes, native file dialogs, where the machine-global config lives, which system fonts exist, how to reveal a file in the file manager — lives behind [`src/platform.hpp`](src/platform.hpp). Projects are portable between the two: the `.tyra` format is identical, and a font referenced by a name this OS doesn't have falls back instead of failing the bake.

On Linux the editor registers itself with the desktop on every start — `~/.local/share/applications/tyrax-editor.desktop` plus its icon under `~/.local/share/icons/hicolor/` — so the window, the dock and the app grid all show the TyraX icon and `Exec=` keeps pointing at wherever the binary currently is. That entry is not a nicety: under Wayland there is no protocol for an application to set its own window icon, the compositor resolves it from the `.desktop` file matching the window's app id. (Windows takes its icon from a resource inside the .exe and installs nothing.)

Then in the editor:

1. `File > New Project` (`Ctrl+N`) — pick a name, location, the **world scale** (1 unit = 1 meter unless your content says otherwise) and the flat terrain size (100 × 100 units by default), hit **Create**.
2. The *Viewport* shows the terrain preview (drag to orbit, scroll to zoom).
3. Press **Build & Run** (`F5`) — the first build downloads the `h4570/tyra` Docker image and compiles the engine inside the container (a few minutes, one time). Subsequent builds take seconds. PCSX2 boots your ELF automatically.

## Features (MVP)

- **New project** (`File > New Project`, `Ctrl+N`) — name, location (defaults to the folder set in `Edit > Preferences > New projects`, otherwise `~/TyraProjects`), the **world scale**, flat terrain size (width × depth in world units, **100 × 100** by default) and one of three **presets**: **FPP (first person)** — a Player entity you walk with the left analog stick and look around with using the right one; **Third person** — the same Player entity with the camera on a boom behind it, its avatar being that object's own animated model (`.glb`/`.fbx`, assigned later in *Properties* — the rig and the movement work without one); or **Empty (no objects)** — an empty scene whose camera does not move on its own: add a player, or drive the camera from your own code, a Camera object or a cutscene. (The camera still circles the terrain in any scene that has no Player object *and* a non-zero `Preferences > Camera > Orbit speed`; the Empty preset just starts that at 0, and projects made before this keep their turntable.) The preset is **fixed for the project's life**: it decides which game-template sources are generated, and those are user-ownable, so switching afterwards would either overwrite your work or leave an owned source no longer matching what the project builds. `Project > Preferences` shows it greyed out and says so; the player's own camera settings (mode, boom distance/height/shoulder, camera style) stay editable on the Player object. Generates a complete Tyra game project: `Makefile`, `docker-compose.yml`, C++ sources rendering the scene (StaticPipeline, no asset files needed) and the single `<name>.tyra` project file. **World scale** — how many world units a real-world meter is ([docs/world-scale.md](docs/world-scale.md)) — is asked here because it is the one setting that is genuinely awkward to change later: it deliberately rescales nothing, so a world built at the wrong scale stays that size. The metric-by-definition defaults follow the choice, so the FPP preset is a 1.8 m player walking 5 m/s whatever you pick. A fresh project is also set up for **authoring** rather than shipping: the **debug** build profile with **Live Link** on (edit the running game; the overlays are one tick away) and **USB keyboard & mouse off**, so a pad game doesn't load drivers it never uses. New projects additionally start with **PAL picture: Full-height 576i** — on a PAL console the region-following interlaced mode boots the true 512-line frame instead of the letterboxed NTSC-size picture, which is what a 50 Hz signal is for; NTSC consoles are unaffected and still get their own 448 lines. All are in `Project > Preferences > Build` — the dialog says so, and the `(?)` next to each line explains why.
- **Open project** (`Ctrl+O`) — pick the project's `<name>.tyra` file.
- **Recent projects** — with no project open, the *Viewport* is a welcome screen: **New project** / **Open project** plus the last ten projects you opened (name over path, most recent first). One click opens one — the common "carry on with yesterday's project" needs no file dialog. An entry whose folder moved or was deleted stays listed but greyed with *(missing)*, and every row has an **x** that drops it from the list (it only forgets the shortcut — nothing on disk is touched). The same list is in **`File > Recent Projects`** while a project *is* open (name in the item, full folder in its tooltip, **Clear list** at the bottom), so switching to another project is two clicks instead of close-then-file-dialog. The list lives in `editor.ini`, so it follows the PC rather than any project.
- **Close project** (`File > Close Project`) — puts the editor back on that welcome screen without quitting it: the project is released, the panels go back to *No project open*, and the recent list is right there to pick the next one. Unsaved edits prompt first (the same Save / Don't Save / Cancel dialog as *Exit*). Anything bound to the project lets go with it — a live collaboration session ends, a running build is cancelled, a phone-camera recording is baked into its cutscene and stopped, a GI bake is cancelled — while a game already running in PCSX2 is left alone. Deliberately **no keyboard shortcut**: `Ctrl+W` sits one slip away from the `W` that flies the viewport camera.
- **Spawn point** — a special scene object (marker with a direction arrow, no geometry in the game). In the FPP template the player starts at the first spawn point, facing its Y rotation.
- **Scene objects** — insert simple 3D primitives (box, sphere, cylinder, cone) via the *Scene* menu or the buttons in the *Project* panel. Each object has a name, position, rotation, scale and color, editable in the *Project* panel and saved to its own `objects/<id>.json` file (one file per object, keyed by a stable id). The list carries a **name search and a type filter** — the type dropdown offers only the types the scene actually contains, each with its count, the layer/prefab group headers count what the filter left, and a *N of M objects shown* line with **Clear filters** says what is being hidden (the filters are a view, so the selection and the Properties panel are untouched). Objects render both in the editor viewport and on the PS2 (scene data is regenerated into `inc/scene_data.hpp` on every build).
- **Decals** (signs, posters, text on walls, fake shadows) — insert a *Decal*, assign a material whose `map_Kd` PNG has transparency, and it draws as an alpha-cutout image. A flat decal is a simple quad you stick on a flat surface; tick **"Project onto surfaces"** and it instead **wraps onto the receiver geometry** (angled/curved walls, models, terrain) so wall text and fake blob shadows conform to what they cover. The projection is computed entirely on the host at build time and baked to static geometry — it draws through the normal pipeline with **zero extra PS2 CPU cost** (no runtime projection or clipping).
- **Mirror objects** — `+ Add object > 3D Object > Mirror` inserts a rectangle that fakes a real mirror the PS2 way: the game **re-draws a hard list of objects** (picked in *Properties > Mirror*) a second time, reflected across the glass plane — no render-to-texture, no stencil, just a reflection matrix over the same vertex arrays on VU1, so moving objects and even **animated models reflect their live pose** for free. An optional **Reflect player** switch mirrors the third-person avatar (an FPP player has no body — vampire rules). The glass itself is a color-tinted quad with an **opacity** slider that blends over the copies. The copies are *real geometry on the far side of the plane*, so build the mirror into a wall (or give it a backing) — the wall hides the mirror world outside the frame, exactly like the classic PS2/PS1 mirror rooms. The editor viewport previews the whole illusion live.
- **Raytraced reflections (VU0, experimental PoC)** — check *Properties > Mirror > Raytraced* on a Mirror and its reflection is **actually ray-traced on a VU0 microprogram**, per pixel, every frame: listed **static models reflect as real, TEXTURED triangle meshes** (decimated to a 36-triangle budget at build, re-transformed live — rotation included — with the kernel returning barycentrics and the EE sampling the model's texture in RAM), **animated models reflect LIVE** (a fixed medoid-picked vertex-index mesh reads the skinned buffers every frame, so the glass plays the clip), flat objects as axis-aligned slabs, everything else as sphere proxies, against the scene's sky gradient — into a texture the glass samples, re-uploaded over PATH3 each frame at a per-mirror **Reflection resolution** of 32–512 (cost scales with the square — 128 still holds a frame rate, 256/512 are photo modes). The kernel is branchless VU0 microcode (saturation-arithmetic step masks, rational nearest-hit comparisons, per-model bounding-sphere early-outs) fed row-by-row through VU0 data memory by the EE, which mirrors the camera across the plane (Householder), packs the returned texels and textures the triangle hits. Budget one per scene. See [docs/raytraced-reflections.md](docs/raytraced-reflections.md).
- **Live texture feeds (CCTV + mirror streams)** — any surface can show a **live feed** via *Properties > Texture feed*: a Camera entity with **Render to texture** renders its view (sky/terrain + an explicit object list) into a dedicated 128×128 VRAM target every frame — security monitors and billboards, the classic 2002 set piece — or a **raytraced Mirror's traced image streams onto any other object** as an emissive screen. Real second render through the env-map redirect bracket, live camera transform (a flow graph panning the camera pans the feed), one feed camera per scene. See [docs/texture-feeds.md](docs/texture-feeds.md).
- **Portal objects** — `Insert > Gameplay > Portal` inserts a linkable surface: point two portals at each other (*Properties > Portal*, one click makes the pair two-way) and each shows a **live view through to the other end** — a real second render from a virtual camera kept in lockstep with the player camera, drawn **in-place at full resolution** through the normal VU1 pipeline and carved into the scene with the z-buffer (the GS has no stencil), so the opening is pixel-for-pixel as crisp as the world around it — correct parallax, no render-to-texture, no visible seam. **Walking into the front face teleports you to the target with position, view angle and vertical velocity carried through the same mapping** — what you see through the surface is exactly where you arrive, so crossing is seamless: smooth teleporters between distant parts of the map. Physics objects can ride along (per-portal switch). Budgeted the era-honest way: up to four live views per frame (nearest first; the rest draw as tinted energy surfaces) and an explicit per-portal list of objects visible through, like the Mirror's — or the experimental **All objects in view** switch, which submits the whole scene into the through-view and lets the virtual camera's frustum culling + draw distances trim the cost. See [docs/portals.md](docs/portals.md).
- **Endless scroller objects** — `+ Add object > World > Scroller (endless)` inserts a conveyor belt for scene geometry: you author one chunk of a level (a tunnel ring, a strip of road, a clump of trees) as a named **segment** of scene objects, give it a length, and the game tiles copies of it along the belt axis **forever**, sliding them past the camera — the level generator in a train window. Multiple segments cycle in order for variety, and **per-cell variation** stops the belt from ever repeating: fold a segment member open and it can appear in only a fraction of chunks, be one of several **alternatives** exactly one of which fills each chunk, and take a random yaw / lateral offset / scale - all resolved from a hash of the chunk's own index along the infinite belt, so it costs no geometry, no state and nothing per frame. The build clones just enough copies to fill a configurable ahead/behind window and a generated director slides them each frame (no runtime spawning or procedural meshing on the PS2) - each clone on the per-object matrix path, which is worth 16 -> 50 FPS on the runner example; the member objects are hidden templates and the belt itself is an invisible, intangible marker aimed by its rotation. A **Procedural volume's baked chunk meshes are ordinary scene objects**, so a strip of world generated once tiles forever like any other member. Speed / start / window are editable in *Properties*, driveable live from the flow graph (**Start / Stop Scroller**, **Set Scroller Speed**), and there's a **"Make endless scroller from selection"** shortcut in the multi-object Properties. The editor viewport previews the animated belt live (semi-transparent ghosts sliding down the axis; hideable per belt from its Properties, or all at once from *View > Scroller preview*, when they cover the members you are editing). Full guide: [docs/endless-scroller.md](docs/endless-scroller.md).
- **Transform gizmos** (ImGuizmo) — click an object in the viewport to select it, then drag the gizmo to move / rotate / scale it. Switch tools with the buttons in the viewport corner or the `W` / `E` / `R` keys; `Delete` removes the selected object. Left-drag on empty space or right-drag orbits the camera, wheel zooms, middle-drag pans, and **right+middle together pans forward and back** along the view direction (drag down = forward) - which is also how you lift the pivot off the ground to look at the sky, since the camera tips both ways and passes through the terrain. *View > Orbit around selected object* (on by default) puts the pivot on whatever you select. Schemes (Tyra/Blender/Maya/Unity), per-axis inversion and a speed for each of orbit / pan / zoom / forward pan live in *View > Navigation controls*.
- **Window layouts** (`Layout` menu) — named docking arrangements saved per project and switched with one click. Six ship built-in: **Default** (Project / Properties / Output + Debug around the Viewport), **Director** (Viewport + the Cutscene Director dopesheet), **Material Designer** (the Material Editor filling the window), **Debugger** (the watched graph plus the Live Debugger's state/watch/timeline column) **Procedural** (the scatter graph along the bottom with the Viewport above it, so a slider drag and the world it changes are both on screen) and **Menu Designer** (the Menu Editor with the Font Manager a tab away, the Menu Preview column beside it). Edit any layout by simply rearranging windows; *New layout…* saves the current arrangement under a new name, and *Reset to built-in arrangement*, *Rename…* and *Delete* round out the menu. Even the built-ins can be deleted per project — a project just always keeps at least one.
- **Interface themes & a real UI font** — the editor no longer looks like a debug overlay: it loads the system's own UI font (Segoe UI on Windows, Inter/Noto Sans/DejaVu on Linux — nothing bundled, and ImGui's built-in bitmap font stays as the fallback) and draws itself in one of four themes picked in `View > Theme` or `Edit > Preferences > Appearance`, applied the moment you pick one. Three of them are deliberate PS2 nods — **Face buttons** (the default: neutral graphite with the DualShock's four colours doing the semantic work, cross blue as the accent, triangle green for *running*, circle red for *stopped*), **Boot screen** (the navy the console fades up from, with the logo blue) and **Memory card** (the browser's violet) — plus **ImGui dark** as an escape hatch. A theme is a palette of nine colours; the rounding, padding, hairline borders, trackless scrollbars, accent tab overlines, tree hierarchy lines and the fading toolbar highlights are shared by all four, so the editor reads as one product either way. Status chips ask the theme for a *meaning* (ok / warn / danger / accent) rather than for a colour, which is why they stay legible in the violet one. Machine-global (`editor.ini`), like the interface scale — opening someone else's project never repaints your editor. See [docs/editor-theme.md](docs/editor-theme.md).
- **Project file, window layouts & undo history** — the project is a `<name>.tyra` **manifest** (project-wide settings, HUD, menus, sequences, save data, plus editor-side state — selection, active tool, view mode — and the named window layouts above, so your arrangements are restored per project) alongside an `objects/` folder holding **one file per scene object** (`objects/<id>.json`); the manifest lists each scene's objects by id in order. This layout keeps git merges painless for teams: two people editing different objects touch different files (see **Multi-user collaboration** below). The undo history (up to 100 snapshots) lives in a sidecar `<name>.history` file, so undo/redo survives editor restarts; it is gitignored in generated projects. The `<name>.tyra` + `objects/` are the source of truth — if edited outside the editor, the stored history is discarded automatically. (Projects from older editor versions used a single monolithic `.tyra`; they load unchanged and migrate to the split layout on the next save, or in bulk via `--resave`.)
- **Multi-user collaboration** — each new project is scaffolded for team work: because scene objects are split one-per-file, editing/moving/recoloring *different* objects never conflicts in git. A generated `COLLABORATION.md` explains the workflow, and a `.gitattributes` marks the files that *can't* be auto-merged — terrain heightmaps and imported `res/` assets — as `lockable`, so a team can `git lfs lock` them before editing (it uses only Git LFS's lock registry — no LFS storage or special server — and is inert until `git lfs install`, so it never disturbs a solo/non-LFS workflow).
- **Live collaboration sessions** (`Session` menu) — real-time multi-user editing on top of the git story: one editor **hosts** its open project, others **join over the LAN** with the host's `IP:port` + a 6-digit code, and everyone edits at once — objects, scenes, terrain sculpting, menus, cutscenes, preferences all stream live with per-object last-write-wins (the host orders every edit, so all editors converge). The whole project transfers on the first join; re-joins fetch **only what changed** (a content-hash cache under `%LOCALAPPDATA%\tyra-editor\remote-cache`). You see everyone else's **selections as colored outlines** in the viewport (and dots in the object list), the Session window lists participants (with Kick for the host), and the toolbar shows a SESSION/JOINED chip. The **host is the only one who saves and commits** — a client's Save is disabled (`[joined]` in the title bar) and its synced copy is still a full, real project: local Docker builds, PCSX2 runs and Live Link all work. Full guide: [docs/collaboration.md](docs/collaboration.md).
- **Copy/paste** — duplicate scene objects with `Ctrl+C` / `Ctrl+V`. The copy is not dropped where it lay: it **follows the cursor** across the viewport (outlined, snapped onto whatever is under it) until a **left click** — or a second `Ctrl+V` — puts it down; `Esc` throws it away, and nothing enters the scene (or the undo history) until it lands. A multi-object paste moves as one rigid arrangement. See [docs/object-placement.md](docs/object-placement.md).
- **Surface snapping** — with *Surface snap* on (the viewport tool row, or *View > Placement*), an object that enters the scene **rests on what is under it** instead of sinking into it: the terrain under its footprint, or the top of the object below — insert a box over a table and it lands *on* the table; insert three in one spot and they stack. Rotation and real model bounds are accounted for (a box rolled 45° rests on its corner, a character authored with its feet at the origin stands on the ground, not half-buried); only solid, collision-enabled geometry counts as a surface, so lights, markers and decals never lift anything. Applies to the Add menu, imported models, generated trees and the paste above; **`End`** drops the current selection onto the first surface *below* it as a one-shot. A machine preference (`editor.ini`), not project data. See [docs/object-placement.md](docs/object-placement.md).
- **AI Assistant** — *Tools > AI Assistant*: a chat inside the editor that **answers questions about the editor** and **does things in the project**. Ask "what is a Procedural volume for?" and it reads the documentation page and tells you - every `docs/` page is baked into the exe, so its answers are these guides rather than a model's memory of them; ask "add a usable red lever at 4, 0, -6 that logs when the player uses it" and there is one in the scene with a flow graph on it. It knows your project (scenes, objects, assets, presets) and **what you have selected**, so "make this one usable" resolves, and it **searches the full text of the documentation** when a question does not match a page title; it can add / change / delete objects (one or many at a time), rewrite an object wholesale, write flow graphs (validated against the live node registry, same as above), **edit anything that is not a scene object** — menus, cutscenes, credits, save values, the HUD, fonts, the input map, presets, settings — through the same per-section JSON the project file stores, add and delete scenes, and *check its own work*: `refresh_generated` shows it the C++ its graphs compiled to (a node naming something that does not exist comes back as a comment), and with **build & run** ticked it builds in Docker, waits for the game to come up in PCSX2, **presses the buttons itself** (the Remote Pad channel) and reads back what the graphs did — the game's own log and the Live Debugger's fire counts. Place a thing, build it, drive the player into it, see what happened. Every tool call is **one undo step** and nothing reaches disk until you save; an **Allow project edits** switch turns the acting half off and leaves a read-only helper. Conversations are **kept**: a chat is saved after every reply and *History* lists this project's chats to go back to (stored next to `editor.ini`, never in the project). The footer shows what the next request carries and what the session has actually cost (tokens and dollars, from the backend's own numbers), and when a conversation outgrows its budget the model **compacts** it — a recap replaces the older messages, recent turns kept verbatim, ~64k of context back down to ~6k. Uses the same backend setting as the generator below. [docs/ai-chat.md](docs/ai-chat.md).
- **AI flow-graph generation** — *Flow Graph* window → **Generate with AI...**: describe the logic in plain language and the configured backend (Claude CLI, OpenAI Codex CLI, GitHub Copilot CLI or the OpenAI API — pick the backend, a model from the dropdown (or *Custom...* to type any model id) and a *Thinking* toggle in `Edit > Preferences > AI assistant`) builds the graph. An existing graph is sent along automatically, so "make the timer 5 seconds" or "also play a sound" **edits it in place** — the model returns the complete updated graph, unchanged nodes keep their ids and positions. The reply is validated against the live node registry (including your custom `.flownode` nodes) and applied as one undo step; a spinner + **Cancel** cover the wait. Also headless: `--ai-graph`. [docs/ai-flow-graph.md](docs/ai-flow-graph.md).
- **AI-agent CLI** — the editor exe doubles as a headless toolbox for AI assistants and scripts: `--dump` (project summary), `--list-nodes` (node catalog), `--dump-graph`/`--apply-graph` (validated graph I/O), `--refresh-gen` (regenerate game sources without Docker). [docs/ai-tools.md](docs/ai-tools.md).
- **AI support in projects** — the **New Project** dialog (and later `Project > Preferences > AI support`) can install assistant guidance into the game project: Claude Code skills + `CLAUDE.md`, the same guides as `AGENTS.md` + `.agents/skills/` for **Codex**, and/or `.github/copilot-instructions.md` — teaching an AI assistant the project structure, the ownership markers, flow graphs, custom scripting, the **menu stylesheets** and the CLI above. Refreshable with the same delete-the-marker-to-own rule as generated sources. [docs/ai-support.md](docs/ai-support.md).

## Shortcuts

| Shortcut | Action |
| --- | --- |
| `Ctrl+N` / `Ctrl+O` / `Ctrl+S` | New / open / save project |
| `F5` | Build & run in PCSX2 |
| `Ctrl+Z` / `Ctrl+Y` | Undo / redo |
| `Ctrl+C` / `Ctrl+V` | Copy / paste the selected object (paste follows the cursor; `Ctrl+V` again or a click places it, `Esc` cancels) |
| `W` / `E` / `R` | Move / rotate / scale tool (viewport) |
| `Delete` | Delete the selected object (viewport) |
| `End` | Drop the selection to the floor (viewport) |
| `Num 5` / `Num 1` / `Num 3` / `Num 7` | Perspective ⇄ ortho / front / right / top view (`Ctrl` = opposite side) |
- **3D terrain preview** — *Viewport* window with a checkerboard terrain grid (matching what the PS2 renders), scene objects with a selection outline, world axes and an orbit camera (mouse drag = rotate, wheel = zoom).
- **Textures (PNG)** — per-object textures (*Set...* in object properties; the object color modulates the texture, white = plain) and a tiled terrain texture (*Preferences > Rendering*). UVs are generated for all primitives, `vt` is read from .obj models. Tyra loads PNG natively: 32/24bpp or palletized 8/4bpp (fastest on the PS2); keep sizes power-of-two.
- **Asset Browser** (*Tools > Asset Browser*, or *Project > Assets > Browse assets...*) — a real file manager over the project's `res/` tree instead of a flat list: **folder tree**, a **thumbnail grid** (static `.obj`, animated `.glb`/`.fbx` and `.mtl` libraries are rendered into a cached 128² preview — a material on a sphere; images are their own thumbnail) or a detail list, **type filter chips carrying the count in the current scope** (`Textures (0)` tells you the folder has none without switching filters), name search, a recursive *Sub-folders* scope, and an inspector with each type's own controls (triangle/clip counts, missing-texture and WAV-format warnings, texture quality, LOD chain, *Add to scene*, *Edit in Material Editor*). What a plain file manager can't do: it knows **who references every asset** — one pass over the project records every stored path (object model/material/sound, terrain materials and painted layers, HUD/menu/splash/loading images, fonts, the audio lists, texture quality, LOD chains, animation edits, audio flow nodes) plus the references living inside `.mtl` files, so the inspector lists the users (with **Select** to jump to the object, switching scenes if needed) and a tile nothing references gets a ring in its corner — the honest answer to "can I delete this?". **Drag files onto a folder to move them and every reference follows in the same edit**; drag a **model onto the viewport** to place it in the scene where the cursor points. Moves respect the one rule the PS2 imposes — a `mtllib` / `map_Kd` reference is a bare sibling name, resolved next to the file that named it — so a move carries the whole dependency group along, **copies** a shared dependency the files left behind still need, and **refuses with the reason** rather than half-applying a move that would break a reference; a rename inside a folder instead rewrites the siblings that name the file (and renames the `.mtl` a model exclusively owns). Paint-layer and UV sidecars travel with their asset, the baked `.tmdl` is dropped for the next build to redo, and a WAV moved between `res/audio` and `res/sfx` switches roles between the Music and Sounds lists. Delete asks once for the whole selection, listing what is still in use. Files the build writes into `res/` (baked menu panels, text sprites, glyph atlases, `.tmdl`) are hidden behind a *Generated* toggle and read-only here. Full guide: [docs/asset-browser.md](docs/asset-browser.md).
- **Material Editor & texture painting** (*Tools > Material Editor*) — authors the `.mtl` materials the whole pipeline consumes (color × brightness + `map_Kd` texture, saved on every change, scene viewport updates live). A **Reflection** section makes a material shiny the way PS2 racers did it: pick a small **sphere map** PNG (a sky gradient with a bright horizon works great) — or **`<dynamic - live sky>`**, which re-renders the scene's sky into the map every frame, GT3-style, so reflections follow script retints — plus a strength, a **Rounded normals** toggle and a project-wide **Reflection probe: aim along the reflected ray** preference (the env camera renders from the point your view ray hits the reflective surface, along the reflected direction — smoothed; what the chrome under your crosshair actually mirrors, instead of the classic level-forward approximation) (flat faces sweep a gradient of the map instead of one uniform sample — the curved-lacquer look for walls and monoliths); the game draws the surface a second time with additive blending, sampling the map by camera-space normals **computed on VU1**, so the highlight slides over the paint as the camera moves at zero EE cost; the viewport and the Material Editor preview mirror the effect live. Stored as the standard `refl` statement in the `.mtl`. Full guide: [docs/reflective-materials.md](docs/reflective-materials.md). A **Glow (emissive)** section makes a material light *itself*: a strength and a glow color (seeded from the material color) become a per-channel **brightness floor** baked into the vertex colors, so the surface keeps its own color in a pitch-black scene — sun, ambient, baked AO and point lights can only make it brighter, never dimmer. A **White-hot core** blows it out toward white the way an overexposed emitter looks on camera (the only way *up* once a colored surface has hit the framebuffer maximum in its own hue), and **Lights up surroundings** turns the emitter into a real lamp: its light is baked into the terrain, walls and props around it — the ambient-occlusion machinery in reverse, sharing its analytic shapes and its once-per-object pruning, and **blocked by solids**, so a wall stops the glow. Because an emitter is an **area** source (a lava plate, a neon strip) that shadow lands with a real **penumbra** that widens with distance from the caster: eight deterministic rays across the emitter's silhouette, the unblocked fraction as visibility — free, because it is baked on the host. It lands **per pixel** on the ground and on static primitives, through the same lightmap images the ambient occlusion ships (`A` = occlusion, `RGB` = light, one texture read twice) — a light pool on the terrain would otherwise be quantised to the ~2-metre vertex grid, gradients and shadow edges alike. Stored as the standard `Ke` statement. Pair it with the bloom **Threshold** and **Spread** (below) for the halo. Full guide: [docs/emissive-materials.md](docs/emissive-materials.md). The preview shows a unit primitive **or any of your `.obj` models** (the open file acts as the model's material override, exactly like in the game; drag orbits, wheel zooms). **Duplicate** copies a material together with its referenced textures (repaint-safe), **Delete...** removes one from the project (confirmed, objects fall back gracefully). **Paint** draws straight onto the preview mesh through its UVs, on a **layer stack** (Background + layers with Normal/Multiply/Add/Overlay blend modes, opacity and visibility; the stack persists in an editor-only sidecar) — with a soft color brush, an eraser, or a **brush image**: project-global PNGs under `res/brushes/` (*Import brush from PNG...*) stamped GIMP-style (the PNG's alpha is the dab shape, its RGB the paint) at a configurable **Spacing** (low = a continuous line, 100%+ = separate stamps), with per-dab **rotation** (a fixed Angle for orienting bricks, or Random for organic scatter), per-dab **opacity variation** (Vary — hand-worn strokes instead of a uniform coat) and a **Live dab** ghost that previews the stamp under the cursor before you click. Every stroke saves the flattened PNG, which is exactly what the PS2 loads (no separate bake; brushes and layer sidecars never ship). The window keeps its own undo: **Ctrl+Z while it's focused** (or the Undo button) steps back through strokes, layer ops and material edits without touching scene undo. *Texture > New paintable texture...* creates a blank pow2 canvas next to the `.mtl` for texturing a model from scratch. The preview also offers **display modes** (wireframe overlay, a generated **UV checker**, and **PS2 CLUT** — the texture palette-quantized live through the exact median-cut quantizer the build ships, with a Floyd–Steinberg/ordered/none **dithering comparison**, the surviving palette as swatches and a **memory budget line** like `128x128 4-bit = 8.0 KB + 64 B palette`), a **UV layout panel** with two-way hover sync (hover a face in 3D → its texture region lights up; hover a UV triangle → it outlines on the mesh), a **Light** combo (bake the preview with the scene's ambience — the default, what actually ships — a **neutral studio** light, or any ambience preset, so a dark scene doesn't hide the material you're authoring), a **UV validator** (overlapping islands, out-of-range/flipped/degenerate triangles, texel-density outliers — findings click-to-highlight in both views) and a one-click **automatic UV unwrap** (smart-project: normal-clustered charts, uniform-density packing, rewrites the `.obj` in place — unwrap before texturing). A **Bake maps** block runs a progressive **raytraced UV-space baker** (BVH + cosine hemisphere sampling, deterministic, multithreaded): ambient occlusion, bent normals, thickness, curvature, position and object-space normal maps in one pass, optional **high-poly cage projection** for baking dense-mesh detail onto game meshes — with a live preview on the mesh while you drag the sliders, one-click **"Bake & add AO layer"** (lands as a multiply paint layer) and a six-map PNG export. On top of the bake sit **smart masks** — procedural layer generators (edge wear and cavity grime from curvature, dirt from occlusion, height streaks, world-space Perlin/Worley that flows across UV seams, bricks) with a remap window and noise breakup, regenerating live as the bake refines — and **material presets** that save a mask stack as a reusable recipe applied to any other asset's own bake. Full guides: [docs/material-painting.md](docs/material-painting.md), [docs/material-baking.md](docs/material-baking.md).
- **Optional terrain** — the ground plane is a per-scene choice, not a fixture. *File > New Project* and *+ Scene* ask **Create terrain** (on by default), and the **Terrain Editor** carries a **Terrain in this scene** checkbox that removes or creates it at any time (one undo step; the heightmap, the paint and the layer list are kept, so turning it back on restores the terrain you had). Removed means **removed**: no ground mesh or grid in the viewport, no terrain chunks and no ground textures in the game (they are not even listed, so they cost no VRAM), no terrain lightmap, no ground light pools — and **no floor**: the player, physics bodies, dropped props and particles rest on the geometry you place and fall through the void anywhere else, which is what an interior, a platformer or a space level wants. The scene's width/depth stays the **world bounds** every walker is clamped to, and a terrain-less scene starts its player at the spawn point's own height. Navigation AI still needs a terrain (the navmesh rasterizes the ground). Headless: `--new ... --no-terrain`. Full guide: [docs/terrain.md](docs/terrain.md).
- **Terraforming** — the *Sculpt (4)* terrain brush: paint the terrain relief with a smooth brush (LMB raises, Shift+LMB lowers, Flatten levels to a target height, RMB orbits). Lives in the **Terrain Editor** window (below) together with the Paint brush; quick radius/strength sliders float in the viewport while the tool is in hand, **`[` / `]`** resize the brush, and the ranges **scale with the map** (a 2000×2000 world sculpts as comfortably as a 64×64 garden). The heightmap is stored in `terrain-<scene>.heights`, compiled into the game, and everything follows the relief: FPP walking, object physics, shading.
- **Terrain painting** (*Tools > Terrain Editor*, or the *Paint (6)* tool) — the terrain no longer wears a single tiled texture: add **terrain layers** (each an existing `.mtl`, so they inherit its texture, tint and tiling, plus a per-layer **Size**) and **paint their blend straight onto the terrain in the viewport** with the shared terrain brush (Shift or the Erase toggle removes). The Terrain Editor hosts both terrain tools — Sculpt and Paint as switchable modes — plus the layer stack (add/rename/pick material/reorder/remove, active-layer radio). The PS2 draws the blend the era-correct way: **two-pass GS splatting** — painted chunks draw one extra alpha-blended pass per layer, weights interpolated from the vertices, so layer textures stay **tiled at full resolution** on any map size, and unpainted chunks cost exactly what they always did. The editor viewport draws the same two passes live. Each layer (and the base) also has a **Stochastic tiling** toggle — build-time texture bombing that bakes a larger non-repeating supertile to break the tell-tale tiled-grid repetition (zero runtime cost, best on organic textures) — and a scene-wide **Variation** control adds large soft light/dark ground patches via world-noise baked into the vertex shade (infinite period, tints base and layers coherently). A scene with no layers is exactly the old single-material terrain. Full guide: [docs/terrain-painting.md](docs/terrain-painting.md).
- **Orthographic & axis views** — the viewport camera also renders **parallel** (no perspective foreshortening — equal sizes read equal anywhere on screen), optionally **locked to a world axis**: Top / Bottom / Front / Back / Right / Left, the floor plan and elevations you want when lining a street of houses up or matching two platform heights. Switch with the **axis gizmo** in the viewport's top-right corner — the three world axes as coloured balls (X red, Y green, Z blue) that turn with the camera: click a ball to snap to the orthographic view from that end of the axis (the active one wears a white ring), click the hub to toggle perspective ⇄ parallel. Or use the `Proj:` button in the opposite corner, *View > Projection*, or the numpad (`Num 5` toggles perspective, `Num 1`/`3`/`7` pick front/right/top, `Ctrl` for the opposite side — the number *row* keeps the transform tools). Orbiting a locked view drops the lock and returns to the projection you came from — perspective unless you had picked free ortho yourself, so an axis view is a glance rather than a new home. Picking, the terrain brushes, rubber-band selection, the gizmo and paste placement all follow the projection; the choice is persisted per project. See [docs/orthographic-views.md](docs/orthographic-views.md).
- **PS2 output in the viewport** — the viewport can render the scene the way the console does instead of the way your monitor does: rasterized at the **GS framebuffer size** of *Preferences > Display mode* (512×448 interlaced, 512×224 with true field rendering, 448×448 in 480p…), then point-scaled into the 4:3 / 16:9 picture a television shows — so the resolution, the framing and the non-square GS pixels are all the console's. The engine's own projection aspect comes with it, which means the horizontal stretch a real PS2 outputs (1.167×) is finally visible at the desk. Switch in the viewport's gear or *View > Viewport output*; machine-global, and the game is identical either way. See [docs/ps2-viewport.md](docs/ps2-viewport.md).
- **View modes** — *Solid*, *Wire* (colored wireframe) and *Wire+Solid* (solid shading with a wireframe overlay); buttons in the viewport corner, the choice is persisted in the `<name>.tyra` project file. *View > Preview > Distance fog* toggles the editor's distance-fog preview off/on (handy for seeing distant geometry while authoring) — a viewport-only convenience that doesn't change the scene's fog or the generated game.
- **Scripts** — user C++ scripts live in `src/scripts/` (subfolders welcome — everything under it compiles) and that directory is **exclusively yours**: engine-generated sources live in `src/gen/`, so the *Scripts* list shows only your files and the editor never regenerates them. The primary, Unity-style flavor is the **object script**: a class derives from `ObjectScript` (see the generated `inc/scripts/script.hpp`), overrides `onStart`/`onUpdate`/`onUsed` and registers with `TYRA_OBJECT_SCRIPT(MyScript);` — it runs only when **attached to an object** (*Properties > Scripts*, attach the same class to any number of objects across scenes). Every attachment becomes its own instance at scene load with its own members and a `self` pointer to the object it hangs on — spin `self`, read its color, react to the player using it. Global scripts still exist for game-wide logic: derive from `Script` (`init`/`update`), register with `TYRA_SCRIPT(MyScript);` and they run every frame in every scene. The *Scripts* section in the *Project* panel lists the files, creates new ones from an attachable stub (**New script...**, also available straight from *Properties > Scripts*, which attaches the new class to the selected object) and opens the project in VS Code (**Open in VS Code**) with working IntelliSense — the generated `.vscode/c_cpp_properties.json` points at the bundled Tyra engine headers and the PS2SDK headers exported from the docker toolchain on first build. Each `ScriptContext` gives access to the engine (pad!), player/camera position, scene objects and the sky color, plus helpers like `padVibrate(ctx, big, small, seconds)` for controller rumble. New FPP projects include an example: walk up to the box and press X — the sky changes color and a message lands in the PCSX2 log. Full guide: [docs/object-scripts.md](docs/object-scripts.md).
- **Empty objects** — `+ Add object > Empty` inserts a pure transform (a small sphere marker in the editor, invisible and non-colliding in the game): an anchor to hang object scripts on, a waypoint for flow-graph logic; scripts read its position/rotation/scale/color.
- **Areas (invisible volumes)** — `+ Add object > Gameplay > Area` inserts a box that has **no geometry in the game at all**: a wireframe in the editor, nothing on the console, no collision, no triangles. It exists to replace numbers you would otherwise type blind. Point a **streaming layer's auto zone** at one and the zone becomes that box instead of a center + radius circle — which also means it **bounds height**, so one floor of a building can stream on its own. Set it as a **catch area** on a Mirror, a Portal or a feed Camera and every object inside the box joins that surface's re-draw list, without maintaining the list one name at a time (resolved at build, and the Properties panel shows exactly how many objects it caught — the PS2 cost stays visible instead of growing silently, and caught objects are kept out of static batching like listed ones are). Tick **Update every frame** on that catch area and the volume is re-tested live, so a crate that rolls in front of the mirror — or the player walking in — starts reflecting the moment it crosses the boundary: only objects that can actually move are re-tested (the static rest is still resolved at build), the test is a few dot products against a basis computed once per frame, and "can move" is exactly the set static batching already refuses, so nothing else changes. And the **In Area** flow trigger fires the frame a player enters the volume, with a live "inside right now" bool output for the logic gates (wire it through NOT into On Condition for an exit trigger). Areas are read live, so a flow node that moves an area drags its trigger volume and streaming zone along with it. Sound emitters and point lights deliberately keep their radius — those describe a falloff, not a boundary. Full guide: [docs/areas.md](docs/areas.md).
- **Flow graph** — visual logic (CryEngine-style): wire triggers (On Start, **On Update** (every frame), On Button, Near Object, In Area, Every N Seconds) to actions (Set Sky Color, Set Object Visible, Move/Rotate/Recolor Object, Play/Stop Sequence, Log) in the *Flow Graph* tab. The **Graph of** picker marks every object that already owns a graph with a `*`, and a checkbox inside the dropdown lists **only those** — a scene is mostly props with no logic, and those are the entries you come back to. The graph compiles into `src/gen/flow_graph.gen.cpp` on every build. Actions that used to come in show/hide pairs are now single nodes with a labeled exec pin per branch — **Set Object Visible** (show/hide/toggle), **Set HUD Visible**, **Set Text Visible**, **Set Layer Loaded** (load/unload) and **Animation** (play/stop). The **Raycast** node casts a ray from the player's eye along the view direction and outputs the hit position and the hit object — wire its object output into Set Object Visible / Set Object Color / Despawn Object for "what am I looking at" mechanics, its position output into Spawn Object / Set Position for aim-placed effects. **Get Position** doubles as a live position source (consumers read the target's current position) and, with its exec input wired, a **sampler**: the position latches the moment the exec fires and the "after" exec chains on — capture "where was it when X happened". **Control flow is a first-class part of the graph** (the **Flow** category): a node there decides which of its OWN exec outputs continues, so the graph branches instead of just listing what a trigger does. **Branch (If)** is the if/else on a bool value (asked at the moment it runs, unlike *On Condition* which is a rising-edge trigger), **Sequence** fires four outputs in a guaranteed order, **Do Once** / **Do N Times** / **Cooldown** tame a trigger that fires every frame, **Gate** is an open/close valve, **Flip Flop** alternates A/B, **Switch Number** dispatches a state machine kept in an int variable, **Random Branch** picks an output at random, and **For Loop** runs its body N times with the index on its number output. Two of them are timekeepers: **Timer** is a stopwatch whose number output is the elapsed seconds (an on-screen clock is Timer -> Number To Text -> Display Text) and **Tween Value** ramps a number From -> To over N seconds with an ease and fires *finished* when it lands - wire its number output into Set Bloom, Set Music Volume, a save value or a position and that parameter **animates**, with the game doing the interpolation instead of a graph re-entered 50 times a second. **Text formatting and live screen effects** close the set: **Number To Text (formatted)** (decimals + zero-padded width, so a score reads 00420), **Seconds To Clock** (a Timer straight into "1:23.4"), **Join Text** and **Text Equals**; and **Set Screen Effect** finally makes a custom `.screenfx` effect *live* - its `set` pin writes the effect's own named parameters, `on`/`off` switch it, and a wired number drives the first parameter, so a Tween can ramp a tint up. Plus **Value At Most** and **Restart Scene**. **Graphs talk to each other**: **Send Event** broadcasts a name (plus an optional number payload) to every graph in the game and every **On Event** of that name fires - so a pickup can tell the HUD, a switch can tell three doors and a boss can tell the music, without any of them naming the others. Delivery is one frame later and **uniform for every receiver**, whichever object owns it: the bus is double-buffered behind a script registered ahead of every graph, so the order graphs happen to run in can never change the outcome. Before this the only channel between two objects' logic was a global variable polled from *On Update*. **A graph can direct the camera**, and it does so through the very fields the Cutscene Director publishes - so there is no second camera system and a playing cutscene always wins. **Set Camera** takes its eye from a linked position and aims at an object (from *On Start* a fixed room camera, from *On Update* a tracking one); **Camera From Object** cuts to an object's position and its own aim, so a Camera entity placed and pointed in the viewport *is* the shot; **Release Camera** hands it back; **Camera Shake** knocks whatever camera is in force, easing out. **Set Screen Fade** and **Set Letterbox Bars** (cinema 2.39:1 / wide / pillarbox / frame) take a 0..1 amount, so a Tween wired into either is a real fade or slide-in - and the Tween's *finished* output is where you switch scenes at full black. **Set Player Visible** drops the third-person avatar so the camera can fly free, and **On Sequence Finished** fires when a cutscene stops for any reason (ran out, stopped, skipped), which is what lets you chain "play the cutscene, then carry on". **The player and an object's transform are readable**, which a graph could not do at all before: **Player Position** (either player), **Player Look Direction**, **Player Fall Speed**, and on objects **Get Object Scale** / **Get Object Rotation** / **Get Velocity** - all three riding the position plane as 3-vectors, so "turn this thing to face 90 degrees" is Get Object Rotation -> With Y -> Set Object Rotation and nothing else. **Distance To Object** turns "how far away is the player" into a *value* the comparators, Remap Range and a fade can use, where the Near Object trigger only ever answered yes/no at a fixed radius. The writers that were missing came with them: **Set Object Scale**, **Scale Object By**, **Look At** (yaw only, or tilting too), **Set Velocity** (units/second, replacing rather than adding like Apply Impulse), **Stop Motion**, **Set Object Usable** for a door that only works once you have the key, **Is Object Active**, and **Find Nearest** - the runtime counterpart of naming an object, latching the closest one whose name starts with a prefix. **Set Player Input** locks and unlocks the controls for a dialogue or a scripted moment; only input is taken, so a locked player still falls and is still framed, and a scene load always unlocks. **The value plane is a real calculator, and it reaches positions too**: the **Math** category now covers Min / Max / Modulo / Power alongside the four operators, the unary shapers (Absolute, Negate, Sign, Floor, Ceiling, Round, Square Root, Sine, Cosine in degrees, **Clamp**, **Lerp**, **Remap Range** - the one node between "a distance in world units" and "a 0..1 amount"), the comparators (At Least / At Most / Equals with a tolerance / In Range) and three clocks: **Scene Time**, **Frame Time** and **Oscillate**, a sine wave on the scene clock that costs one `sinf` where a pulsing light done by hand costs a graph running every frame. **Roll Random** is deliberately an action rather than a pure node - it latches its roll so two readers see the same number. The new **Vector** category does the same for coordinates: **Position** (a literal), **Offset / Scale / Rotate Around Y**, **With X / With Y / With Z** (the bridge from a computed number to a coordinate), **Snap To Terrain**, plus the readers **Get X/Y/Z**, **Distance To Point** and **Terrain Height At**, and **Roll Point In Area** for scattering inside a placed volume. Chained, they compose - a ring of eight crates on the ground is For Loop -> index x 45 -> Rotate Around Y -> Snap To Terrain -> Spawn Object, with no scripting. **Values a graph computes, not just values you type**: a fifth link kind carries a **number** from a source (**Number**, **Get Int**, **Get Save Value**) through **Add / Subtract / Multiply / Divide** into any node's first numeric param, overriding it the way a position link overrides X/Y/Z - and **Number At Least** / **Number To Text** bridge back to the bool and text planes, so a computed score can gate a trigger and appear on screen. For the common case the graph stays two nodes: **Set Int** has *set* and **add** pins (On Button -> add with Value 1 IS a counter) and **Set Bool** has *set* and *toggle*. **Rotation** comes in the same three shapes position does: **Rotate Object By** (a delta in degrees), **Set Object Rotation** (absolute) and **Spin Object** — the one to reach for when something has to turn *all the time*. Spin Object only sets an angular velocity in degrees per second; the game integrates it in its own object pass and renders the spinner through a per-object matrix instead of re-baking its vertices, so a permanently rotating coin/fan/lighthouse is `On Start -> start` and costs one matrix refresh per frame (start/stop pins, frame-rate independent). Doing the same thing by nudging a transform from On Update pays a full world-space vertex re-bake every frame per object - the node exists precisely so you don't. **Set Depth Of Field** overrides, disables or restores the authored depth-of-field effect (see *Screen effects*). **Vibrate Pad** rumbles the DualShock (heavy-motor strength 0..1 + the on/off buzz motor) with an optional auto-stop after N seconds — impacts, explosions, heartbeat loops. **Every node documents itself, and so does every knob on it**: hover a node (or its add-menu entry) and you get what that node is *for*, then one line per parameter and per exec pin; hover a parameter and you get that parameter alone — what the number means, what 0 or -1 does, which trap belongs to it. All 186 built-in node types carry it, the same text feeds the AI generator's catalog (so it fills parameters in better too), and a custom `.flownode` writes its own with `desc` + `tip0`..`tip3` / `tip_string`. Need an action the editor doesn't have? Define your own **custom node** in a `flow-nodes/*.flownode` text file — no editor rebuild. A quick node is a tiny header + an inline C++ snippet; a `call = fn` node runs a real function you write in `inc/scripts/flow_nodes.hpp` and can have **input and output pins of any kind** (object/position/bool/text) — e.g. a node that picks the object the player looks at and hands it to a built-in *Set Object Visible*. Copy the file (and its function) to reuse a node in other projects: [docs/custom-flow-nodes.md](docs/custom-flow-nodes.md).
- **NavMesh + NPC AI** — NPCs that find their own way: a navigation grid is **baked from the scene on the host at build time** (terrain slope + blocking objects, tunable in *Preferences > AI navigation*, previewed with *View > Nav mesh overlay*) and the PS2 only runs **A\* on the EE** over the finished bitmap — budgeted at one pathfind per frame, with string-pulled paths so NPCs walk straight lines instead of stair-stepping the grid. Four flow nodes make enemies without a line of code: **Patrol Waypoints** (walks the objects named `wp1`, `wp2`, … in order, pausing at each), **Chase Player** (repaths after the moving player, stops at attack range, optionally gives up), **Flee From Player** (runs until safe) and the **On Player Seen** trigger (vision cone + range + terrain line-of-sight; its bool output feeds the logic gates for "lost sight of the player"). One AI state per object — a Chase interrupts a Patrol; **Stop AI Movement** returns to idle. Agents snap to the terrain and turn to face their motion, so a walk clip on an animated model lines up for free. Scenes without AI nodes carry zero nav data or code. See [docs/navigation-ai.md](docs/navigation-ai.md) and [examples/nav-ai](examples/nav-ai).
- **Cutscene Director** (*Tools > Cutscene Director*) — a keyframe **timeline sequencer** for cinematic cutscenes on the PS2, with a dopesheet UI: one lane per animated object plus a camera lane, keyframes as draggable diamonds (click to select, drag to retime, right-click for easing/delete, double-click a lane to drop a key), a click-scrubbed time ruler with zoom (a *Zoom* slider or **Ctrl + mouse wheel** over the sheet), and a playhead that previews the whole scene live in the viewport. A *sequence* poses scene objects (position/rotation/scale/color/visibility) **and the game camera** over time with per-key easing (linear / smooth / step). Every camera key is a *shot* that films from a **Camera entity** (`+ Add object > Gameplay > Camera` — a film-camera marker with an FOV frustum wedge in the viewport): the shot uses the entity's live pose + FOV, so keyframing the entity itself in an object track gives dolly/crane moves, and Step easing between two cameras is a hard cut. (Place and aim the cameras in the scene, then the camera lane just says *which* camera films *when* — no separate "free" camera to keep in sync.) Shot FOV drives the **real PS2 projection** (restored when the cutscene ends), per-shot **camera shake** adds handheld energy, and each sequence can be **skippable (START)**, **fade in/out from black**, **hide the third-person player avatar** for the duration (so the camera flies free without the body in shot) and mask the frame with **widescreen bars** (Cinema 2.39:1, Wide 16:9, Pillarbox, Frame) that composite over the HUD with per-sequence slide-in/out times (0 = they appear/vanish instantly, like the fades). Fire it from the flow graph with the **Play Sequence** / **Stop Sequence** nodes (e.g. On Used → play a cutscene); the camera track takes over the game camera for the duration and hands it back when the sequence ends. Compiles into `src/gen/sequences.gen.cpp` (a runtime player) on every build. Authoring workflow: while paused, **selected objects keep their real transform** (the preview doesn't fight the gizmo — pose, then snapshot), optional **Auto-key** drops a keyframe at the playhead when a gizmo drag ends, *+ Add object track* opens an object picker with **Add selected**, and the viewport can **look through any Camera entity** (*View:* control in the viewport corner, or *Look through* in the camera's Properties) with one click back to the free camera — the camera you look through hides its own model so it doesn't fill the frame. Turning **Preview in viewport** off still animates the scene (a Camera entity dollies along its track) but leaves the viewport on the free camera, so you can watch the move from outside. **Space** toggles play/stop while the window is focused.
- **Phone camera takes** (*Cutscene Director > Import take...*) — record a real 6DoF camera move on a phone (ARKit world tracking, e.g. the [CamTrackAR](https://fxhome.com/product/camtrackar) iPhone app) and import it **into a chosen Camera entity** — its transform track + FOV are baked from the recording, so the camera dollies along the path (two cameras in one scene each get their own move): "walk around a room looking around" becomes a PS2 cutscene camera move. Reads CamTrackAR `.hfcs` exports and an app-agnostic CSV (spec in [docs/camera-takes.md](docs/camera-takes.md)); the import modal maps the take into the scene (scale "1 m = N units", extra yaw, origin placement at the preview camera, start-at-playhead) and **decimates** the 60 Hz recording with an error-bounded tolerance slider (a 6.6 s take → ~12 keys) so the compiled PS2 keyframe table stays small. After importing, the whole path can be re-positioned and re-oriented (start point + start yaw) without re-importing. Imported shots are ordinary editable keys — scrub, retime or delete them like hand-authored ones.
- **Phone camera — the phone as a live viewfinder** (*Tools > Phone Camera*) — the editor hosts a link on your LAN, a companion iOS app ([doctorspider42/tyrax-cam](https://github.com/doctorspider42/tyrax-cam) — ARKit, sideloaded, no App Store; its own repo because it is a different toolchain entirely) connects with a 6-digit code, and from then on **the phone screen shows a live stream of the editor viewport while the phone's 6DoF motion drives that camera**: walk around the room and the game camera walks with you. Then, in the *Cutscene Director*, hit **Record** and the move is written into camera keyframes as you move — at a **configurable keyframe density** (a custom keys-per-second rate, one key per game frame in sync with the project's 60 Hz NTSC / 50 Hz PAL frame rate, or the error-bounded decimator that keeps the compiled table tiny) — with the dopesheet filling in live and a REC badge, elapsed time and key count on the phone. The phone is **landscape-only** and its **tilt about the lens axis is part of the shot** - a real Dutch angle, recorded as a roll channel (free shots) or folded into a Camera entity's rotation track, with a *Tilt* slider to damp it from "as held" to "horizon pinned level". *Record / Stop / Recentre* are on the phone too, so you never reach for the keyboard while holding the camera; **Recentre** re-anchors the whole thing on the editor's own viewpoint and aims it where the viewport is looking. The phone sees the editor's actual rendered frame (colour grading included), not a second render, and the live view and the baked keys run through identical math — so what you frame is what the console plays. The recording ends as ordinary editable `SeqCameraKey`s: nothing in the generated game, the codegen or the project format knows this exists. **No phone at hand?** The link's port also serves a self-contained **browser test client** (`http://<editor-ip>:7798`) that shows the same stream and fakes a pose with mouse and WASD. Full guide: [docs/phone-camera.md](docs/phone-camera.md).
- **World scale** (*Preferences > World*) — one number, **units per meter**, that says how big a real-world metre is in your project, so everything imported from reality lands at the size your own content already uses. A model import asks what the file is authored in (meters / centimeters / inches, or "this is 1.8 m tall") and records that **per asset**; objects made from it are inserted at the scale that implies — a Mixamo character stops arriving knee-high in a world built five times larger than metric. A phone camera take seeds its "units per metre" mapping (and its decimation tolerance) from the same number instead of assuming 1, and the modal shows the recording both ways ("4.80 m walked → 24.0 units"). The setting is authoring metadata only: it never reaches the game and never moves anything already placed. It also restates the FPP player in metric (eye height, walk speed, gravity), which is usually how you find out what scale your world is at — and **walk speed is now edited in units per second** (with the m/s equivalent next to it) instead of the engine's per-1/50 s step, where every sane value was a fraction in the first few percent of the field. Its default came down with it, from 20 units/s (72 km/h for a person-sized player, which is what quietly pushed projects into being built several times larger than metric) to a brisk 5 units/s — for **new projects only**; anything already saved keeps the speed it was tuned at. Two readouts tell you how big anything actually is, in units **and** metres: a **Size** row under Scale in the Properties panel (primitives are unit shapes, so a stock box is 1×1×1 units — one metre in a metric project, 20 cm in a 5-units-per-metre one), and a **measuring tape** in the viewport (*Measure (7)*) — click two points and read the distance plus its per-axis split, with the end following the cursor until the second click. See [docs/world-scale.md](docs/world-scale.md).
- **Physics** — rigid-body objects (*Physics* checkbox + per-object Mass/Bounciness/Friction/Tumble/Sleep-after): full 3D velocity, restitution bounces off terrain slopes (real heightfield normals), friction slides, tumbling, body-vs-body momentum exchange, resting on / bouncing off static solids, and player shoves. A thrown body **wakes the sleeping bodies it hits** (the impulse pass trades momentum, so crates knock crates around); tumbling boxes and models **contact the ground through their rotated bound** (they ride on their corners instead of sinking in like spheres) and **settle flat onto their nearest face** as they come to rest. Near-rest bodies sleep after a per-object **Sleep after** delay (default 3 s), so a settled scene costs nothing; the solver's vector math runs on VU0 (`Tyra::Vec4` macro-mode ops) and **moving bodies render through a per-object model matrix on VU1** — geometry bakes once in local space and flies/tumbles with zero per-frame EE rebuild cost (a 28-body scene went 14 → 156 FPS in the vsync-off bench). Scripts get `velocityX/Y/Z` + `spin`, the flow graph gets an *Apply Impulse* node. Plus FPP player physics: gravity, jumping on X, collision with scene objects (a rotated primitive blocks along its real, rotated faces — box collision honors the object's yaw; mesh-collision models block in any orientation — wall steepness is judged in world space, so a physics model resting on its side still has solid walls — and fast steps can't tunnel through into the mesh), walking on top of them.
- **Player entity** (`+ Add object > Gameplay > Player`) — a controllable player that becomes the game camera, in one of three **modes**: **Walk (FPP)** (first-person, gravity + jump + collision), **Noclip (fly)** (free 6DoF, X up / Square down) and **Third person** — an orbit camera that rides a boom behind a **visible avatar**. The avatar is simply the Player's own **animated `.glb` model**: it renders through the exact same skeletal pipeline as NPC animated models, so no new asset workflow. Its clips map to locomotion states — pick an **idle**, **walk** and (optionally) **run**/**jump** clip and the runtime auto-selects and cross-fades them from the player's *actual* planar speed, scaling playback so the feet don't slide. Drop in a model, name three clips, and you have a fully animated character walking/running/idling — **zero scripting**. **Directional locomotion** stacks on top: turn on **Face camera (strafe)** and the avatar keeps facing the camera while moving, with optional **back** and **strafe left/right** clips auto-selected from the movement direction relative to the facing (any unmapped direction falls back to walk). The escape hatch keeps it flexible: a script or flow-graph **Play Animation** on the Player fires any one-shot (wave, attack) that plays to the end before locomotion resumes, and attached scripts see the avatar as `self`. The third-person camera rides a **spring arm**: the boom is raycast every frame and the camera stops at the first wall/prop/terrain in the way, with side **whisker casts** that see walls coming and ease the boom in ahead of the hit (a hard clamp still guarantees it never clips through; it eases back out when clear), so approaching cover reads as a smooth dolly-in, not a snap. Per-mode tunables (walk/look speed, jump, eye/body height) plus the third-person camera rig live in *Properties*: **distance** (back), **height** (up) and **shoulder** (sideways) are the rig offset in the camera's own frame — set *shoulder* to ~0.6 for a classic **over-the-shoulder** shot (negative = left shoulder; the avatar slides off-center as eye and aim point shift together), plus a **turn rate** for how fast the avatar turns to face its movement. A **camera style** picker widens third person beyond the chase cam: **Orbit (behind)** is the classic free-look rig, while **Top-down**, **Isometric** and **Fixed angle** pin the camera to a set **angle** (elevation above the horizon) and **direction** (world heading = which way is "up" on screen) for camera-locked games — Zelda-style top-down, Diablo-style isometric. Top-down and Isometric are just presets of Fixed angle (picking them seeds the angles, which stay fully editable), the left stick keeps moving the avatar relative to the camera heading, the spring arm still keeps the boom out of geometry, and an optional **Right stick rotates** switch lets the player orbit the pinned view (the elevation stays locked). The Player also carries the camera **Flashlight** (additive spot cone, optional toggle button, flippable from the flow graph). The first Player in a scene drives the camera.
- **Two-player games** (*Preferences > Multiplayer*) — local co-op on one console: **shared screen** (one camera frames both avatars, boom stretching with their separation) or **split screen** (P1 top / P2 bottom, each player's own camera — no projection tricks, a per-half raster bracket in the engine fork). Player 2 is simply the scene's **second Player object** (own spawn, speeds, avatar); they can **join and leave mid-game** — Start on pad 2 (hot-plug friendly) or a ready-made **Player count (1P/2P)** menu option block, both kept in sync. Full guide: [docs/multiplayer.md](docs/multiplayer.md).
- **Configurable buttons & keys** (*Tools > Input Map*) — every gameplay button in a generated game goes through a named **action** (`jump`, `sprint`, `use`, menu navigation, or your own custom ones) instead of a hardcoded pad button. Bind each action to a pad button **and/or** a keyboard key **and/or** a mouse button, keep several named **presets** per project (switch them from a menu row or the *Set Input Preset* node), and let the **player rebind them in-game**: a *Menu Editor* **Rebind key** row arms capture mode ("PRESS..."), the next button or key pressed becomes the binding, and the override persists in a save value on the memory card (0 = back to the project's preset). One click scaffolds the whole controls page (*+ Option block > Key bindings*, also included in *+ Options menu*). In the flow graph, **On Action** fires for "whatever jump is bound to right now" and **On Key** for a fixed debug key. Ships with a configurable **sprint** (pad R2 / Left Shift, *Sprint speed* multiplier — a third-person avatar crosses its run threshold and plays the run clip for free). Existing projects keep their exact old bindings. Full guide: [docs/input-bindings.md](docs/input-bindings.md).
- **Text icons (button glyphs)** (*Tools > UI Editor > Button icons*) — write `{{cross}}` in any text and the game draws the ✕ button glyph there: HUD texts, menu titles and labels, option labels, loading screens and *Display Text* nodes all understand it. `{{action:jump}}` draws whatever that action is **currently bound to**, so a prompt stays correct after the player rebinds. Every project is seeded with the full pad set (drawn by the editor in the DualShock colors — blue ✕, red ○, pink □, green △, plus plates for L1-R3/Start/Select and arrows for the d-pad); override one by replacing its PNG, or add your own `{{coin}}`. Baked text gets the icon composited into its sprite (free at runtime); runtime text blits it from one shared sheet that only reaches VRAM if something actually draws an icon. Full guide: [docs/text-icons.md](docs/text-icons.md).
- **Keyboard & mouse controls** — generated games are playable with a USB keyboard and mouse: WASD walks, the mouse looks around (FPS-style), `E` uses, `Space` jumps, `Esc` opens the pause menu, arrows + `Enter` drive menus. Off in new projects — tick *Project > Preferences > Build > Keyboard & mouse controls* for a keyboard/mouse game and a pad game never loads drivers it doesn't poll; then the game loads the PS2SDK `usbd`/`ps2kbd`/`ps2mouse` drivers and maps keys onto a **virtual pad**, so menus, flow-graph *On Button* triggers and scripts react without any changes — pad and keyboard work at the same time. In PCSX2 the editor configures the emulated USB ports automatically (USB1 = HID keyboard, USB2 = HID mouse); on a real console boot from a disc/USB/exported ISO and plug USB devices into the front ports, or use the F6 "Run on PS2" network deploy — the [TyraX ps2link](tools/ps2link/README.md) it boots bakes the USB stack into itself, and *Also over ps2link* is on by default so the game reuses it. Note the console only speaks the USB HID **boot protocol** — plenty of wireless/gaming keyboards and mice are invisible to it (and to other PS2 homebrew); the hardware path is verified only as far as the drivers reporting ready. All bindings (USB HID key codes → pad buttons, mouse buttons, sensitivity) live in the generated `inc/controls.hpp` — user-ownable per project. See [docs/keyboard-mouse.md](docs/keyboard-mouse.md).
- **Custom .obj models** — `+ Model` imports a mesh into `res/models/`; it renders in the viewport and is compiled into the game. Models behave like any scene object (gizmos, physics, scripts, lighting). You keep authoring `.obj`, but the game never parses text: the build compiles each model into a binary **`.tmdl`** with the triangulation, flat normals, material assignment, atlas UV rects and texture paths already resolved, so loading a 9 216-vertex model on the PS2 dropped from **306 ms to 59 ms** — the difference between a visible hitch and none inside a [streaming layer](docs/streaming-layers.md)'s one-asset-per-frame job. The same format carries **distance mesh LOD** for static geometry (12 copies of that model: a hard 25 FPS → a steady 50), either build-decimated or from **your own LOD meshes** assigned per model. Full guide: [docs/model-pipeline.md](docs/model-pipeline.md).
- **Tree Generator** (*Tools > Tree Generator*) — procedural low-poly trees, so you stop hunting for tree models: dial one in against a **live turntable preview** (drag orbits, wheel zooms, *Wireframe* shows the tessellation) and **Add to scene** bakes `.obj` + `.mtl` + a tileable bark PNG + an alpha-cutout leaf card into `res/models/trees/` and drops an ordinary **Model** object in. Nothing new reaches the PS2 — a generated tree is just a static mesh with two materials, so leaves ride the alpha test the static pipeline already does. Presets (**Oak / Birch / Spruce / Poplar / Dead tree / Bush**) plus knobs for trunk (height, thickness, flare, taper, gnarliness), branching (1–4 levels, children per level, tilt, ratios), leaves (count, size, foliage style: broadleaf / needles / single blade), bark style and colors. Two **crown architectures**: *Spread* grows the branching recursion a broadleaf needs, *Conical* gives the trunk an unbroken leader with **whorls** of boughs that shorten toward the apex — the conifer habit, which the spread rules cannot approximate (their falloff is a per-generation ratio, not a profile along the trunk). **Height is the tree's size**, not just its trunk length: thickness and leaf card are shares of it, so the slider scales the tree instead of thinning it. Everything is **deterministic in the seed**, and each branch draws from its own stream, so nudging a slider adjusts the tree instead of reshuffling it — "five oak variants" is five seeds, not a mesh library (**Roll** re-seeds; a preset keeps your seed). Explicit **poly-budget** levers interpolate detail from trunk to twig, with a live triangle count (the presets land at 437–1440 tris, the conifer the heaviest); the practical limit is instance count, since models don't join static batching. Full guide: [docs/tree-generator.md](docs/tree-generator.md).
- **Procedural generation** (*Tools > Procedural*, *+ Add object > Procedural volume*) — a **node graph that fills a region with instances**: forests with clearings, rock fields, orchards, fence posts along a curve, a colonnade around a plaza. A **Procedural volume** carries the graph and IS the region (its box is the area; the ordinary gizmo moves and resizes it). Nodes pass typed data — point clouds, 2D masks, curves — through sources (surface / grid / volume / along-a-curve, or a **single placed point**), **noise and terrain masks** (Perlin/ridged/Worley, height / slope / curvature / **one painted terrain material** — pick *grass* from a dropdown and the trees land on the grass and nowhere else, reading what the ground actually shows so rock painted over that grass reads as rock), **filters** (attribute range with a soft edge so the forest thins instead of ending on a line, mask thinning, minimum distance, keep-away-from an object or a curve, merge, limit), **exact repetition** (*Array* steps every point along a line — a stack, a row, a spiral with per-copy yaw and taper; *Radial Array* rings them around their own position — twelve columns around a circle, evenly over a full turn or an arc), a **weighted asset pool** and **transform variation** (yaw, scale range, tilt, align-to-normal). An **Object Settings** node states properties once for **everything the volume bakes** — mesh LOD distance (which is also what makes the build bake the decimated tiers for those meshes), baked lighting, reflections — because a generated chunk is rebuilt by every bake and cannot be hand-edited into shape. The viewport previews the result live, with a **triangle budget** readout because that is the real PS2 constraint. **Every build bakes** the result into ordinary static chunk meshes — instances of one asset inside one world chunk merge into one mesh, so the console draws a handful of models and never evaluates anything (on real hardware each submit costs ~1 ms flat, so per-instance drawing is not an option). The evaluator is **deterministic** (`hash(seed, node, point)` — adding an unrelated node cannot reshuffle the forest), **prefix-stable** (raising density adds points between the existing ones instead of relayouting) and **cached per node** (a slider at the end of a 20-node graph re-runs one node). Hand edits survive: move, rotate, rescale or delete a single instance and the edit sticks to that point's stable identity through every later re-evaluation. Full guide: [docs/procedural-generation.md](docs/procedural-generation.md).
- **Runtime procedural generation** (*Tools > Procedural*, the mode combo) — the same graph, **compiled into the game and evaluated on the EE** instead of baked: a world that is different every boot and takes no disc space at all. Costs load time, RAM and a much smaller node vocabulary, and the window says which nodes this graph cannot run *before* you build rather than after. Generation reports into the loading screen's progress bar; a **Generate Volume** flow node re-runs a volume at any time with a fresh seed, which is where the variety a player can actually feel comes from (a button press has entropy; a boot clock barely does). Instances merge into per-chunk vertex bags the game builds itself, so the frame draws a handful of bags — and merged geometry with collision contributes world boxes the walker tests, so generated architecture is solid. A **Blocks Fill** node adds the block-world source: it fills the volume with columns of cubes from layered noise and emits only the blocks with a **visible face**, each carrying a 6-bit mask of *which* faces to draw (a flat plain costs two triangles per block instead of twelve), plus `depth` and `height` attributes so grass/dirt/stone is the ordinary filter+pick vocabulary and not a special node — and its solid field is published as the world's **collision**, one 32-bit word per column, so the player walks on the cubes. Full guide: [docs/procedural-runtime.md](docs/procedural-runtime.md).
- **Prefabs** (*Tools > Prefabs*) — build a hut out of primitives, select it, **Create from selection**; from then on it is one thing with a name that you stamp into the world by hand, scatter with a procedural graph (**Pick Prefab**) or spawn while the game runs (**Spawn Prefab**). Members are ordinary scene objects with their flow graphs, stored in the prefab's own local frame, so everything the editor and the runtime already do with an object keeps working. The part that makes it affordable on this machine is the **split**: plain static members are merged into ONE geometry bag (a PS2 submit costs ~1 ms flat, so 20 wall slabs as 20 objects is a third of a frame — as one bag it is nothing), while members that need an identity — a graph, a script, physics, a light — are spawned as real objects out of the clone pool. The Prefabs window states that split per prefab (*"20 merged into 1 draw call, 1 spawned object"*) and marks which member is which, because the second number is the one that runs out. Merged geometry still **collides** (conservative world boxes the walker tests), and a prefab scattered by a procedural volume merges into the *volume's* chunks — which is why 27 rooms cost four draw calls. Full guide: [docs/prefabs.md](docs/prefabs.md).
- **Drone Generator** (*Tools > Drone Generator*) — an ambient/drone music generator, so a level can have a background bed without a DAW: dial a patch in against **live playback** (the sound card plays the patch as you turn the knobs) and **Render** writes `res/audio/<name>.wav` + a re-editable `<name>.drone` patch and adds the track to the Music list — play it with *On Start > Play Music* (Loop on). Nothing new reaches the PS2: the output is the plain 16-bit 22050 Hz stereo WAV `AudioSong` already streams. The synth is a real one, with a **VST-style rotary** for every parameter: **four oscillator layers** (sine/triangle/saw/square/pulse/FM/organ, PolyBLEP band-limited, up to 5-voice unison with detune, stereo spread and slow per-voice **drift** so a held chord never sounds frozen; each layer picks which chord degrees it plays, so one is a sub and another a pad), a **chord progression** of up to 8 steps that **glides** between chords, a filtered **air bed**, sparse **bells** (FM / plucked string / glass, on the beat or free, drawn from the chord or the scale), a resonant SVF **filter**, **three LFOs + a five-point arc envelope over the whole piece routed through a 6-row modulation matrix** (cutoff, resonance, pitch, layer levels, bell density, delay/reverb mix, shimmer, drive, width) — which is what turns a static patch into a piece — and an FX rack: drive, ensemble chorus, tape wow/flutter/hiss, ping-pong delay on musical divisions, an **8-line FDN reverb** with up to a 40-second tail plus **shimmer** (pitch-shifted feedback — the sound everyone means by "ambient reverb"), tilt EQ, stereo width with mono bass, limiter and dither. Background music loops, so **Seamless loop** renders past the end and *adds* that tail over the beginning — what a looping player literally hears — instead of crossfading: measured on *Deep Space Hum*, RMS across the wrap goes 0.1545 → 0.1530 (inaudible) where the un-looped render jumps 0.1688 → 0.0351. The fold is **windowed to zero at its end** (unity, then a raised cosine), because adding a tail and simply stopping leaves a step one *Loop tail* into the file — a tick measured at 0.37 against a 0.11 p99 neighbour jump, now 13× smaller and below the local noise; *Match decay* sizes the tail to the reverb so the wrap keeps its room. A **timeline** turns a patch into a piece: hit **Rec** and turning any knob drops a keyframe at the playhead — a lane appears for that parameter and an amber dot marks the knob as automated (Read/Write behaves like a DAW: with Write off an automated knob shows what the timeline is playing and moving it does not stick). All **137 saveable parameters** are automatable, because the lane list is derived from the same field walk that writes the patch file; a knob dragged for seconds merges into a couple of keyframes instead of a smear; lanes are edited by dragging points (double-click adds, right-click deletes) and automation sets the base value that the LFOs and arc still modulate on top of. The transport has two modes — **Generate** (free-running, for dialling a sound in) and **Record** (**stops at the end of the piece**, and *Rec* writes keyframes while it runs) — and both play from the playhead, because "let me hear how it ends" is a transport need, not a mode. Seeking **settles** the synth rather than just moving the clock: notes snap to the chord and to the level an attack running since that chord began would have reached, the periodic LFOs jump to their analytic phase, and a 1–3 s pre-roll (scaled by the reverb tail) fills the delay and reverb lines — otherwise jumping to 0:50 drops you into the opening fade-in, which is what makes a fragment sound wrong. The strip above the tabs is a foobar-style position bar — ticks, elapsed fill, a triangle per keyframe, `0:27.0 / 1:00` — and clicking it **seeks live playback**, so the timeline drives playback instead of just reporting it. Ten presets (*Deep Space Hum*, *Cathedral Pad*, *Glacial Shimmer*, *Rust Wind*, *Dark Cave*, *Underwater*, *Ritual Bells*, *Machine Room*, *Neon Dusk*), a waveform/scope + spectrum + peak meters display, and everything **deterministic in the seed** — a re-render is byte-identical, so a track is a file you can regenerate rather than a take you must keep. A patch is a **project asset**, not a scratch file: the bottom bar is a document bar (New / Open... / Save, the open path, a `*` for unsaved edits), the Asset Browser gives `.drone` its own kind — *audio project*, with an inspector that reads the patch and says how long it is, how many layers and automation lanes it has and whether it has been rendered — and a track in *Project > Music* that has a patch grows an **Edit** button. **Render WAV asks before replacing an existing track** (it writes two files from a typed name, and the patch is the only copy of the work). Full guide: [docs/drone-generator.md](docs/drone-generator.md).
- **Animated models (.glb, .fbx)** — import a skinned/rigged model (*Project > Assets > Import model...*, then *+ Add object > Model > your file `(animated)`*): **glTF Binary** from Blender, or **FBX** straight from Blender/Maya/3ds Max (read by the vendored [ufbx](https://github.com/ufbx/ufbx); axes/units auto-normalized, so a centimeter Maya rig imports at the right size; FBX animation curves are resampled and keyframe-reduced into the same runtime data, take names like `Armature|Walk` shorten to `Walk`, and textures referenced as separate files are copied into the project on import). A real skeletal runtime plays named clips on the PS2 — EE pose evaluation, VU0 macro-mode skinning, rendered through the same static pipeline as everything else — with crossfade blending between clips and per-object *start clip / autoplay / loop / speed / color / box collision*, plus an optional **`.mtl` material override** (on top of the file's built-in materials, resolved by part name and baked into the model — the same override a static `.obj` takes; the Material picker's **+ New material from this model** extracts the model's own materials into an editable `.mtl` you then edit/paint in the **Material Editor** previewed on the model itself). Trigger clips from the flow graph (the **Animation** node's play/stop pins, **On Animation Finished**) or from scripts (`playAnimation` / `stopAnimation` / `animationFinished`). Clip length is nearly free (~150 KB for a 1500-vertex character with three clips); three stacking LOD levers keep crowds under the frame budget — per-object **draw distance**, project-wide **animation LOD** (distant instances re-pose every 2nd/4th frame) and **mesh LOD** (build-baked decimated variants, static models included). Full guide: [docs/animated-models.md](docs/animated-models.md).
- **Animation editor** — *Tools > Animation Editor*: **non-destructive** per-clip editing with a live preview. Retime a clip (**Time scale**), **trim** it to a range of the source animation (rebased to 0, with interpolated boundary poses), **rename** it to the name scripts and flow nodes use (existing references are retargeted), and set its default **Loop**. The `.glb`/`.fbx` is never rewritten — the edits are folded into the `.tskl` at build time, so the console pays nothing, and the scene viewport applies the same numbers, so what you scrub is what ships. Alongside it, *Project > Preferences > Rendering >* **Animation fps** fixes the classic whole-export mismatch in one place: glTF/FBX store keyframe times in seconds and no frame rate, so a clip animated for 30 fps but exported from a 24 fps Blender scene plays 25% too slow — state the exported fps and the intended fps and every clip is scaled to match. A **Light** combo picks what the preview bakes with — the scene's ambience (the default: what actually ships), a **neutral studio** light, or any of the project's ambience presets — so a deliberately dark scene no longer means a preview you can't read.
- **Texture atlasing** (*Preferences > Build > Texture atlasing*, off by default) — small clamp-safe material textures pack into shared **256×256 pages** at build: one GS VRAM allocation (+~8 KB overhead) per page instead of per texture, fewer texture switches. Conservative eligibility (model UVs checked against the real mesh; tiled terrain, emitters, decals, sphere maps and quality-pinned textures keep their own files); model UVs remap through a `# tyra-uvrect` hint in the baked `.mtl`, primitives remap in the generated builders — sources in `res/` are never touched. Palettized projects share one 256-color CLUT per page, the era-authentic trade. The boot log prints what was packed. Full guide: [docs/texture-atlasing.md](docs/texture-atlasing.md).
- **Static batching** (*Preferences > Rendering > Static object batching*, on by default) — the generated game merges non-moving primitive objects that share a material into combined draw bags at scene load. On real hardware every separate object costs ~1 ms of fixed per-submit EE overhead regardless of size (PCSX2's fast EE hides it), so a map decorated with dozens of small boxes/pillars pays for its object *count* — batched, a cluster pays once. Objects with physics, scripts, flow-graph references, mirror/portal view-list references, save-state or a streaming layer stay individual, and a batched object edited at runtime (Live Link, Raycast-driven actions, scripts) drops back to its own bag automatically — batching is a pure optimization, never a behavior change. The boot log prints `Static batching: N objects in M batches`.
- **Directional lighting** — light direction + ambient/diffuse in preferences, baked into vertex colors; identical shading in the viewport and on the PS2.
- **Point lights** (`+ Add object > Point Light`) — colored pools of light with radius/brightness. By default they bake into nearby vertex colors at build (static, zero runtime cost). Tick **Dynamic (live)** and the light instead registers with the engine every frame: it can **flicker** (torch-like wobble slider), move with its object (Move Object moves the pool of light), hide with Show/Hide Object, and be switched or dimmed at runtime by the **Set Light** flow node (On + Intensity). Dynamic lights light **objects** through the same VU1 per-vertex path as the flashlight — the engine picks the strongest light per mesh, so up to 8 dynamic lights per scene cost virtually nothing over the flashlight alone. On the **terrain** each dynamic light paints a smooth additive ground pool instead (terrain draws in chunks, and a per-chunk pick would cut a pool into rectangles at chunk borders). The camera flashlight gets the same treatment — its pool follows where you aim, so you can light the ground at your own feet, which per-vertex lighting alone cannot do (the beam's footprint there is smaller than a terrain cell). That pool's sprite is swappable (*Player > Flashlight > Pool texture*), which makes it the beam's **shape** knob — drop in a gobo, a cross or a cracked-lens blob (additive, so the shape goes in the RGB channels). Dynamic lights (and the flashlight) also reach **animated .glb models**: their contribution is sampled once per model per frame into the ambient term, so a character walking into a torch's pool of light brightens with it.
- **Light beams** (*Point Light > Beam*) — draw the light source itself: an additive camera-facing **glow corona**, optionally with a **cone shaft** pointing down (street-lamp / stage-light look, vertex colors fading to nothing at the rim). Beams follow the light's runtime state — flicker, Set Light, Show/Hide Object — on dynamic lights, and glow steadily on baked ones. Depth-tested against the finished scene (no z-writes), so walls occlude them correctly.
- **Blob shadows** (*Project > Preferences > Shadows*) — a soft dark terrain-conforming quad under every moving thing (the third-person avatar, animated models, physics objects), fading out as the object rises. One quad per object through the flare's soft-glow sprite as an alpha mask — the classic PS2 trick that visually grounds characters and props for almost nothing.
- **Projected shadows** (*Properties > Projected shadow (live)*, not to be confused with the baked-AO *Cast shadow* next to it) — the real thing, per-object opt-in: the object's geometry renders a second time each frame into a small VRAM target (64×64) from a camera at the light, and the resulting **silhouette** is projected onto a terrain patch under it — the actual shape of the object, following its animation and movement. **Each caster picks its own light**: the point light (baked or dynamic) that lights it most strongly wins, so a prop walking past a torch swings its shadow around and grows it as it closes in — a real diverging point-light shadow, not a parallel one. The scene sun competes on the same footing and wins in daylight; in a night scene lit only by torches it scores nothing and stays out of the way. A dynamic light's shadow breathes with its flicker, stops when *Set Light* switches it off, and dissolves over the outer quarter of the light's radius instead of popping. The engine keeps 4 shadow slots (VRAM allocated only in projects that use the feature); the 4 casters nearest the camera are active and fade out with distance, so slot handoffs never pop. Mark hero objects — each caster costs one extra small render — and keep the cheap blob shadows for the crowd. The shadow lands on whatever **solid surface is under the caster** — the terrain, or geometry: an indoor level's real floor is boxes metres above the heightfield, and the receiver patch follows it up there (extents are the same box the walker stands on, so the shadow lands exactly where the feet do). The patch lies on whatever the surface under its CENTRE is - terrain (following the relief) or a piece of geometry (flat, the way a floor is) - so a prop standing inside the patch can no longer fold it into the air. One placement rule remains: put the light *above* the caster — a light level with a wall's middle throws a shadow with no far edge, and the patch is clamped rather than run to the horizon.
- **Sun lens flare** (*Tools > UI Editor > `[ Lens flare ]`*) — additive flare ghosts along the sun-to-screen-center axis (the sun sits infinitely far along the lighting direction, tinted by the light color). Occlusion is one ray cast per frame against objects + terrain, so the flare eases out when the sun hides behind geometry and eases back in the open — no pixel readbacks, PS2-style. The sprites are procedural (baked at build into `res/hud/flare-*.png`), drawn under the whole HUD. Per-scene brightness in *Scene > Preferences > Post effects*; the **Set Lens Flare** flow node changes it at runtime.
- **God rays** (*Tools > UI Editor > `[ God rays ]`*) — sun light shafts: the frame is bright-passed and iteratively zoomed toward the sun's screen position on the GS (reusing the bloom blur buffers — a few quarter-res blits, zero EE/VU cost), then composited back additively. Sky seen through doorways, trees or fog streaks toward the camera, ICO-style. Works with the sun on screen or just past the edge; per-scene strength + the **Set God Rays** flow node.
- **Day / night cycle** — a time-of-day slider from midnight to midnight, with a sun and a moon on authored arcs across the sky: drag it past sunset and the sun really goes down, the moon comes up, and the light swings with them. Not a screen tint — the resolved light direction is what the **vertex shading, the baked contact shadows, the GI bake and its probe grid, and the runtime projected shadows, lens flare and god rays** are all built from, because it replaces the ambience preset's light inside the one function every consumer already reads. Colours through the day come from a free list of keyframes (sky horizon and zenith, light colour, ambient, fog), interpolated cyclically across midnight. The moon disc is baked from **NASA's Lunar Reconnaissance Orbiter colour map** (public domain, built into the editor — only the small disc ships) with the phase applied as a real elliptical terminator, or from any texture you import. A **procedural night sky** comes with it, and it is real glowing points rather than a texture: the field is drawn through additive bags, so each star ADDS its colour to the sky and a bright one saturates and blooms - 400 stars is three submits, per-star colour comes from a black-body temperature, there is a tilted Milky Way band, and fading the whole sky in at dusk costs three bytes a frame. Static or **live**: leave the slider parked and the hour bakes into the scene, or turn on *Let the clock run* and the game advances it - the sun and moon move, the sky gradient and fog retint, the projected shadows sweep, the flare tracks the sun and the stars come out, all from things the frame was already computing. At twilight the light **switches** from one body to the other rather than blending toward a direction neither of them has, and the cast shadows fade out and back across the swap - so dusk dissolves its shadows the way dusk does, instead of flipping them to the wrong side of the caster. The baked half (vertex shading, AO, GI) stays frozen at a chosen bake hour, and a per-frame **drift grade** carries the world's level and colour across the gap - one postFx call, identity at the bake hour, and measured at **50 FPS / 100 %** through a full cycle on the console. See [docs/day-night-cycle.md](docs/day-night-cycle.md).
- **Baked global illumination + light probes** — the sun gets shadows, the sky becomes a light, and light **bounces**: a red wall tints the floor beside it. A host-side ray tracer walks the scene's *real triangles* (not the analytic boxes the contact shadows use, so a cylinder casts a round shadow) and folds sky, sun, emissive materials and baked point lights into one integrator with interreflection. Static untextured geometry takes it **per pixel**, through the RGB channel of the lightmap the ambient occlusion already ships — no new texture, no new pass, no extra VRAM. Everything else — the player, NPCs, animated models, physics bodies, imported models, textured surfaces — reads an **L1 spherical-harmonic probe grid** (12 bytes a probe), so a character walking from sunlight into a doorway darkens and picks up the interior's colour. The console pays **nothing**: 50 FPS with GI on and off alike. Anything that can move is kept off the lightmap automatically (a lightmap glues the light to the surface — tip a lightmapped crate over and it carries a shadow that matches nothing), with *Properties > Baked lighting* as the manual override. The bake is explicit (*Tools > Ambience Editor > Global illumination*, worker thread + progress, or `--bake-gi`) and cached in `.res-baked/gi/` — a build never re-bakes, and a stale bake is *visible* instead of silently shipped. Previewed live in the viewport. See [docs/global-illumination.md](docs/global-illumination.md).
- **Baked ambient occlusion (contact shadows)** — soft shadows where geometry meets: terrain self-shadowing (ravines, foot of hills) and darkening where objects touch the ground and each other. Baked at build into **per-pixel AO textures** (a terrain map + a per-scene primitive lightmap atlas) drawn as extra blended passes — smooth, no visible triangle edges. Scene-wide strength/radius live in *Tools > Ambience Editor* (enabled by default for new projects); **which objects cast is per object** — *Properties > Cast shadow*. Previewed live in the viewport. Imported/animated models cast but don't receive (their per-vertex bake read as triangulated shading — parked until a lightmap unwrap exists). See [docs/ambient-occlusion.md](docs/ambient-occlusion.md).
- **Sky** — gradient dome (horizon/zenith colors) or flat clear color; scripts can retint it at runtime.
- **HUD from images** — `+ Image (PNG)` imports into `res/hud/`; position/size editable with a live preview over the viewport; rendered in-game as 2D sprites. The built-in **USE prompt** is a pinned entry in *Tools > UI Editor*: reposition/resize it or replace its sprite with a custom PNG (reset to the built-in anytime).
- **Fonts** — *Tools > Font Manager*: the project's typefaces, each an entry (name + a TTF imported into the project or a stock system font). Everything that draws text — HUD texts, menus, loading screens, *Display Text* nodes — picks one **by name**, so restyling a project is one edit here. The first entry is the default every unset reference falls back to; replace it to restyle everything at once. No TTF ever reaches the PS2: static text is rasterized to sprites at build, and only a font a *Display Text* node uses additionally bakes a glyph atlas.
- **On-screen texts** — *Tools > UI Editor > Texts*: named texts (font, size, color, multi-line, drop shadow) baked to sprites at build — the PS2 engine has no font. The *Set Text Visible* flow node's show/hide pins trigger them at runtime, with an optional auto-hide after N seconds: subtitles, tutorial hints, pickup toasts. The string is frozen at build.
- **Runtime text** — the **Display Text** flow node draws a string that is only known while the game runs (a score, a save value, a timer), so it cannot be a pre-baked sprite. Wire any text source into it (*Get Save Text*, *Get Int As Text*, *Position To Text*, ...), give it a font, screen position and size, and drive its **show** and **hide** pins; a static prefix ("Score: ") sits in front of the wired value. It draws glyph by glyph from the font's baked atlas, and that atlas only reaches VRAM the first time the text is actually on screen — a font nobody displays costs nothing.
- **Screen effects** — *Tools > UI Editor* composites the whole screen as one reorderable **screen stack**: the built-in **bloom** (+ color grading) and **film grain** effects and the HUD sprites, dragged into the order they draw (e.g. bloom under the HUD so it doesn't blur the crosshair, grain over everything). Bloom carries a **Threshold** (bright pass) and a **Spread**: at threshold 0 the whole frame glows (soft focus), raised it collapses the halo onto the pixels brighter than the cut — which is what turns an [emissive material](docs/emissive-materials.md) into a glowing object instead of a veil over the picture — while Spread adds blur rounds with doubled tap offsets to grow a tight fringe into a real corona. Bloom itself goes to **2×** (the GS blend factor is a whole byte, so the blur can be over-added for a blown-out glow). Cost: one extra quarter-res GS sprite for the bright pass, four per spread round, no EE time. A **depth of field** effect blurs the image past a focus distance — per-pixel, following real scene depth (the blurred frame is composited back through z-tested sprites). It is authored as its own pinned stack entry (*Amount* / *Focus* / *Range*, per-scene overridable in *Scene > Preferences > Post effects*) that always composites right after the 3D scene, under the whole HUD — sprites stamp depth across their full rectangle, so compositing DoF above them would punch sharp boxes into the blur; pinned underneath, the HUD always stays crisp. At runtime the *Set Depth Of Field* flow node overrides it (custom focus / range / amount, or wire a position to keep an object in focus), switches it off, or restores the scene's authored values (*Scene setting* mode). Need an effect the editor doesn't have? Define your own **custom screen effect** in a `screen-effects/*.screenfx` text file — no editor rebuild. There are no pixel shaders on the PS2, so an effect is written **low-level** (a small manifest + raw GS-blit C++, the same way bloom/grain are built); it appears as a positionable stack entry with numeric parameters. Copy the file to reuse it in other projects: [docs/custom-screen-effects.md](docs/custom-screen-effects.md).
- **Neural upscaler (BLSS)** — *Tools > Neural Upscaler (BLSS)*, settings mirrored in *Project Preferences > Rendering*, off by default. Renders the 3D scene into a **half-resolution** GS target and reconstructs it to the display buffer, with a small **neural network** — a 6→12→3 MLP, trained on the host, baked into the game as 123 floats — deciding per 32×32 screen tile how much **point**, **temporal** and **sharpened** reconstruction that tile wants. Three facts about the hardware make it possible: `XYOFFSET` is 12.4 fixed point, so the frame can be jittered by an exact ±¼ pixel for free (two phases = a real quincunx pair); the GS blend factor can come from **per-vertex alpha**, so drawing a Gouraud grid instead of a sprite turns the network's output into a smooth spatial field the rasteriser interpolates for nothing; and double buffering already keeps the previous finished frame at full resolution, so the temporal history costs **zero** VRAM. The network never touches pixels — its six inputs (motion, depth, depth gradient, geometric edge density, texel density, coverage) all come from what the EE already holds while it submits bags, so no frame is ever read back and nothing stalls the pipeline. It had eight, and both deletions were **measurements rather than tidying**: `histAge` was letting the net memorise which shot had been still rather than learn anything, and `luma` was a channel the EE could not actually produce, so the net was fitted on a brightness and run on a constant. `--blss-eval --cv --drop-feature` with a control channel is what settled both. Cells whose weight rounds to zero are not drawn, so the net's own confidence sets the frame's fill cost — and **the training objective charges for that fill**, as a step on the quantised alpha byte the hardware's own skip test reads, because a kernel nothing pays for is a kernel the network asks for everywhere. The HUD and every post effect still draw at full resolution. **Everything below is in the editor**: the *Tools > Neural Upscaler (BLSS)* window trains, evaluates, cross-validates and emits without a terminal, on a background worker that leaves the editor usable, showing the tables as tables, the comparison renders as pictures with an A/B wipe, and the tool's own output underneath every one of them - it runs the CLI below and parses it, so there is no second implementation to disagree. **Which corpus is one switch in its header, shared by all five verbs, and it defaults to this project's own scenes** with *Fit every shot* on — the configuration that was measured to work; a per-tab copy is how a net trained on the project gets evaluated against the bestiary without anyone noticing. Train it with `tyrax-editor --blss-train <projectDir>` — **on your own project, not on the built-in corpus**: a net fitted to the procedural bestiary measured **worse than doing nothing** (−0.4 dB) on a real project's scenes, because the channels its temporal gate leans on are out of range there. `tyrax-editor --blss-eval <projectDir>` also answers "is there anything to win here at all", which for some scenes is no — the window's Evaluate tab states that verdict in one line above the table, from the oracle row, which is the scene's own ceiling. `--blss-eval` prints PSNR against every fixed kernel and against that oracle upper bound, plus temporal flicker and **occupancy** — what fraction of the screen each pass actually draws and the mean full-screen passes per frame (1.00 is plain bilinear, 5.00 the worst case, the shipped net ≈1.8). Training is threaded (`--threads N`, the corpus render and the oracle; the sequential SGD fit is now the largest remaining phase at 34%) and **the thread count moves the wall clock and nothing else** — the same seed writes the same `blss.net` byte for byte at any `--threads`, including matching the binary from before the corpus was parallelised, which is what keeps every published fold table a measurement of the current code. `--blss-eval --cv` is **leave-one-shot-out cross-validation** and is the number to act on: one held-out split is a sample of size one, which this feature quoted five times before anyone checked. It also **hands VRAM back**: the z buffer follows the reduced raster instead of the display, which returns more than the low-res colour target costs (measured at PAL 512×512: 0.227 MB free with it off, 0.727 MB with it on). Incompatible with depth of field — including a `Set Depth Of Field` flow node — portals and split-screen (they need real GS depth at display resolution); the **build refuses** the combination with an `#error` naming the feature and the scene, and the editor says the same thing live before you get there. Reflections, camera feeds and projected shadows used to be silently broken by it and are not any more. Still a **proof of concept, off by default**: on content it was *not* trained on it beats plain bilinear by **+0.42 dB** (13 shots × 3 seeds = 39 fold-runs, sd 0.35, 3 below bilinear; +0.26 dB over the six shots that took no part in tuning), it still *loses* on an indoor corridor, and no frame timing has been measured on console or hardware. What the console *is* instrumented for is what the network sees: engine debug view 2 — a *Debug view* entry in the settings now, not a hand-edit of the `.tyra` — logs the per-channel spread and the fill each frame paid, and `--blss-eval --probe` places that line inside the training distribution — the pair that found the frame being described to the net by two bounding spheres. Full guide: [docs/neural-upscaler.md](docs/neural-upscaler.md), arithmetic in [docs/blss-reconstruction.md](docs/blss-reconstruction.md).
- **Game menus** — *Project* panel, *Menus* (or *Tools > Menu Editor*): panels baked to sprites at build and driven by the dpad in-game. Entry actions: close, switch scene, open the save menu, open a submenu, set/add a save value, fire a flow event, roll the credits, rebind a key, apply a video mode — plus stateful **Toggle** and **Choice** rows bound to a save value, and **Label** rows (section headers and spacers the cursor skips). A row can also carry a **class**, an **icon**, a **description** and an **Enabled when** save value that greys it out and makes the cursor skip it, so a LOAD GAME row can be dead until there is something to load.
- **Menu stylesheets** — the look of a menu is a **CSS-shaped stylesheet** (`menu-styles/*.menustyle`), edited with widgets in *Menu Editor > Style* and baked at build: a real box model (gradients, 9-slice frames, rounded corners, drop shadows, per-element fonts, letter spacing, text outlines), per-state row styling (`row:selected` with a highlight plate that the cursor eases onto, `row:disabled`, `row.myclass`), **scrolling lists** up to 32 rows, a **description pane** for the selected row, **slider bars** instead of option labels, and **motion that costs nothing**: open/close transitions, a caret that eases between rows, a breathing highlight, a light sheen sweeping the panel, a list that settles into its window, a flash on a changed value — and, for what a baked gradient cannot do, an **animated background layer** (`background-anim`) that either scrolls a tiling texture or steps through a frame strip, all of it one sprite and one texture. Everything static is baked, so it costs the console nothing; a state costs one baked cell and the editor prints the count, the textures, the KB and the **% of GS VRAM** before you build. Five sheets ship as starting points (Classic, Neon, Blade, Parchment, Minimal) — *Install a copy…* puts one in the project. A menu with no sheet is the old look, byte for byte, so existing projects change nothing; the menu's own accent/sizes/font remain the base of the cascade. Menus also **scale to the display mode** (the framebuffer is 512x448 interlaced but 448x540 in 1080i), and the preview can show any of the project's *Supported resolutions* at the size the game will really draw it. Edit the sheet with widgets, as text with live diagnostics, or **Open in VS Code** (the bundled extension colours `.menustyle`); watch it in a **Menu Preview** window of its own with a zoom and the cost readout, and use the **Menu Designer** layout (*Layout* menu) to get the editor, that preview and the Font Manager arranged in one click. Full guide: [docs/menu-styles.md](docs/menu-styles.md).
- **Options menus** — the Menu Editor scaffolds settings screens: **+ Options menu** builds an *OPTIONS* root that opens *AUDIO* / *CONTROLS* / *DISPLAY* submenus (categories are plain submenus, so all styling applies), and **+ Option block** drops a ready-made row bound to a built-in engine setting — music / sound volume, controller deadzone, aim response curve, display mode (480i/480p/1080i/480i field rendering/full-height PAL 576i) and widescreen (4:3/16:9). Each block is a normal Toggle/Choice row you can restyle and relabel; the generated game applies the chosen option to the engine every frame, no flow wiring needed (persisted in the save value like any stateful row). The display-mode row's options are picked from a **dropdown of the engine's scan modes** (offer any subset, in any order, with a free-text label), including a **Default (project)** entry that maps to whatever mode the game booted in on the player's console (the region + PAL-picture default, or the project's fixed mode) — so a typical row is DEFAULT / 480p / 1080i and "default" always means the right thing per region, and an **Apply video mode** row makes it stage-then-commit: while one exists anywhere in the project, cycling the display option only stages the choice and the screen switches when the player picks APPLY (with the keep-or-revert prompt); without one the row keeps the classic switch-on-change behavior. The scaffolded *DISPLAY* submenu includes the APPLY row.

- **Save Editor** (*Tools > Save Editor*) — everything about memory card saves in one place. **Card appearance**: set the save's browser **title** (two lines, `|` breaks the line) and give the save a real **3D icon**: pick any project model — a `res/models` **.obj** (with its `map_Kd` texture) or an **animated .glb**, whose chosen **clip** is sampled into up to 8 morph shapes so the icon *plays your animation in the PS2 browser*, exactly like retail saves — or stay with the default **image quad** (any project picture resampled to the PS2's 128×128 icon texture). Models get auto-fitted into icon space, static sources (the quad, .obj) receive a gentle idle sway, and the Save Editor shows the exact triangle/shape/size cost next to a byte-exact texture preview. The editor bakes real `icon.sys` + `list.icn` files (`res/save/`) and the game copies them onto the card, so the save shows up in the PS2 browser with your game's name, artwork and motion instead of an anonymous folder. **Size preview**: an exact byte breakdown of what one save slot stores (header, each save value, the 32-byte text slots, save-flagged object states) with the resulting slot file size, and — separately, because it is always bigger — the **card space actually used**, since a PS2 card allocates whole 1 KB clusters and no two files share one (a 128-byte slot costs a full kilobyte). Plus a per-scene list of every object with *Save state* enabled, so "what actually lands in my save?" has a visible answer. **Save data**: the named values and texts persisted in every slot (moved here from the Project panel) that flow-graph *Save* nodes read and write. Full guide: [docs/save-editor.md](docs/save-editor.md).
- **Checkpoints** — flow-graph save points that don't touch the memory card: **Save Checkpoint** snapshots the entire save payload (scene, player, values, texts, flagged objects) into a single in-RAM buffer — instant, no "checking memory card" pause — and **Load Checkpoint** restores it (respawn-on-death without a card round-trip). **Commit Checkpoint** writes that snapshot to a real card slot when the player reaches safety, and **Has Checkpoint** is a bool source for wiring "Continue from checkpoint?" logic. Deliberately only one checkpoint exists at a time and the buffer is the same fixed-size payload a card slot stores (typically well under a kilobyte, shown in the Save Editor) — checkpoints cost a few KB of RAM, never megabytes.
- **Memory card safety screen** — every real card write/read shows the classic full-screen warning ("Checking memory card (PS2)... Do not remove the memory card, reset or switch off the console.") over a dimmed game. The warning is guaranteed to be on screen *before* the blocking card transfer starts and holds for a minimum beat afterwards, exactly like retail games; the sprite is a baked text (`res/hud/save-busy.png`), replaceable like the other save-menu sprites.

- **Start scene** — which scene the game boots into is *Scene > Preferences > Startup > "Boot into this scene"*, and the *Project* panel marks it **(start)**. New projects boot the first scene, so nothing changes until you move the tick; deleting a scene carries the setting with the scene it points at rather than leaving it on a number. It reaches the game as the single `START_SCENE` the boot `loadScene()` takes, so testing a level deep in the game no longer means walking there through every *Switch Scene* — see [docs/loading-screens.md](docs/loading-screens.md#the-start-scene).
- **Loading screens** — *Tools > Loading Screens*: define named loading screens shown while a scene loads (also at boot). Each has a background color, image and text elements (baked like the HUD) and **progress bars** — *continuous* (a track with a fill that grows) or *quantized* (N segments that light up one per 1/N of progress; segments are colored rects or an optional PNG tinted on/off). The bar reflects **real** load progress: the game counts the work (streamed assets + objects + terrain chunks) and presents the screen every few units. Assign a screen per scene in *Scene > Preferences*, mark one the project default, or leave a scene unset to use the default; with none defined, the built-in `loading.png`-on-black is shown. The master toggle stays *Project > Preferences > "Loading screen between scenes"*. See [docs/loading-screens.md](docs/loading-screens.md).
- **Credits rolls** — *Tools > Credits Editor*: end credits as project-wide data, started by a menu row (action **Play credits** — a title screen's `CREDITS` row) or the *Play Credits* flow node. A roll is a vertical flow of blocks — **headings**, **role/name rows** (the classic two-column credit, several names per role), **wrapped lines**, **images** and **page breaks** — each free to override the roll's size, typeface and color, so restyling a whole roll stays one edit at the top. It **scrolls up** at a chosen speed or plays as **cards** (one screenful at a time, cross-fading — title cards, dedications), over a **music track** it starts (and stops) itself, with a fade in/out, a start delay and an end hold, an optional still **backdrop** image, and a **skip** that accepts the menu confirm action (or one you name) after a short deadline plus a baked `PRESS {{cross}} TO SKIP` hint. A roll **owns the screen and the pad** while it plays — nothing is simulated behind it — and then runs its own **finish action**: resume the game, switch scene, open a menu, fire a flow event (caught by *On Menu Event*), or hold the last frame; a skip runs it too, so a player who skips lands where a player who watched lands. *On Credits Finished* fires either way. Long rolls belong in a text editor, so **Import text...** reads a plain-text format (`# SECTION`, `Role: Name`, `> centered`, `[image ... 0.5]`, `---` for a page break) and *Re-import* picks the file up again after an edit. On the console the roll is a **strip of baked page textures** the runtime scrolls — two sprites a frame whatever its length — and because the GS pins every texture it draws, the editor prints the page count, the running time and the VRAM estimate under a preview that draws **the same baked pages the console gets**. Full guide: [docs/credits.md](docs/credits.md).
- **Runtime scene** — scripts receive mutable `RuntimeObject`s (move/hide/recolor objects every frame); geometry rebuilds automatically.
- **Project preferences** (`Project > Preferences`, `Ctrl+,`) — the project's preset (read-only: it is picked once in *New Project* and fixed for the project's life, since it decides which user-ownable game sources are generated), terrain size and detail (max grid cells), **video output** (target system NTSC/PAL/auto plus the scan mode: stock interlaced 480i/576i, interlaced with **true field rendering** — a fresh half-height 512x224 image every field, i.e. 50/60 distinct pictures per second at full speed for about half the fill and VRAM cost of whole frames, the classic PS2-era recipe — flicker-free **progressive 480p**, pillarboxed **1080i** — the two DTV modes need component cables on a real console and always run at 60 Hz — or full-height **PAL 576i**: a true 512-line PAL frame (the "full PAL" of European retail releases, ~14% more picture than the NTSC-sized modes), always a 50 Hz PAL signal regardless of the target system, at the cost of ~380 KB of GS VRAM. The region-following interlaced mode additionally has a **PAL picture** choice — *Letterbox* keeps the classic NTSC-size 448-line picture on PAL consoles, *Full-height 576i* promotes them to the true 512-line frame at boot (NTSC consoles always get 480i), so one build serves both regions the way the author intends; PCSX2 shows every mode — and a **Widescreen (16:9)** switch that widens the projection anamorphically for widescreen TVs), **triangle handling** (*Precise clipping on VU1* — the default: no holes at screen edges and no EE cost, triangles are clipped by the VU1 microprograms; *Precise clipping on EE* — the legacy CPU clipper, kept for comparison/fallback (projects saved before the VU1 default keep it automatically); *Fast culling* — fastest, large near triangles may vanish), sky color, the player camera defaults (eye/body height, walk/look speed) for the two player presets or, for the empty one, the orbit speed — how fast the camera circles the terrain when no Player object owns it, 0 (the Empty preset's default) parking it at a fixed vantage point. The scan mode and widescreen can also be changed at runtime from the flow graph (**Set Display Mode** / **Set Widescreen**): Set Display Mode optionally shows a "keep video mode?" prompt that reverts automatically unless the player confirms with X in time — so a mode the TV can't display never strands anyone on a black screen. Stored in the `<name>.tyra` project file and baked into the generated `terrain_config.hpp` on every build; the viewport reflects sky color and terrain detail immediately. A **debug** build profile also enables on-screen overlays (*Show FPS*, *Show memory usage*, a per-phase EE-time **frame profiler** — whole frame / scene / usable-highlight / particles; see [docs/profiling.md](docs/profiling.md) — and *Show areas*, which draws Area objects in the game as wireframe boxes so an invisible volume stops being invisible when you are debugging why a zone did not unload), all stripped from release builds.
- **Pickable objects** — check **Pickable** on any solid object and the player can press **USE** on it to pick it up (the on-screen prompt says **PICK UP** instead of USE — built-in `res/hud/pickup.png`, replace to customize): it hovers a short reach in front of the face and is **swept against the world every frame**, so it keeps colliding with walls and props — you can neither push it through geometry nor park it behind something. The carry reach follows the third-person spring arm's policy: a blocked reach **snaps in** (the object comes closer to the face, never into the wall) and eases back out when the wall clears; a **carry whisker** in the walker pushes the carrying player back from geometry the object no longer fits in front of, so you can't press face-first into a wall while holding something. It stops colliding only with its *carrier* (it can't wedge the player, and the third-person spring arm ignores it). USE again drops it exactly where it hovers — always a legal spot; give the object **Physics** and it's handed straight back to the rigid-body sim on release (it wakes, falls, bounces and rolls with its own mass/bounce/friction/tumble), while a non-physics object simply stays where you left it. An experimental **Can throw** option launches the carried object with **Circle** (`BTN_THROW`): a physics object is thrown *by the sim* — it arcs, bounces off walls and tumbles to a stop — and a non-physics one flies a simple swept arc that stops on the first hit. Reach, throw speed and the button live in `inc/controls.hpp`. A pickable object can also be *Usable* — the same press fires **On Used** (wire a grab sound) and picks it up; while your hands are full there is no use-targeting, USE means "drop".
- **Usable-object highlight** — objects marked *Usable* glow while the player is within a proximity distance (color / rim width / blur steps / opacity in *Preferences > Usable objects*, per-scene overridable). Drawn cheaply on VU1 as grown silhouette shells; opacity sets the strongest shell's transparency (the rest fade from it), and an experimental **Draw over object** toggle paints the glow *on* the surface instead of only a rim behind it.
- **Build & Run in PCSX2** (`F5`) — builds the ELF inside a Docker container (the `h4570/tyra` image with the PS2DEV toolchain) and launches it in PCSX2. Build logs stream into the *Output* window.
- **Logs split by severity** — both log panels (*Output* for the build/run stream, *Debug* for the game's own `log.txt` and PCSX2's `emulog.txt`) classify every line as **error / warning / info / verbose**, draw it in that color, and put a **chip per level with its count** above the log — click one to hide that level, so "show me only what broke" is one click on a 15 000-line build log. A diagnostic is treated as a *run* of lines, not a line: a compiler error keeps its source snippet and notes, and an engine assertion dump keeps its whole body, so hiding the noise never leaves an error stranded without the lines that explain it (which is also why the counts read *1 error* for such a block — they count entries). **Copy** copies what is shown, and because ImGui's editable text is one color, a **Select text** toggle swaps in a read-only box over the same filtered lines when you want to select with the mouse. The filters live in `editor.ini`, per panel. See [docs/log-panels.md](docs/log-panels.md).
- **The run toolbar** — the menu bar carries the whole build/run loop as icons: **Save**, **Build** (no run), then **Play**, its caret dropdown, **Debug** and **Stop**. The dropdown picks the **target** — *Emulator (PCSX2)* or *PlayStation 2 (ps2link)* — and both triangles are colored by it, **green for the emulator, blue for the console**, so you can see where the next run goes without opening anything. Under the target sit the run variants for it: **Run**, **Run without build** and **Debug**. **Debug** (also its own button, a play triangle wearing a breakpoint dot) builds & runs and opens the *Debugger* panel; it stays on the bar always but greys out outside the *Debug* build profile, because Live Link, the Live Debugger and Live Logic only exist in debug builds. **Stop** cancels a running build, and otherwise closes PCSX2 or stops the game on the console, following the same target. The target choice is machine-global (`editor.ini`), not project data; `F5`/`Ctrl+F5` (emulator) and `F6`/`Ctrl+F6` (console) stay target-explicit and ignore it. The live chips (LIVE / DBG / LOGIC / SESSION) follow to the right.
- **Live Link** — edit the **running** game: with the *debug* build profile, moving / rotating / scaling / recoloring objects streams into the game live (a gizmo drag moves the object on screen as you drag), and **adding / deleting objects works too** — new objects are instantiated through the game's runtime spawn pool (cloning a same-recipe authored object), deleted ones are hidden, undo restores them. Works in PCSX2 **and on a real PS2** — the snapshots travel over the same host filesystem the game loads assets from, so no extra transport exists. The toolbar **LIVE chip** shows the state (green streaming / amber "rebuild" when an edit can't be applied live — recipes changed, no template to clone, baked lights/decals/mirrors…) and **clicking it toggles Live Link per project** (also *Build > Live Link* and *Project > Preferences > Build*); off = the game is built without the poller, and release builds never carry it. **Texture hot reload** rides the same channel: repaint a texture in the Material Editor (or re-bake its AO layer) and the running game **re-uploads the pixels into the texture's existing GS VRAM allocation** within a fraction of a second — paint in the editor, watch it change on the console, no rebuild. See [docs/live-link.md](docs/live-link.md).
- **The frame's vital signs** — *Debugger > Stats*: FPS, what went to VU1 this frame (bag flushes, quadwords, vertices), **GS VRAM** free with its low-water mark, resident textures, uploads and evictions, free **EE RAM** on request, and the scene's object counts. Plus a **flush map** — every draw of the last frame with its vertex count, fattest highlighted, **click one to capture it**. None of it is newly measured: the engine and the VU1 tap already counted all of it on the console, and it was simply never carried across. See [docs/devkit.md](docs/devkit.md).
- **See what VU1 was fed** — VU1 debugging is blind (no printf, output straight to the GS), so the devkit taps the one thing that *is* ours: the DMA chain the EE builds for every draw. One click captures the next packet and the editor decodes it — DMA tags, VIF `UNPACK`s with their VU1 addresses, the `MSCAL` that names the microprogram — plus a **wireframe of the exact vertex stream** that went across (orbit it with the mouse). A frame sends one chain per bag flush, so **each click walks to the next draw** (or pin one and watch it over time), and one flush holds a position stream per mesh — a slider picks which the wireframe draws. Above it the panel prints **what looks wrong**: a staged packet that misses the drawing window, triangles spanning the whole GS plane, degenerate or fully transparent geometry. Headless: `--dump-vucap`. See [docs/devkit.md](docs/devkit.md).
- **Write a VU1 microprogram in C++, and run it without a PS2** — the last hand-carved part of the engine has a framework. A program is *described* once in C++ and both sides are generated from it (the `.vclpp` microcode and the EE-side class whose unpack layout and tag-block arithmetic used to be kept in step by hand), and a **host VU simulator** executes it on either vector unit — VU1's 1024 quadwords of data memory or VU0's 256, masked fields, the accumulator, Q/I, the clip flags, and the `vcallms` entry contract a VU0 kernel is called under. The backend emits VCL rather than raw microcode, so `vcl` still schedules and allocates registers: a generated program goes through the same optimizer as a handwritten one. The claim is *checked* rather than asserted — `--vu-check` runs the handwritten and the generated program on identical randomized input and diffs every quadword the GS would receive, and all fifteen StaPip programs - the five `as_is`, the five `cull` and the five Sutherland–Hodgman `clip` programs, control flow, scratch polygons and all - come back **bit-identical**, at the same instruction count. It also flags what the assembler will not: a `div` whose Q is overwritten before anything read it. See [docs/vu-framework.md](docs/vu-framework.md).
- **Compose a microprogram out of stages, with no assembly at all** — *Tools > VU Programs*. A project's own VU1 program is a **base plus an ordered list of stages** (Wobble, Twist, Inflate, Squash, Vertex snap, Posterize, Desaturate, Scroll UV…), each parameter either baked into the microcode or bound to one of **four per-mesh numbers** set in the object inspector. VU1 micro memory has no room for a program per object, so the effect is per material class and its STRENGTH is per mesh — which only works because **every stage is the bit-exact identity at zero strength**, checked against the engine's own program over randomized draws. The panel answers the two questions authoring raises without a console in the loop: the micro-memory bar against the real 2042-slot ceiling (read from the engine's own `.vclpp` files, with the resident set auto-detected from what the scenes draw), and the program **run in the host simulator** with its GS vertices printed beside the same run at zero. See [docs/vu-authoring.md](docs/vu-authoring.md).
- **…and the same C++ authoring on VU0, as a compute kernel** — a `.cpp` in `src/vu0/` subclassing `vu::Kernel` becomes **N quadwords in, N quadwords out**, plus the EE driver that calls it: `setParams` / `setTime` / `run(in, out, count)`. Same value types, same scratch contract, same `c.raw()` escape hatch as a VU1 script — and the stage catalogue still composes one too, for what it covers. It is a **calculator, not a GPU**: 512 micro slots, 256 quadwords of data memory, `run()` blocks the EE and clobbers the register file the engine's `Vec4` math uses, and there is **no cross-element reduction** (VU0 computes the terms; the EE sums the array). What it costs the VU1 drawing budget is **nothing** — those instructions land in VU0's own micro memory. `--vu-check` builds and runs every project kernel on the host under the VU0 machine model, and reports one that changes nothing, overflows, or comes back non-finite. See [docs/vu-authoring.md](docs/vu-authoring.md).
- **Crashes report themselves** — a failed assertion or a recovered asset error prints a delimited **TYRAX** block that the editor pops in a copyable dialog; a game that simply *stops* is caught by the devkit's heartbeat ("stopped reporting at frame 1487") and shown next to **what the graphs were doing in the seconds before**; and with the *EE crash handler* on, a real CPU exception says so **on the TV** and writes a register dump plus backtrace that the editor resolves to **function names and source lines** through the PS2 toolchain (`--symbolize` headlessly), with a **Run again** button next to it. See [docs/devkit.md](docs/devkit.md).
- **A real devkit, with a receipt** — Live Link, the Live Debugger, Live Logic, the time machine and the Remote Pad form one development kit for the console (all of them over the same host filesystem, PCSX2 **and** real PS2). The part that matters for shipping: **a release build carries none of it** — the generated runtimes become empty translation units, the predicates become compile-time `false` so the calls fold away, and the instrumentation is never emitted. That claim is *checked*, not asserted: every release build runs an **audit of its own ELF** (`--audit-release`) that scans for deliberate devkit markers and the channel file names, and prints the verdict with the numbers. Measured on one project: debug carries ~18 KiB of extra code and ~145 KiB of `.bss`; release comes back **clean**. See [docs/devkit.md](docs/devkit.md).
- **The time machine** — the running game captures everything it mutates (object transforms and physics, animation, flow variables, save values, where the player stands) a few times a second into one small fixed-size file next to the ELF; the editor keeps a history of those captures **in memory** and the Debugger's *Rewind* tab pushes any of them back, so the PlayStation 2 snaps into the state it was in seconds ago and keeps running from there — no rebuild, no reboot. Together with Live Logic that is the whole loop: rewind a few seconds, fix the graph on the running game, and watch the fix play out on the situation that just broke. The history is bounded by a RAM budget (`Edit > Preferences`, 128 MB by default) and never grows on disk; a release build carries none of it. See [docs/time-machine.md](docs/time-machine.md).
- **Live Logic** — **edit a flow graph and the running game changes, with no rebuild.** Graphs normally compile to C++ (that is why editing one meant a Docker build); with the *debug* profile the editor **compiles the graph itself** into a pre-resolved instruction list, drops it next to the ELF on the same host filesystem, and a small interpreter in the game runs it while the natively compiled script for that graph stands down. Change a timer, a color, a radius, rewire the exec chain — it takes effect in a fraction of a second, on PCSX2 **and on a real PS2**. Triggers, object/scene/HUD/variable/save actions, delays, logic gates and conditions are covered; graphs using audio, AI, animation, spawning or runtime text are named in the *Debugger > Logic* tab and still need a build (the **LOGIC** chip goes amber). A patched graph shares variables, save values and Live-Debugger node keys with the compiled ones, so breakpoints and node highlighting keep working. See [docs/live-logic.md](docs/live-logic.md).
- **Live Debugger** — the other direction of Live Link: **step through your game's logic while it runs on the PS2**. A debug build reports every flow-graph node it fires, so the *Flow Graph* window becomes a live instrument — node titles glow as they run, the exec links behind them light up, hit counters tick in the corners. Set a **breakpoint** on a node (right-click it) and the game **stops** — world frozen, picture still up — then **Continue** (F10), **Step frame** (F11) or **Step node** (run until anything fires). The *Debugger* panel (F9, plus a built-in **Debugger** window layout) watches every flow variable and save value live, lists breakpoints, and keeps a **rewindable timeline**: scrub back through the last ~900 frames and the graph replays what fired on each one. You can even **fire a trigger from the editor** to test a branch without walking to it. Same host-filesystem channel as Live Link, so PCSX2 and a real console over ps2link work identically; the toolbar **DBG chip** shows fps / halted / rebuild-needed. Release builds carry none of it (the hooks compile to nothing). See [docs/live-debugger.md](docs/live-debugger.md).
- **UI scripting** — **the editor can drive itself.** `tyrax-editor --ui-script <project> "click Tools; click 'Remote Pad'; hold 'Remote Pad/Cross' 2; shot pad.png"` runs the real editor and holds its own mouse and keyboard, naming **widgets** instead of pixels — so a script does not care about DPI, UI scale, or where a panel is docked, and **no window needs the keyboard focus**. It falls out of two things Dear ImGui already does: it announces every widget it submits (label, rectangle, checked/open state) through hook functions meant for a test engine, and its input is a queue anyone can push to. `dump` prints every widget on screen with its state, which is how you find out what a dialog's button is called; `expect` / `expect-checked` turn that into assertions, and the exit code gates a shell script. The `imgui_test_engine` library is *not* vendored — none of it is needed. See [docs/ui-scripting.md](docs/ui-scripting.md).
- **Remote Pad** — **hold the running game's controller from the editor.** *Tools > Remote Pad* draws a DualShock you can click (and a keyboard mode: WASD/arrows on the left stick, IJKL on the right, Space = Cross…), and the game overlays that state on its physical pad. The point is that **nothing needs the window focus**: PCSX2 can sit behind the editor or on the other monitor and still be driven — so testing a pad-driven feature no longer means clicking into the emulator first. The same channel is **scriptable**: `tyrax-editor --pad <project> "stick l 0 -127; wait 2; press cross"` drives a running game from a command line, which is what makes an unattended input test (drive, then screenshot) possible at all. Works in PCSX2 **and on a real PS2** over the same host filesystem, drives both connectors (so a two-player hot-join is testable with no second controller), and a driver that stops refreshing the state has it dropped rather than leaving a direction held. Release builds carry none of it. See [docs/remote-pad.md](docs/remote-pad.md).
- **Graceful errors** — engine errors in the running game no longer take over the console screen. **Missing assets degrade instead of crashing**: a missing/broken texture shows an obvious magenta placeholder, a missing model/sound/animation is skipped, and the game keeps running. Genuinely fatal errors (a real assertion) halt the game with the last frame left on screen. Either way the editor tails the game log and pops the error in a **copyable** dialog (worded "kept running" vs "stopped"), flashing the editor window for attention. The same text is in the *Debug* window (*Game log*), where it is one of the entries the **errors** chip counts (see the severity split above). Turn the popup off with *Pop up on errors* there (or in the dialog) to let errors go only to the console — the setting lives in `editor.ini`.

## Requirements

- **Windows or Linux.**
- [Docker](https://www.docker.com/products/docker-desktop/) running (Docker Desktop on Windows, `docker` + the compose plugin on Linux) — the generated game is compiled inside the `h4570/tyra` container.
- [PCSX2](https://pcsx2.net/) with a BIOS configured. Auto-detected in `Program Files\PCSX2` on Windows, and on PATH / as a flatpak / as an AppImage under `~/Applications` or `~/Downloads` on Linux. Any other location can be pointed at under `Edit > Preferences`.
- To build the editor:
  - Windows: CMake, Ninja, GCC/MinGW (e.g. `scoop install mingw cmake ninja`). **MinGW only** — MSVC cannot compile `src/templates.cpp` (see the Quickstart note).
  - Linux: CMake, Ninja, GCC and the X11/Wayland/GL development headers — `./setup.sh --deps` installs them for apt / dnf / pacman / zypper. `zenity` (or `kdialog`) provides the native file dialogs; without one the editor still builds and runs, but the Open/Import buttons have nothing to open (`build.sh` warns).
- **Keep the project path short.** PCSX2's `host:` loader silently refuses an ELF path longer than about 145 characters — it loads the ELF and the game never starts, with a black window and nothing in the log. The editor warns in the *Output* panel when a project is past the limit; move it somewhere shorter. (Easy to hit on Linux: a home directory plus a deep tree adds up fast.)

## CLI

Projects can also be created and built headlessly:

```bash
tyrax-editor --new <name> <parentDir> [width] [depth] [empty|fpp|thirdperson] [unitsPerMeter] [--no-terrain]
```

(`build\tyrax-editor.exe` on Windows, `build/tyrax-editor` on Linux.)

projects). Use it to batch-migrate existing projects without opening the GUI.

`--build`/`--resave`/`--refresh-gen`/`--apply-graph`/`--ai-graph`; run
`--migrate` instead — it backs up the project files into `_backup/` first,

for the same backup-and-migrate. See
[docs/format-versioning.md](docs/format-versioning.md).

`--new` takes the same defaults as the dialog: `100 100` terrain, the `empty`
preset and `unitsPerMeter` = 1 when omitted, the **debug** profile with Live
Link on and USB keyboard & mouse off. It prints the terrain size and the world
scale it used. The preset argument takes the same three values the dialog
offers (`fpp`, `thirdperson`, `empty`); anything else is treated as `empty`.

A second family of commands targets AI assistants working inside a generated
project — `--dump`, `--list-nodes`, `--dump-graph`, `--apply-graph`,
`--ai-graph`, `--add-ai-support`, `--chat-prompt` — see
[docs/ai-tools.md](docs/ai-tools.md).

## How Build & Run works

1. `docker compose up -d` in the project directory (the first run downloads the `h4570/tyra` image). Each project gets its own container (`<name>-compiler-1`) straight from that image — there is no per-project image to build.
2. The Tyra engine sources live **in this repo** (`vendor/tyra`, bind-mounted read-only at `/engine-src`). The Runner syncs them into the shared build volume (`tyra-engine-<hash of the engine path>`, mounted at `/tyra`) with a checksum `rsync`; when anything changed, `libtyra` is rebuilt once and every game relinks against it — all projects built from the same checkout share the result. The VU1 microprograms sit outside `make`'s dependency tracking and are force-rebuilt, but only when a VU source (`.vclpp`/`.vcl`/`.vsm`/`.i`/`.h`) actually changed — editing engine C++ costs seconds, not the two minutes `vcl` needs for the whole set.
3. `rsync` project sources into the container volume (`/host` → `/src`).
4. `make -j` inside the container (`mips64r5900el-ps2-elf-g++` compiler).
5. `rsync` the `bin/` directory back to the host.
6. Launch `pcsx2-qt -elf <project>/bin/<name>.elf`.

Every step is incremental, and that includes the code generation: a generated
file whose content did not change is not rewritten, so `make` sees the same
timestamps it left behind and a build with nothing to do finishes in seconds.
When something goes wrong in a way an incremental build cannot see, **Build >
Rebuild** (`--build <projectDir> --rebuild`) drops all of it — the container,
the game objects, the compiled engine — and builds from source. *Clean* is the
neighbouring hammer: it also wipes `bin\` on this machine.

## Run on a real PS2 (network deploy)

With a PS2 connected to the LAN and running the **TyraX ps2link**,
**Build > Build && Run on PS2** (`F6`) boots the
game on the console over ethernet: the ELF and every asset are served straight
from the project's `bin\` on this PC (no ISO, no SMB), and the console's log
streams live into the *Output* window as `[ps2]` lines. Set the console's IP
under `Edit > Preferences > Real PS2` (a machine-global editor setting, shared
by every project); headless: `--build <projectDir>
--run-ps2 [ip]`. The editor drives the console with a patched
[ps2client](https://github.com/ps2dev/ps2client) shipped in `tools/ps2client`
(see the README there — the patch fixes a Nagle/delayed-ACK stall that made
file serving ~100x slower).

The console side is **always our own [ps2link](https://github.com/ps2dev/ps2link)**:
a pinned upstream plus this repo's patch, built in Docker by
[`tools/ps2link/build.ps1`](tools/ps2link/README.md) (`build.sh` on Linux) and
flashed onto the memory card once — nothing downloads a ps2link for you, and
stock ps2link is not a supported target: ours bakes in the USB keyboard/mouse
stack, and **fixes the hangs that made a network session need a console reset**
(upstream's `host:` receive loop spun forever when the PC closed the socket, its
reply parser desynced permanently on any unexpected packet, its IOP exception
handler faulted before it could report a crash, and its IOP reset waited on an
inverted condition). It also **silences the SPU2 on reset**, so a redeploy no
longer leaves the dead game's voices looping — the chip keeps its registers
across an IOP reset, which is why that used to need a separate silencer ELF
deployed after every Stop. The boot banner carries an `r<n>` revision so you can
tell which fixes a flashed card has. The one-time console setup — hardware, flashing,
`IPCONFIG.DAT`, firewall ports, what every failure message means — is
**[docs/ps2link-setup.md](docs/ps2link-setup.md)**.

## The in-tree Tyra engine

`vendor/tyra/engine` is a fork of the [Tyra engine](https://github.com/h4570/tyra) (Apache License 2.0, forked at `9273416`; license text in [`vendor/tyra/LICENSE`](vendor/tyra/LICENSE)), maintained directly in this repo — edit it and the next Build & Run picks the change up automatically. The editor's modifications over upstream (marked `Modified by TyraX` / `TyraX guard band` in the sources):

- `planes_clip_algorithm.cpp` — Cohen–Sutherland outcodes: fully-visible triangles skip the 6-plane clipper, fully-outside ones are rejected instantly.
- `stapip_clipper.cpp`, `stapip_qbuffer.cpp` — static pools instead of per-call heap allocations.
- `render_bbox.cpp` — guard-band frustum margins; only near-plane-crossing geometry goes to the EE clipper, side overflow is left to the GS scissor.
- `vcl_sml.i` (`PerformClipCheck`) — VU1 guard band: XY accepted up to 3× outside the clip volume (the GS scissor trims pixels), with an explicit w ≤ 0 test for behind-the-camera vertices.
- `audio_song.cpp` — the song player reads the WAV header (PCM 8/16-bit, mono/stereo, standard rates, arbitrary chunk layout) instead of assuming 16-bit/22050 Hz/stereo with samples at a fixed offset.
- `pad.cpp` — `Pad::setActuators()`: runtime DualShock vibration control (the on/off buzz motor + the 0–255 heavy motor), driven by the *Vibrate Pad* flow node and the `padVibrate()` script helper.

Generated games additionally enable the real per-triangle clipper (`fullClipChecks` + `Precise` culling) and correct `PlanesClipAlgorithm::clipMargin` (the upstream default pushes the near clip plane ~10 units away from the camera).

Before each build the editor refreshes its generated files: `docker-compose.yml`, `inc/terrain_config.hpp` and `inc/scene_data.hpp` are always rewritten from project data; `src/terrain_game.cpp` and `inc/terrain_game.hpp` are rewritten only while their first line still contains the `Generated by TyraX` marker — delete that line to take ownership of a file (scene objects will then stop syncing into the game code automatically).

## Dependency policy

Four rules, so that "it built last year" keeps meaning something.

**1. Pin the commit, never a branch.** Every entry in `deps.ps1` / `deps.sh`
names an exact SHA. A branch is a moving target, and because setup skips a
vendor directory whose probe file already exists, a branch pin also freezes
silently: two people who ran setup a month apart get two different imgui and
neither is told. To bump a dependency, change the SHA in **both** lists, delete
the vendor directory, re-run setup, and actually build.

**2. Mirror everything the build needs.** Each dependency also carries a
`Mirror` URL — our fork under `doctorspider42/tyrax-vendor-*`. Setup tries
upstream first and falls back to the mirror, so a deleted, renamed or
force-pushed upstream costs a slower fetch instead of a broken build. Refresh a
mirror with `gh repo sync` *before* bumping its pin, so the new SHA exists in
both places.

**3. If the license permits redistribution and the thing is small, vendor it
in-tree.** Fetching at setup time buys nothing legally — MIT, zlib, Apache-2.0
and public domain all allow redistribution outright — so it is purely an
engineering trade. Fetch only what is genuinely large, or what may not be
redistributed. `vendor/tyra/engine` is in-tree for exactly this reason.

**4. Assets are not code; verify them file-by-file.** A permissive license on a
project says nothing about the license on its models, textures or sounds, and
asset collections are commonly *mixed* — a CC0 default with a long tail of
AGPL/GPL leftovers is the normal shape of an open asset pack, not the
exception. Never conclude "the project is CC0, therefore the pack is CC0".
Anything that cannot be redistributed must be an **optional** download whose
absence disables one feature, never something the build or the editor requires.

Notices for everything currently shipped are in
[THIRD-PARTY-LICENSES.md](THIRD-PARTY-LICENSES.md).
