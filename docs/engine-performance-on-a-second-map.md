# Does the renderer work generalise? A second map says yes, except for one change

Rounds of renderer and code-generation work were driven by one scene, the Motor
District in `examples/vehicle-playground`. That is the trap the work had to
answer for: a change measured only on the scene it was written against may be
tuning for that scene rather than improving the engine. This page is the control,
and it has now returned both answers.

`examples/large-terrain` — a different map with no content in common — gains
**8.9% of its measured work and 11.4% of its render submission** from the same
engine and the same code generator, with its triangle and packet-flush counts
unchanged. That is the bulk of the work, and it generalises.

**One change did not**, and the control is the only reason anybody knows.
Imported-model batching was worth −0.46 ms on the district and **+3.20 ms, 29% of
the frame, on this map**. It has since been fixed, and the fix moved this map to
**10.789 ms — better than either the regression or turning batching off** — see
[the last two sections](#the-control-earned-its-keep-one-change-does-not-generalise).

## What the two maps do not share

| | Motor District | large-terrain |
| --- | --- | --- |
| objects | 142 | **1,181** |
| imported `.tmdl` models | 70 | **none at all** |
| the rest | roads, vehicles, buildings | 621 cones, 310 boxes, 169 cylinders |
| view measured | parked garage | fixed high vantage over the terrain |
| triangles in view | 25,650 | 10,297 |
| packet flushes | 118 | 21 |

They therefore exercise different halves of the work. The district's gain leans
on static-model triangle strips and imported-model batching; large-terrain has no
imported models, so its gain comes from terrain strips, the VU1 spot-light gate,
retained command data, the branchless frustum test and the compacted part bounds.
**Neither map can produce this result on its own**, which is the point.

## The measurement

Both arms are a fresh boot over ps2link on physical hardware, release profile,
PAL, frozen camera, 120 warm-up frames then 240 recorded. Each arm's fixture was
**regenerated by the editor that built it** — `b9894c12` for the before arm,
`c4407798` for the after — because a fixture carrying an example's committed
generated sources measures a different game (see
[the measurement traps](vu1-and-dma-cache-cost.md)). The example needed a format
migration (v23) before either editor would open it.

| metric | before | after | delta |
| --- | ---: | ---: | ---: |
| work | 12.094 | **11.023** | **−1.071 (−8.9%)** |
| render submission | 9.451 | 8.378 | −1.073 (−11.4%) |
| dispatch | 5.514 | 4.468 | −1.046 (−19%) |
| VIF1 wait | 3.904 | 2.989 | −0.915 (−23%) |
| packet construction | 0.669 | 0.465 | −0.205 (−31%) |
| bounds | 0.508 | 0.433 | −0.075 (−15%) |
| update | 2.108 | 2.112 | +0.004 |
| **triangles** | **10,297** | **10,297** | **0** |
| **packet flushes** | **21** | **21** | **0** |

The same buckets move, in the same direction, in similar proportion to the
district's (work −12.7%, submission −14%). Triangle and flush counts are
identical, so this is the same geometry drawn in the same number of submissions
for less time.

## Two things to read carefully

**The spawn pose measures nothing, and nearly fooled this page.** The first pair
of arms used the player's own start position: 2,528 triangles in 11 flushes, work
8.66 ms. It showed the same directional improvements at a third of the
magnitude, which is a much weaker claim than it looks — a light scene cannot
separate a real gain from noise. The vantage script (`zz_vantage.cpp`, archived
with the raw arms) puts the camera high over the middle of the terrain, where
this map's 1,180 objects actually are, and is driven from the script's own frame
index rather than a wall clock so two boots traverse identical content.

**The before arm still printed `VRAMSTAT` every 120 frames**, because gating that
off is itself one of the changes being measured. It is two host writes inside a
240-frame window, worth roughly 0.02 ms a frame against a 1.07 ms delta.

## Reproducing it, or doing this for another map

`tools/instrument-frame-cost.py` is the project-agnostic instrumenter this needed
— the Motor District's own version brackets that example's `updateVehicles` call
and four-pose day/night script and works on nothing else. It patches any
generated game's `loop()`, records update / submission / finish / presentation
plus the static pipeline's telemetry buckets into RAM, and writes
`bin/frame-cost.csv` once after sampling.

```bash
python tools/instrument-frame-cost.py <fixtureDir> [--warmup N] [--samples N]
```

Regenerate the fixture with the editor under test **first**, build it with
`tools/toolchain/native-build.ps1` directly (an editor `--build` regenerates the
instrumentation away), and give the fixture a frozen camera — a Player with
`walkSpeed: 0` and `lookSpeed: 0` for a ground-level pose, or a global script
setting `ctx.cameraOverride` for one the player cannot stand in.

[The raw arms, the vantage script and the measurement harness](../examples/large-terrain/authoring/engine-generality-2026-09-16/)
retain both vantages and both editors.

## What this does not establish

Two maps are two maps. Neither is a moving-camera test, neither exercises
vehicles in motion, and large-terrain's 10,297 triangles in 21 flushes is a
lighter frame than the district garage's 25,650 in 118 — a scene heavier than
either could behave differently again. And none of it says the Motor District
garage can reach 60 fps; it says the engine got faster for reasons that are not
about the district.

## The control earned its keep: one change does NOT generalise

Re-measured at the branch tip after a second day's work, this map came back
**worse** — 12.094 → 14.226 ms, with 2,015 more triangles and 12 more packet
flushes. Isolating it against the editor immediately before the imported-model
batching merge, the same engine and the same fixture recipe either side:

| | batching off | batching on | delta |
| --- | ---: | ---: | ---: |
| work | 11.021 | **14.226** | **+3.205 (+29%)** |
| render submission | 8.374 | 11.575 | +3.202 |
| dispatch | 4.539 | 8.167 | +3.628 |
| triangles | 10,297 | **12,312** | +2,015 |
| packet flushes | 21 | **33** | +12 |
| bounds | 0.363 | 0.378 | +0.015 |
| VIF1 wait | 3.008 | 2.994 | −0.015 |

Everything outside the batching path is flat, so this is that change and nothing
else. **The same feature is worth −0.46 ms on the Motor District.**

The mechanism was written down in advance, in `#269`'s own commit message, as
"the widened-bounds regression seen with district-scale material groups": a
batch's bounding box is the union of its members, so the batch passes the
frustum where its members individually would not. An 80-unit coarse cell suits
a compact garage of 142 objects; this map has 1,181 spread over 940 units, and
the same cell merges things that should have been culled separately.

**Read the two halves of this together.** With batching excluded, the second map
improves 12.094 → 11.021 — the −8.9% this page was written to report, intact.
Every other change on the branch generalises. Exactly one does not, and it took
a second map to find out, which is the entire argument for having one.

## ...and the control then FIXED it

The regression was traced to the grouping cell and removed. The cell was
`max(mapW / 4, 48)` — a fraction of the **map**, so it grew with the world and
made the cull coarser the bigger the map got. This map's 2048-unit terrain
therefore got a **512-unit** cell and merged **1,100 objects into 4 batches**,
while its cones carry `drawDistance` 60.

The cell is now bounded by the draw distance its members share, which is
already a group key and so is a length the scene states about itself. Full
mechanism, tables and the rejected alternatives:
[model-pipeline.md](model-pipeline.md), "Why the cell is bounded by the draw
distance".

Measured here the same way this page's other rows were — same fixture recipe,
same frozen vantage, each arm regenerated by the editor that built it, all
three ELFs hashed and distinct:

| per frame | batching off | batching on (before) | batching on (after) |
| --- | ---: | ---: | ---: |
| objects batched | — | 1,100 in **4** batches | 1,085 in **198** batches |
| widest cell | — | 512 | **60** |
| triangles | 10,297 | **12,392** | **10,297** |
| submitted vertices | 30,891 | 37,176 | 30,891 |
| packet flushes | 21 | **33** | **21** |
| VU1 packages | 320 | **825** | **320** |
| pixels differing from unbatched | — | **400** | **0** |

The counts come back to the unbatched numbers **exactly**, so the widened-bounds
cost on this map is now zero while 1,085 objects still merge into 198 batches
instead of being submitted one at a time. The Motor District is untouched —
`min(80, 145)` is still 80 — and its 65 objects in 48 batches, its counters and
its captures are identical either side.

**The pixel row is the part worth keeping.** The old batching was not only
slower here, it drew **400 pixels of cones the unbatched scene culls**: a batch
outlived its members' 60-unit cut-off by the spread of a 512-unit box. So the
second map did not just price this feature, it caught a visible defect in it —
which is a stronger argument for a control map than the milliseconds were.

These are counts and pixels from PCSX2, which is where this branch's rule says
they belong; **the milliseconds are the console's to measure**, and the
conversion is the same one this page's first table came from.


## And the fix, measured

Capping the batching cell at the draw distance the group shares returns this map
to the unbatched counts while 1,085 of its objects still merge:

| | before the work | batching broken | batching off | **fixed** |
| --- | ---: | ---: | ---: | ---: |
| work | 12.094 | 14.226 | 11.021 | **10.789** |
| render submission | 9.451 | 11.575 | 8.374 | **8.141** |
| dispatch | 5.514 | 8.167 | 4.539 | **4.517** |
| triangles | 10,297 | 12,312 | 10,297 | **10,297** |
| packet flushes | 21 | 33 | 21 | **21** |

**The fixed arm beats turning batching off by 0.23 ms**, so the feature now pays
on both maps rather than on one. Whole improvement for this map across the work:
**12.094 → 10.789 ms, −10.8%**.

The Motor District is unchanged by construction — its cell is `min(80, 145)` and
was already 80 — and the console confirms it: triangles and packet flushes
identical in all four poses either side of the fix.

The mechanism turned out not to be the one `#269` predicted, and that is worth
keeping. The cell was never an 80-unit constant: it is `max(mapW / 4, 48)`, a
**fraction of the map**, so the cull gets coarser the larger the world. And the
dominant cost was not the frustum widening but the **draw-distance test**, which
is applied once per batch to the nearest point of the member-centre box — this
map's cones vanish at 60 units and a 512-unit box held them drawn, an 8.5×
overrun. Capping the cell at the group's own `drawDistance` works because that
value is *already* a grouping key, so every member of a batch agrees about it:
it is a length the scene states about itself rather than a constant to re-tune.

One finding nobody was looking for: the broken batching did not merely cost time
here, it **drew 400 pixels of cones the unbatched scene culls**. Only a third,
batching-off arm could show that — two arms can say something moved, not which
one is right.
