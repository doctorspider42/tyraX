# Pool2 EE lazy-source diagnostic design review

Status: source-only design accepted for separate private native preparation, with the target gates and limitations below. No source-routing or lifetime blocker found against the pinned current wild-pool2-ee-physical-v2 engine. This review does not compile/run the probe, observe actual VU/GS output or establish physical benefit. All declared workshop input/output hashes were independently rehashed; source-review.json records them. No shared mirror was read or changed for this review.

The probe uses persistent aligned inline arrays, a persistent typed u32 colorGeneration and a persistent View. All live source pointers, readiness storage and metadata survive render, frame submission and synchronizeFrame. There is no temporary vector or transient stack coefficient storage handed to DMA. The engine captures member coefficients into a qbuffer-owned Slice and packetizes them before the post-sync probe can change the next epoch. The normal frame lifecycle is retained; snapshots and validation happen after existing synchronizeFrame rather than inserting a new diagnostic wait. Source review cannot prove native DMA/cache ownership or the completion behavior of a particular executable; bind those gates to the final fixture and symbols.

Both arms author identical coefficient bits from Color values, exact alpha128, fixed source positions/ST and one explicit generation per render. Arm0 binds eager colors and a View with null expanded/ready fields. Arm1 binds poisoned lazy backing and zero readiness. Current generation is assigned before rendering; capturePoolTable's current-generation/count/pointer checks can therefore admit it. materializeRange's typed word size/aligned Color assumptions match this source. Three iterations cannot wrap the counter. Geometry contentVersion/bbox remain fixed because only coefficient values change.

The disabled oracle remains disabled before every render; observePoolTable is a no-op when collectCounters=false, and the probe compares before/after poolTableCounter bytes. The ordinary candidate readyCount0 gate rejects any actual fallback rather than silently accepting a materialized source. Together with independently decoded output epoch it can establish that the observed table output was produced without expanded-color materialization in this fixed case. A zero readyCount alone can also result from an entirely rejected/cached/unexecuted draw, so it must never replace the output gate.

The lazy snapshot checks are logically correct for the live source extent: every readiness word equal to this epoch must have current baseline color bytes; every other readiness word and Color element must remain identical to their immediately prior snapshot. Older fallback generations are correctly permitted to retain older bytes outside the current consumed range. This proves invariance over [0,caseId), not over all allocated 192 elements in the 96-element case: snapshots cover all192, but comparisons only cover caseId. Do not claim guards/out-of-bounds-write coverage beyond the live source extent without extending that check separately.

Clip mode's finite +/-1000 triangles at z0, camera z-20, fullClipChecks/Precise, and VU1Clipping=false are a reasonable deliberate EE side-plane crossing input. Every triangle spans the viewport; no near singularity is introduced by source values. The current EE copy/clip consumers materialize before reading source colors. Candidate readyCount>0 proves at least one fallback read/materialization occurred, not that EE clipping actually ran, the exact classification/copy subroute, that all expected source ranges were consumed, or that output topology matches baseline. Because counters stay disabled, target route proof must come from independent retained debugger/actual-output evidence. Paired clipped-output/raster equality remains mandatory for any clipped-correctness claim.

Per-iteration red values 31/32/33 and 95/94/93 create source epochs that differ between repetitions and arm-pair inputs remain equal. The final captured RGBA should be independently checked against the requested epoch rather than only compared between arms: two stale equal banks could otherwise pass. Epoch2/3 matching distinguishes old versus current content for the observed final output. It still does not prove fresh execution on every preceding warm iteration, all unobserved packages, or GS raster/consumption equality. B192 overwrites the first75 package in the two final VU banks; the established final-bank decoder only covers the remaining75 and42, not all192 source vertices.

Every epoch invalidates the retained/baked key by poolGeneration (and baked color contentVersion). The fixture tests changed-color cache invalidation and actual current output; it does not test stable-generation warm cache HIT reuse. No source freshness metadata should say universal warm reuse was qualified by these changing epochs.

README helper adaptations are necessary and correctly scoped. finish-probe must accept zero old counter fields, require one matching SOURCE row per completed frame, validate generations1..N and the chosen inside/clip readiness predicates, and reject missing/extra/mixed-case rows. verify-capture must bind the actual new source count/manifest and exact final source/ELF/READY/halt evidence. Ordinary decoder must validate final epoch packed RGBA and preserve inside package/marker checks. Clip requires its own topology-aware decoder and cannot reuse the inside-only package assumptions. capture-ready must select the new helper paths, preserve SaveState CRC/schema/paused memory proof, and use exact owned-instance stop controls. None of these parser/decoder changes are implemented or verified by the source workshop itself.

No target result or physical speed benefit is claimed. Native source/ELF/ABI pins, actual no-oracle inside output, actual fallback route and clipped output, and the corresponding final-epoch source/ready evidence remain the next separate gates. getPrint remains outside the accepted diagnostic scope.
