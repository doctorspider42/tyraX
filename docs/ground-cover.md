# Ground cover

Ground cover is grass (or any other card-shaped plant) that grows by itself
wherever a terrain material is painted. You switch it on for the base terrain
or for a painted layer and set how dense it is. The game then draws it in a
ring around the camera, and it thins out towards the edge of the ring card by
card, so there is no visible line where the grass ends.

Nothing is placed by hand and nothing is stored per card. Paint the layer and
the grass follows the paint.

## Using it

*Terrain painting* window, section **Ground cover**:

- **On the base / On <layer>**: switches cover on for that surface. A cover
  grows wherever its surface shows, weighted the way the terrain draws it: a
  layer painted at 50% grows half the cards, and a layer painted over the base
  takes the base's cards away.
- **Card**: the texture. The default *Built-in grass tuft* is generated by the
  editor (`res/materials/vegetation/grass-tuft.png` + `.mtl`, rewritten when
  missing). Any `.mtl` with a `map_Kd` works. Alpha 0 is cut away (the GS
  alpha test, no blending), so give a custom card a hard alpha edge and leave
  the top and bottom pixel rows clear.
- **Density**: cards per square metre where the surface fully shows (one card
  is one quad, about a dozen blades on the built-in tuft).
- **Width / Height / Size spread / Tint**: card size in metres, random size
  variation, a colour that multiplies the texture.
- **Wind**: how far the card tops sway in the gusts, as a fraction of the
  card height (0 = still). Gusts roll across the field as a wave, so
  neighbouring cards move together. Computed on VU1, so it costs the EE
  nothing.
- **Draw distance** (per scene): how far from the camera cards are drawn, in
  metres. The outer quarter of it is where the cards thin out.

Under the sliders, the panel shows the worst case: how many card slots the
ring holds and how much RAM it takes.

The viewport shows the same cards the console draws, grown around the
editor camera. The one difference is roads: the game also removes cards that
stand on a road strip, and the preview does not.

## How it works

The world is divided into 2-metre tiles. Each tile seeds its cards from a hash
of its coordinates, so a tile grows the same cards every time it comes back
into range. For every card the game picks a position in the tile, a size, a
brightness, a mirror flag and a random **thinning threshold**. The card is kept
only if a random number falls below the composited weight of its surface at
that point, and it stands on the terrain triangle the renderer actually draws.

Only a square ring of tiles around the camera is in memory: a toroidal slot
table, one tile per slot. When the camera enters a new tile, the tiles that
came into range are generated, a few per frame. The visible cards are then
packed into one draw array per cover, grouped in blocks of 4 x 4 tiles. Each
block is one bag of the engine's **grass program** with its own world box. In
a frame where the camera stays inside its tile, the EE does nothing for the
grass except one frustum test per block and the submits of the blocks in
view.

### The grass program

`stapip_billboard_g_vu1.vclpp` is a VU1 microprogram written for the cards,
selected by `StaPipBillboardBag::grass`:

- **One qword per card goes in**: `(x, ground y, z, s)`. `s` is the card's
  size, the fade's grow-in included, and its sign mirrors the texture. Size,
  tint and wind are per bag.
- VU1 builds the upright quad from the camera's flattened right vector and
  world up, sways its top along the wind by a parabolic sine
  `4g(1 - |g|)` of a travelling wave (no EFU), and culls the whole card if
  any corner leaves the raster window, like the particle program does.
- **4 vertices come out** as one triangle strip, ST + XYZF2 only. The first
  two vertices of each card carry ADC, which breaks the strip between cards.
  The colour and Q = 1 go out once per package as an RGBAQ write before the
  prim tag, so texturing is affine. That is fine for upright cards.

A card used to cost 3 input qwords and 18 output qwords (the particle
program: 6 vertices x ST, RGBAQ, XYZF2). Now it costs 1 in and 8 out, so a
VU1 package holds about 50 cards instead of 21, and the EE's per-package
cost (packet build, DMA submit) drops with the package count. The EE also
writes one qword per card when it packs instead of three.

The program joins the billboard family in the VU1 program set only when a
game asks (`StaPipCore::setGrassProgram(true)`, called by the first scene
with cover). It is about 110 words, and the fixture's set went from 1918 to
2028 of 2042. A project whose set is already bigger gets the billboard family,
grass included, **swapped on demand** instead of resident. The boot log says
which (`billboards resident (with ground cover), N of 2042 words`) and
`Program_swaps_count` in `--profile-frame` counts the swaps.

**The edge.** Each card fades by its own distance from the camera: past 75% of
the draw distance a card is drawn only while the fade is above its threshold,
and it grows out of the ground as the fade passes it. The ring therefore ends
in a ragged band a quarter of the distance wide. An earlier version faded
whole tiles, and the 2 m steps showed.

## Cost

Measured in PCSX2 with `--profile-frame` on a flat 100 x 100 m scene, base
cover, 16 m draw distance, camera at standing height looking slightly down.
The profile is synchronized: EE, VU1 and GS are counted one after another, so
a real frame overlaps them.

| Setup | Ground cover | VU1 packages |
|---|---|---|
| 3 / m², every ring slot sent to VU1 (first cut, particle program) | 1.56 ms | ~175 |
| 3 / m², packed visible cards in 4 x 4-tile blocks (particle program) | 0.47 ms | ~50 |
| 10 / m², packed, particle program | 1.36 ms | ~140 |
| 10 / m², packed, **grass program** | 0.51 ms | ~60 |

The cost follows the number of cards in view: each VU1 package (about 50
cards with the grass program) costs the EE a packet build and a DMA submit.
To make grass look denser for free, use a card with more blades. Lowering the
draw distance cuts the cost with the square of the distance.

Not measured on a real PS2 yet.

## Limits

- Terrain only (heightmap scenes). Grass on meshes is not supported.
- The cards are not lit. The tint is all the colour there is (one RGBAQ per
  package), so at night the grass does not get darker with the ground.
- No bending around the player yet.
- Projects whose `terrain_game.hpp` is user-owned do not get the new
  `TerrainGame` members and will not compile with a cover until they add the
  three declarations (`buildGroundCover`, `updateGroundCover`,
  `renderGroundCover`).

## Where it lives

- Model: `GroundCover` on `TerrainLayer::cover` and
  `SceneData::terrainBaseCover`, plus `SceneData::groundCoverDistance`
  (format v130).
- Host: `src/groundcover.cpp` (built-in tuft, cover list, the card generator
  the viewport uses), `Viewport::drawGroundCover` (draws the program's sway
  with the same wave).
- Engine: `StaPipBillboardBag::grass` + its per-bag fields, the
  `StaPipBillboardGrass` program (`programs/billboard/stapip_billboard_g_*`),
  `StaPipQBufferRenderer::setGrassProgram`.
- Codegen: `GROUND_COVER_*` in `inc/texture_data.gen.hpp`, emitted only when a
  scene has a cover. The runtime (`buildGroundCover` / `updateGroundCover` /
  `renderGroundCover` in the scene shard) compiles to empty bodies without
  `GROUND_COVER_ON`.
- The generator runs twice: `groundcover::tileCards` on the host and the
  `fill` step of `updateGroundCover` in the game. Change the seed, the order of
  the random draws or a formula in both.
