# Critical path and VU offload investigation

The final-VIF experiment is closed without promotion. This follow-up measures why the unchanged-quality daytime drive still misses refreshes, before proposing another VU0/VU1 job.

`tools/tyrax2-critical-path-fixture.py OUT QUALIFIED_CURRENT_TERRAIN_FIXTURE` creates a private six-trip observer Off/On/Off/On/Off/On comparison. It uses the current common terrain builder in the inherited qualified drive/residency/renderer fixture, not a pristine full-current-production build. Offline terrain is disabled, its tables are never loaded, and the final-VIF experiment is absent. Direct world cells, paint, hybrid wheels and event-driven idle audio remain common to all roles. No draw, capture cadence, material or raster setting changes.

The observer has bounded static storage and exports outside recording. It separates inclusive game/scene/reflection/terrain/road/object/wheel/particle/Core intervals from VIF waits, GS FINISH waits, pending presentation, vsync and flip. Existing render-cost barriers stay disarmed. Boundary timestamps connect prior native launch, current preparation, pending-job completion and presentation; raw VIF/GIF/CHCR/GS snapshots preserve the observed state. They are not utilization counters. Parent and child scopes overlap and must not be added; recursive wait aggregation is inclusive too.

The native source/ELF gate and ordinary six-trip verifier retain exact held rasters, reconstructed endpoints, poses, capture workload, SDK body audits and source-reader lifetime gates. `--quality-trial` is forbidden. The observer has its own same-ELF price; an expensive probe cannot be treated as an unobserved deadline failure. Physical present records decide missed refreshes, with the pending N−1 versus preparation N relationship preserved. PCSX2 runs only in the private invisible WSL/Xvfb session.

VU0 already executes macro-mode vector/matrix/bounds/skinning operations and supports a micro ray tracer. A new asynchronous microjob needs explicit ownership and an actual COP2-free EE interval. VU1 already transforms/clips the submitted geometry, and the fixed world's direct packets bypass much EE interpretation. A new program must target the positively activated consumer, fit the actual resident instruction/data budgets, preserve exact output and win a physical both-order comparison. Source loop counts, DMA waits and historical garage timings do not establish this drive's bottleneck.

## Completed physical diagnosis

The [sealed evidence](tyrax2-critical-path-2026-10-20.json) binds 506 native source files, ELF, platform logs, all input assets, raw timing/presentation CSVs and both completed readers. All six emulator and physical trips pass 54 exact held rasters, six exact endpoints, 3942 equal pose rows, live capture/paint work, SDK bodies and owner delivery. The observer exports 537 rows in each On trip and no rows in Off. Each measured frame has exactly one native launch, and every subsequent row links the actual previous launch/sequence to the presented job. Owned processes stopped before final verification; the console remains powered.

Actual physical late intervals are 8/7/7 in Off and 7/7/7 in On, per 537 moving loops. All seven recurring sites appear in every observed and unobserved trip. The extra Off-only site at1416 occurs in the first trip and is not assigned an observed cause. On-minus-Off mean non-pacing contrasts are −0.005519/+0.002238 ms in the two orders; there is no resolved universal positive observer fee and no optimization claim. Scope storage is 127,440 bytes common to both roles. The extra timer branches/common code layout are not priced against a pristine executable.

## VU power-move assessment

The current selected ring/fold/paint set is genuinely nearly full: nine unique images alias12 logical programs, using2034 instruction words plus a six-word FINISH helper in2048. Only **eight instruction words** remain. `tyrax2-vu-residency-audit.py` checks native source selection, linked symbol lengths, the actual resident runtime witness and the symbol-ELF digest. This budget describes the private tested image set, not every production material configuration. A new large program cannot simply be appended.

**VU1 candidate: transform strip vertices once before triangle clipping.** The actual selected `stapip_clip_tc_vu1_ring_hybrid_fold_paint.vclpp` loads and multiplies all three corners in every `triLoop`. A native strip of72 inputs represents70 triangles and therefore repeats210 corner transforms before clipping, though only72 input positions exist. A per-input preparation stage in VU1 memory can eliminate this repetition while retaining the same ordered triangles, parity, six-plane clipping, attributes and output rings. It changes neither mesh density nor reflection cadence.

This is a source-backed architecture candidate, **not an implemented or priced shader**. Begin with the explicitly unlit native-strip route. The current spot/env/directional paths can need original positions/attributes; indiscriminately overwriting their input would be incorrect. Keep the original MVP operation order and actual target numerical behavior; host/emulator agreement alone does not prove PS2 equivalence. Preserve both XTOP halves, current input ownership, scratch/output lifetimes and GS state. Eight free words force consolidation/replacement of an existing image or a separately qualified class budget, not adding a job and silently evicting billboards/materials. Packet/topology/native numerical, actual VU memory and exact raster oracles must precede same-ELF physical pricing. The transform count reduction is not a promised frame-time percentage, and this proposal does not fix the three EE-preparation sites by itself.

**VU0 is not the first intervention.** The activated EE routes include generic Core/road/object interpretation and a rare terrain rebuild burst, not a measured large, independent vector job. Existing macro-mode COP2 use prevents treating VU0 as an idle worker. A viable offload first needs a measured arithmetic batch, explicit macro/micro ownership, bounded input/output and an EE overlap interval that does not touch COP2. Moving pointer dispatch, lifetime validation or waiting to VU0 would not address the observed consumer cases. Do not repeat rejected same-call clip-plane reuse, blanket cache work or per-frame transcoding on the strength of inclusive Core time.

The immediate engineering priority is therefore the VU1 native-strip consumer redesign **plus a separately narrowed EE preparation path**. Stable60 is not proved, no image-quality trade was accepted and no production defaults changed. Full current-production, night/variable-dt coverage and actual shader implementation/pricing remain open.
