# Menu stylesheets (`.menustyle`)

A menu's look is a **stylesheet**, not code and not a pile of fields. The files
live in `menu-styles/` at the project root; a menu picks one by name (the
`"style"` key in the `.tyra` manifest), and an empty name means the built-in
**Classic** look.

Everything in a sheet is **baked into sprites when the game is built**. The
PlayStation 2 has no font, no layout engine and no CSS - the editor rasterizes
the whole panel on the PC and the console draws the result. That single fact
decides what is possible, so read the cost table below before promising
anything.

```css
@style "Neon"                    /* the name the editor shows */

:root {
  --accent: #78d1ff;             /* variables, used as var(--accent) */
  --ink:    #eaf6ff;
}

panel {
  width: 512px;
  quant: 8bit;
  background: linear-gradient(180deg, rgba(6,12,26,0.95), rgba(10,20,42,0.8));
  border: 1px solid var(--accent);
  border-radius: 8px;
  padding: 14px 0 0 0;
  shadow: 0px 3px 10px rgba(0,0,0,0.65);
}

title  { color: var(--accent); letter-spacing: 3px; text-transform: uppercase;
         rule-below: 1px solid rgba(120,209,255,0.35); }
row    { color: var(--ink); padding: 3px 0 8px 44px; }
row:selected  { color: #ffffff; translate-x: 6px;
                background: linear-gradient(0deg, rgba(120,209,255,0.42), transparent); }
row:disabled  { color: #4d5a6b; }
row.header    { color: #7d90a8; letter-spacing: 2px; selectable: no; }
list   { rows-visible: 8; }
value  { color: var(--accent); display: bar; bar-size: 90px 8px; }
hint   { content: "{{cross}} OK   {{triangle}} BACK"; color: #7d90a8; }
marker { marker: none; }

@transition open   { 180ms ease-out; fade; translate-y 10px; }
@animate    panel  { sheen 3.4s 52px rgba(255,255,255,0.18); }

menu#pause { panel { width: 256px; } }   /* this menu only */
```

## What you can select

**Elements**: `panel`, `title`, `list`, `row`, `value`, `description`, `hint`,
`marker` (the selection caret), `image`.

**States** (rows only): `row:selected`, `row:disabled`. A state rule ADDS to the
normal one - it does not restate it.

**Classes**: `row.myname` styles the rows whose *Class* field says `myname`
(set per row in the Menu Editor's Content tab). Free text; a class nothing
defines simply styles like any other row.

**Menu scope**: `menu#pause { ... }` applies only to the menu called `pause`.

**Cascade**: element < class < state, and a menu-scoped rule beats a general
one. The menu's OWN fields - accent colour, title size, row size, panel width,
font - are the base everything overrides, so a sheet only has to state what
differs.

## Properties

| Group | Properties |
|---|---|
| Box | `width` `height` `padding` `margin` (+ `-top/-right/-bottom/-left`) `background` `background-image` `background-anim` `slice` `border` `border-color` `border-radius` `shadow` `opacity` `gap` `quant` |
| Text | `font` `font-size` `color` `align` `letter-spacing` `text-transform` `text-shadow` `text-outline` `rule-below` `content` |
| Rows / list | `translate-x` `icon-size` `marker` `marker-side` `selectable` `rows-visible` `scroll-marker` |
| Values | `display` (`text` \| `bar`) `bar-size` `bar-fill` `bar-track` |
| Description | `height` `area` (`below` \| `right`) `wrap` |

Values look like CSS: `12px`, `#78d1ff`, `rgba(6,12,26,0.9)`, `transparent`,
`linear-gradient(180deg, <from>, <to>)`, `url(res/hud/frame.png) 9-slice 24px`,
`var(--name)`, and the keywords listed above. `width: screen` on `panel` makes a
full-width panel. Text can carry `{{cross}}`-style button icons.

Anything the parser does not recognise is reported with its line number in the
editor's *Menu Editor > Stylesheet* tab - it never silently does nothing.

## What each thing costs

This is the part to reason about before proposing a design.

| Layer | What it covers | Console cost |
|---|---|---|
| **Baked pixels** | gradients, frames, rounded corners, shadows, outlines, letter spacing, per-element fonts and colours | **nothing** - texture bytes only |
| **Baked state cells** | `row:selected`, `row:disabled`, per-row descriptions, option labels and bars | one extra sprite per visible cell |
| **Sprite properties** | slide, fade, scroll, caret easing, pulse, sheen | a few floats per frame |

So a heavily decorated panel is free, while "every row gets its own selected
look" costs one baked cell per row. The Menu Editor prints the textures, the
KB and the **% of GS texture VRAM** for the menu you are editing; if a change
matters, ask the user to read that line back. `quant: 8bit` (or `4bit`) on the
panel is the lever that makes a big menu affordable - menu art palettizes almost
losslessly.

Limits that are hard, not stylistic: a texture axis is a power of two, 512 max;
a panel taller than 512 px is clipped (the editor says so); a menu holds 32 rows
and needs `list { rows-visible: N }` to scroll past what fits.

## Motion

`@transition` reacts to something, `@animate` loops:

```css
@transition open   { 180ms ease-out; fade; translate-y 10px; }
@transition close  { 140ms ease-in; fade; }
@transition cursor { 110ms ease-out; }   /* caret moving between rows */
@transition scroll { 120ms ease-out; }   /* a long list settling */
@transition value  { 180ms; }            /* the changed value flashes */

@animate selected { pulse 1.8s 0.22; }                        /* highlight breathes */
@animate marker   { bob 0.9s 3px; }                           /* caret drifts */
@animate panel    { sheen 3.4s 52px rgba(255,255,255,0.18); } /* light sweeps across */
```

**A baked gradient cannot move.** What can move is a texture's sampling window,
so an animated background is a layer of its own:

```css
panel { background-anim: url(res/hud/stars.png) scroll 12px/s -4px/s; }
panel { background-anim: url(res/hud/flame.png) frames 8 1.2s; }
```

`scroll` tiles the image and slides it; `frames` steps through a vertical frame
strip. Either way it is one sprite and one texture, drawn UNDER everything the
panel bakes - so the panel's own background needs some transparency or the layer
will not show.

## Things to get right

- **A full-width `row:selected` plate usually wants `marker: none`.** Otherwise
  the built-in caret draws on top of the plate.
- **The caret** is `res/hud/save-cursor.png` (16x16, shared with the save menu),
  or a sheet's own `marker { marker: url(res/hud/caret.png); }`. `translate-x`
  moves it.
- **A sheet installed into this project is a COPY** of the built-in it came
  from. It does not pick up later changes to that built-in.
- **Menus scale themselves to the display mode.** They are authored in a logical
  512x448 space; in 480p the framebuffer is 448x448 and in 1080i 448x540, and
  the runtime rescales so the panel keeps its physical size. Do not "fix" a
  1080i complaint by changing sizes - check the Menu Editor's *Preview in* list
  first, which shows the panel in each supported mode.
- **Widescreen is handled too, and must not be handled twice.** 16:9 on the PS2
  is anamorphic - the same framebuffer stretched by the TV - and the runtime
  cancels that stretch for menu panels, so a panel keeps its authored
  proportions on 4:3 and 16:9 alike. There is no 16:9 sheet and there must not
  be one: the player can flip the aspect from the DISPLAY menu while the game
  runs. If a panel looks too narrow in 16:9, it is covering the same physical
  width as before on a wider screen - move or widen it, do not stretch it. The
  Menu Editor's *Aspect* control shows both cases without touching the project.
- **Row content is not style.** A row's label, action, class, icon, description
  and "enabled when" save value live in the `.tyra` (Menu Editor > Content), not
  in the sheet. Changing what a row DOES is a project edit, not a style edit.

## What is deliberately impossible

Say so rather than working around it:

- no runtime layout or text reflow - a baked string is a build-time snapshot
  (the in-game key-rebind row is the one exception; it draws from a glyph atlas)
- `px` only - no `%`, no `em`
- shadows, outlines and gradients are baked, so they cannot follow motion
- the layer order is fixed: dim, chrome, rows, values, description, overlay,
  caret
- motion is sprite position / tint / size / texel offset only
- no media queries, no functions besides `var()` and the colour/gradient forms
- rows cannot animate individually (they live inside one panel texture), so
  "stagger the rows in one by one" is not available

## Editing a sheet

Two equivalent doors, and they cannot disagree - the widgets and the text are
the same AST:

- **Tools > Menu Editor > Style** - a widget per property, grouped by element,
  with the states and the motion. Each row has an override checkbox: off means
  "the sheet says nothing here", on means it owns the value.
- **The `.menustyle` file** - edit it directly (the Stylesheet tab, or *Open in
  VS Code*), then *Reload from disk*.

The **Menu Preview** window (and the *Menu Designer* layout) shows the real
baked panel, plays the motion, and lets the simulated cursor walk the rows -
including the display mode the game will run in. When you change a sheet, ask
the user to look at that rather than guessing.

To apply a change without the editor: rebake with

```
{TYRAX_EXE} --refresh-gen <projectDir>
```

which writes `res/menus/*.png` (the panel, the row-state cells, the value strip,
the scrolling strip, the description atlas) - then build as usual.
