# Flow graphs, input actions, player, World Facts, navigation

Read when you add/change a flow-graph node or pin kind, touch `flowgraph.hpp`/`flowgraph_ui.cpp`/`flowGraphScript`, read a button in generated code, change player movement or two-player, World Facts, or AI navigation.

## Files

- `flowgraph.hpp` (~2.75k): `FlowNode`, `FlowLink` (exec / object-id / position / bool / text / number link kinds; `toPin` = which exec input fires; `fromPin` = which exec output), `FlowGraph`, the built-in `flowNodeTypes()` registry, the custom-node registry (`CustomFlowNode`, `customFlowNodes()`), `reverbPresets()`. Graphs are per object, stored in its `objects/<id>.json`.
- `flowgraph_ui.cpp` (~2.3k): the imnodes editor (add menu, pins, links, params, debugger overlay). **`flowNodeDoc()` is the ONE tooltip renderer** (title, `desc`, a line per parameter and per exec pin) for both add-menu and node hover (the `procNodeDoc` precedent). **`paramTip()` must be called AFTER every `IsItem*` query on its widget** (a tooltip is a window; "last item" is context-global; a tip before `IsItemDeactivatedAfterEdit()` silently stops the edit saving). A drawn param tip suppresses the node tooltip that frame (`paramTipShown`). The ImNodes style is scaled by hand (see editor-ui-and-conventions.md, zoom).
- `flownode.cpp`: custom `.flownode` loader (codegen-and-generated-files.md).
- Codegen: `flowGraphScript()` (templates.cpp) compiles graphs to `src/gen/flow_graph.gen.cpp` - one script class per object graph; object references resolve to indices at codegen; bool logic folds into inline C++ expressions.

## Adding a built-in node

1. Node kind in flowgraph.hpp (designated-initializer entry). **`.category`** is the add-menu submenu; the list is derived (`flowNodeCategories()`), so a new category is just a string. `Procedural` holds nodes that CREATE content at runtime (Spawn/Despawn Prefab, Generate Volume).
2. **`.desc` is mandatory, and a tip on every parameter** (`.numTips[i]`, `.strTip`, `.str2Tip`, `.execInTips[i]` for multi-exec nodes). They feed the add-menu tooltip, node hover AND the AI generator's catalog (`nodeCatalogLine` in aigen.cpp). `.desc` = what the NODE does and why you'd reach for it; a tip = what ONE knob does (PROGRESS 247 fixed 186 entries that mixed them). A trap about one parameter goes in its tip. Never write raw slot names (`num[0]`, `str`) in prose - use the widget label (`flowStrLabel`/`numLabels` are the source).
3. Node UI in flowgraph_ui.cpp (usually automatic from the registry).
4. Codegen in `flowGraphScript()` / `actionCode`.
5. Decide Live Logic support (devkit-and-live-channels.md): the opcode in `livelogic.hpp`, body in `liveLogicOpBodies()`, mapping in livelogic.cpp's `actionMap`/`triggerMap`; otherwise `capability()` reports it unsupported.

Parameter shapes:
- **A numeric parameter that is really a CHOICE** declares `.numChoices[i]` (`'|'`-separated labels in value order) -> dropdown; the stored value stays `num[]` (codegen/links/projects untouched). Prefer it to label-string heuristics in flowgraph_ui.cpp (`"Loop"`, `"Channel"`, `"Times"`), which a new node cannot join; a declared choice wins over them.
- **Number plane** (`FlowLinkNum`, `numIn`/`numOut`): a wired number REPLACES the target's `num[0]` (mirrors `posIn` over X/Y/Z). Codegen resolves it to a self-contained float expression (`numExprImpl`/`numOperand`), no runtime slot. `flowNumFolds()` is the single predicate (editor link pruning AND codegen) and reads two DECLARED flags: `numFold` (n-ary: Add, Min, Modulo) and `numInExtra` (the wire is its own operand, `num[0]` a separate param: Clamp, Number At Least). Inference (`pure && numIn && numOut`) was wrong for unary Sine. A new number consumer reads `numOperand(n)`, not `n.num[0]`; **Live Logic cannot patch any graph with a number link** (IR carries num[] as constants).
- **Planes feed each other** (Get X reads a position, With X writes one): `posExprImpl` and `numExprImpl` recurse through the forward-declared `numInputVis`/`numOperandVis`, which take the VISITED PATH (a fresh path at the boundary recurses until stack overflow on a cross-plane cycle); `numExprImpl` must drop its OWN id before calling `posExprImpl` or the position walk skips its own input. Check with `--refresh-gen` on a deliberate pos->num->pos cycle. A position is three independent expressions, so long Vector chains re-emit per component per consumer (`PosRotateY` folds `sinf`/`cosf` at codegen for a constant angle).
- **An int consumer** must round (the plane is float; `flowInt` is not), and if it names variables join BOTH collect lists (`collectFlowVars` in templates.cpp and the identical walk in livelogic.cpp) - a variable named only by a getter still takes an index slot; a missing entry shifts every later index.
- **Branching nodes** (`Flow` category: Branch, Sequence, Gate, Switch Number, Timer, Tween, For Loop): set `execOutCount` + `execOutLabels` and emit each branch. Link source pin = `FlowLink::fromPin` (`"fpin": N`, omitted at 0); output 0 keeps pin slot 1, outputs 1..7 use slots 18..24 (`kFlowMaxExecOut` = 8). **`flowExecOutCount(t)` is the one answer** (editor pins, both link-validity checks - editor and aigen.cpp - and codegen). In `actionCode`, `branch(outPin, pad)` returns the output's chain as inline C++; each branch walks with its OWN COPY of the visited path (two outputs may reach one action = it runs twice; a link back into the path is still a cycle). Per-frame state (Timer, Tween, Cooldown) is declared via `addMember` in the per-node state pass and ticked in the `update()` prologue like Delay - never straight into `members` (the time machine cannot see it). Live Logic rejects graphs with `flowExecOutCount > 1`; livelogic.cpp's exec walk filters `fromPin != 0`.
- **Several triggers on one node**: `execInCount` + `execInLabels`; switch on `pin` in `actionCode(n, pad, pin, visited)`. Link target pin = `FlowLink::toPin` (`"pin": N`, omitted at 0); ids from `flowExecInPin` (slot 2 first, spare 10..15; `kFlowMaxExecIn` = 7). Do NOT add Show*/Hide* pairs (merged into Set Object Visible / Set HUD Visible / Set Text Visible / Set Layer Loaded / Animation). The merge only fits when both pins share the param: Play/Stop Music and Play/Stop Sequence stayed separate (their Stop is global).
- **Retiring a node type deletes every graph using it** (project-model-and-serialization.md).
- **A flow node cannot call the game.** A graph writes only into `ScriptContext`; a parameter whose meaning is known only at RUNTIME travels as a SENTINEL that `TerrainGame` resolves (Commit Checkpoint: `SAVE_COMMIT_AUTOSAVE`/`SAVE_COMMIT_NEXT`, resolved by `resolveCommitSlot`; sentinels must dodge the field's idle value - `commitCheckpoint == -1` already meant "nothing"). Emitting a `TerrainGame` method call from `flow_graph.gen.cpp` does not compile.
- A node that moves something EVERY FRAME must not re-dirty an object per frame: write a RATE onto the RuntimeObject and integrate in a loop pass on the matrix path (`updateSpinners`, the Spin Object node, PROGRESS 222; runtime-rendering-and-meshes.md).

## Custom nodes and runtime outputs

- Project-specific behavior -> a custom node (`flow-nodes/*.flownode`, no C++ change). Custom nodes plug into `flowNodeType()` lookup, the add menu via `flowAllNodeTypes()`, and a `flowCustomNode()` branch in `actionCode()`. A `call = fn` node runs a user function in `inc/scripts/flow_nodes.hpp` via `FlowNodeIO` with any pins; its **object output is a runtime value**, so `resolveTarget()` returns a C++ int EXPRESSION (literal index for built-ins, `objOut<id>` for a custom output) and built-in object actions fed one are bounds-guarded by the wrapper `actionCode()` emits (`if (<dyn> >= 0 && <dyn> < ctx.objectCount) { ... }`).
- The built-in **Raycast** uses the same runtime-latch machinery: every `flowCustomNode(...)` check on that path also accepts `type == "Raycast"`; a new built-in with runtime outputs extends those spots.
- **AI nodes** (Patrol Waypoints / Chase Player / Flee / Stop AI / On Player Seen) compile to calls into generated `navigation.gen.cpp`; a new AI node usually needs a `nav*` entry point there + an `actionCode` branch. Anything changing walkability updates `navmesh::bake` (no game twin; the game reads the baked bitmap).

## Navigation (`navmesh.cpp/.hpp` ~175+50, docs/navigation-ai.md)

Host-only bake: `bake(Project, SceneData)` rasterizes a walkable-cell grid (terrain slope on the game's bilinear heightmap + `collidePlayer`-box-mode blockers inflated by agent radius; capped 128x128; empty without terrain). Used by codegen (`navDataHeader` -> `inc/nav_data.gen.hpp`, gated on AI nodes existing) and the viewport overlay (`App::updateNavOverlay`, signature-cached). `src/gen/navigation.gen.cpp` runs A* on the EE and ticks all agents (one state per object). `blocksNavigation` is one of the marker skip lists (scene-objects-and-gameplay.md).

## Input actions (docs/input-bindings.md)

- `input.hpp` (~270, header-only): `InputAction` (name + label + `Role` + rebindable), `InputBinding` (pad name / USB HID key / mouse button - all may fire one action), `InputPreset`, `InputMap` (`Project::input`, `Section::Input`). Shared tables: `kPadButtonNames` (Tyra::PadButtons order - the index codegen stores and the Remote Pad mask uses), `inputKeyNames()`, and **`inputCodes()`** - the dense rebind code space (0 = "the preset's binding") stored in players' memory-card saves, so **append-only**; `INPUT_CODES` in the game is its twin. `project::ensureInputActions` seeds/backfills built-in roles with the bindings formerly hardcoded in controls.hpp.
- **Never emit `pad.getClicked().<Button>` for gameplay.** Read named actions: `inputPressed(pad, IA_ROLE_JUMP)` / `inputClicked(...)` from `inc/input_map.gen.hpp`, defined in `src/gen/input_map.gen.cpp` (`inputMapHeader`/`inputMapSource`). A new built-in behavior with its own button: `InputAction::Role` (input.hpp) -> a `kSeeds` entry in `project::ensureInputActions` -> a role slot in `kRoles` of `inputMapHeader` (emits `IA_ROLE_*`, -1 when absent) -> the read site.
- Runtime layers: preset -> player override (an `inputCodes()` index in a save value written by a `MenuEntry::RebindKey` row, applied by `TerrainGame::applyInputBindings`) -> a USER-OWNED `controls.hpp`'s `BTN_*`/`KEY_*` (wins only when it disagrees with the default preset). USB keyboard/mouse folding into `Pad::injectVirtual` is table-driven (`inputApplyKeyboardMouse`), so keys rebind too. Raw `OnButton` stays raw; `OnAction` is the configurable one.
- Rebind rows are deliberately **pad-only** (`inputCapture` ignores keyboard/mouse, `inputBindLabel` omits them; an override replaces only the action's `pad` slot). Lifting that touches all three spots together (game-screens-menus-text.md, menus).
- Vehicle driving buttons: `IA_ROLE_VEH_*` with fallback pad buttons in `updateVehicles`, mirrored by the controls card table `kVehTut` (vehicles-and-roads.md).

## Player movement and two players

- **Speed tiers** (docs/player-speeds.md; the shape to copy for any "0 = inherit" field): `SceneObject::playerWalkSpeed` base; `playerRunSpeed` / `playerSprintSpeed` default 0 = inherit; the fallback chain lives ONLY in `project::playerRunSpeed` / `project::playerSprintSpeed` (+ `settingsRunSpeed`/`settingsSprintSpeed` for the Player-less walker). Codegen bakes RESOLVED values into `PLAYER_RUN_SPEEDS[]`/`PLAYER_SPRINT_SPEEDS[]`; Properties prints through the same functions. Tiers are written only when non-zero (byte-identical resave); 0 resolves to run = walk, sprint = walk x `sprintMultiplier` (old projects MOVE identically). Stick ramps walk -> run (`WALK + (RUN - WALK) * stickMag`), sprint pins the top FLAT. Both walkers (`updatePlayerWalker` and the FPP tail's) carry the expression; `drivePlayerAnim` normalises `speedFrac` by RUN speed.
- The walker reads tiers from `PlayerCtl::speeds[3]`, seeded from the tables at scene load, because the 80-byte Live Link record streams resolved speeds through `ScriptContext::playerSpeeds` (the three fields are deliberately OUT of `liveLinkRecipeHash`; look speed stays baked). Sprint CLIP (`playerSprintClip`, "" = run clip) is chosen by the sprint BUTTON, never a speed threshold; its rate divides out sprint/run.
- **Two players** (docs/multiplayer.md): walker state is a per-player `PlayerCtl` (`players[2]` in the game hpp templates); the walker is `updatePlayerWalker(PlayerCtl&, pi, Tyra::Pad&)` - not loose `entX/entYaw` members. Scene tables come in pairs (`PLAYER_*`/`PLAYER2_*`, first/second Player per scene) selected via `PP_*(pi)` macros in scene_data.hpp; a new per-player property goes into the paired emitter (one loop emits both prefixes) and is read through a new `PP_` macro. `ProjectSettings::multiplayer` ("off"/"shared"/"split") + `p2JoinOnStart` gate everything; menu bind 7 = Player count (edge-triggered + `syncPlayerCountMenuValue`). Split view activates only with a second `Player` (`PLAYER2_INDEXES`).

## World Facts (docs/world-facts.md)

- `facts.cpp/.hpp` (~960+360): catalog of game state, condition trees, reaction rules, test scenarios. Host-only, no GL/ImGui/project.hpp (project.hpp includes it - the input.hpp/ambience.hpp arrangement); language, evaluator, cycle detection and validator run from a harness.
  1. **`layoutOf` is the ONE slot assignment** (`factNum[]`/`factPos[]`); codegen and the editor blackboard both build from it, so compile-time and debugger indices agree by construction.
  2. **A condition is a TREE, not a string**: codegen folds it into one C++ expression, `evaluate` answers host-side, `Explain` names the deciding leaf ("Why?" panel).
  3. **A computed fact has no slot** - it IS a query folded into readers (free, unwritable: validator rejects rules targeting one; Set Fact does not offer it).
  Enum/tier/scope/comparator tables are each ONE list read by serializer, codegen, widgets and tooltips. `cyclicQueries` exists so codegen does not recurse forever: such a query emits `false`.
- `facts_ui.cpp` (~1.5k): Catalog / Queries / Rules / Scenarios / Blackboard tabs. Keeps the sectionJson guard (owns `Section::Facts`); renames go through `project::renameFactRefs` (graph nodes, query leaves, rule conditions/actions, scenario rows); `factValueWidget` is the single value presentation (a one-of-several fact shows its option NAME everywhere).
- The Live Debugger's command carries fact overrides (bits 24-31 = count).
