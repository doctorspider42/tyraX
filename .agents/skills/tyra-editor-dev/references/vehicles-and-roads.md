# Vehicles and roads

Read when you touch `vehbake`, `vehiclesim`, `vehcheck`, `vehicle_ui.cpp`, the generated vehicle runtime (`TPL_GAME_VEHICLES` / `vehicleImpl`), `roadgen`, `junction_ui.cpp`, any other `src/road*` / `traffic*` / `weather_core.inl` file, or road/junction codegen (`buildRoads`). Modelling a NEW car: see the tyra-vehicle-modeling skill. Primary docs: docs/vehicles.md, docs/roads.md, docs/road-textures.md, docs/traffic.md, docs/weather.md, docs/instance-sharing.md.

## Files

- `vehiclesim.cpp/.hpp` (~1.7k+560): wheel detection + the drive model; host-only (no GL/ImGui/App/project.hpp). Single source for the editor test drive (App drives the preview through `step`) and the generated runtime (per-frame twin). Twins with generated code: `bodyRotation`/`vehBodyRotation`, `damagePerformance`, `impactFromDelta`/`dentHash`/`applyDent` vs `vehDentHash`/`vehicleDentApply`, `rpmFor`/`vehRpmFor`, `revLimiterStep`/`revLimiterDipRpm`/`revLimiterOnset` vs `vehRevLimiter*`, `speedFeel`/`updateVehicleSpeedFeel`.
- `vehbake.cpp/.hpp` (~2.3k+320): the vehicle import bake - one `.glb`/`.fbx` in, body `.tmdl` + one wheel `.tmdl` out. Host-only (harness = 40-line main). Deliberately a VEHICLE importer, not a general static .glb path. `kMaxExhausts` = 6.
- `vehcheck.cpp/.hpp` (~1.3k): `--vehicle-check`, the drive model's property tests (exit 0 = all hold).
- `vehicle_ui.cpp` (~1.7k): Tools > Vehicle Editor (edits `Project::vehicles`; the scene knows only a name), `viewportBody`.
  Inspector = scope switch (`vehicleSel_ == -2` is Defaults, `vehicleScopeVehicle_` the car it returns to) + `VehTab` tabs by goal. Every tuned value goes through `tunedRow`/`tunedSlider`: caption | control | a fixed state SLOT (`slotW`, field trimmed with `ui::SetNextRowFieldTrim`) holding Own+revert / Defaults (hover: Make own) / Model / the reason a row is faded / in Defaults the follower squares + Follow popup. Never draw inheritance into the caption column again (it overlapped long labels). A new tunable needs `visitVehicleTuning` (project.hpp) to get inheritance, counts and the tab badge (`tabOfSection`).
- `roadgen.cpp/.hpp` (~1.2k+420): the road spline tessellator; host-only; single source for the viewport and the generated boot-time `buildRoads` raw-string twin in templates.cpp. CHANGE ONE AND CHANGE BOTH.
- `junction_ui.cpp` (~370): junction overrides UI (markers, selection, Junction section); a junction is selected by identity (`App::junctionSel_`), not object index.

## Vehicle geometry

- `glbparser` batches primitives by MATERIAL, incl. geometry from several rigid nodes. `vehbake::meshNodes` and `collect` split a single-weight, identity-IBM part per triangle's palette owner before detecting body and wheels; a genuinely skinned part stays on the dominant-owner path. Without it, four wheels sharing one atlas go to one node and vanish into the body. Rigid nodes sharing one material may collapse to one owner on import; the example preparation keeps one material slot per wheel.
- **Wheel batch is a TRIANGLE STRIP** (1.107.0, "The wheel batch is a strip"): vehbake builds it (vehicle models never pass `bakeStaticModels`) with `meshstrip::Weld::kNoNormal` (unlit, single-coloured bag). Each wheel's block is rounded up to whole runs (else a VU1 package splices two wheels into one triangle). Since 1.117.4 the BODY has a separate `kFull` attempt (legacy flat-shaded bodies honestly refused; a smooth atlas-authored CC96 part: 11,058 list corners -> 4,212 strip vertices, 148 -> 57 packages). **Never `kNoNormal` on the lit body.** Lamp parts stay lists (their rear/front ranges are corner indices). `TYRA_STRIP_VEHICLE_BODIES_BAKE=0` = editor-build A/B control (changes the body `.tmdl` only).
- **Special body parts**: `lamps`, `merged-matte`, and `glass` (split from the palette merge only when `glassOpacity < 1`, after the lamps, never decimated/tiered/mirrored, skipped as wheel carrier; drawn at the translucent tail by `renderVehicleGlass`; the object pass skips it via `GeoPart::translucent`). Any new per-part rule in vehbake (shine, decimation, tiers, carrier) must decide what it does with each; a new object-part render loop owes the `translucent` and `lodHidden` tests.
- **Far tiers** (1.134.0, "Distant vehicles", "An authored far model"): the carrying part is MEASURED (`farPart`, adopted with the lamp indices); the runtime asks that part for its tier - never `parts[0]` (the lamps on a car with lamps; never tiers; drew a second wheel set through every far tier). `VehicleDef::farModel` = authored low-poly twin; `collectFarModel` collects it in the FULL model's canonical frame/origin, matches images by decoded pixels, runs before the palette is sized (its untextured materials share the merge). Unreached parts go into `farHideMask` (`GeoPart::lodHidden`) except `lamps`. Body tier = `vehicleLodTier` (hysteresis; `trafficDistance` for every car but the driver's) via `{{VEHICLE_LOD_TIER}}`/`{{VEHICLE_LOD_HIDE}}` hooks in the object LOD block, not the row's `meshLod`. `applyGeoLod` sets `stripped` for EVERY tier it binds and binds `lodStripVerts` when present. Mixed definitions keep separate runtime wheel batches (a palette car never samples through a textured car's image); verify both together at near range; far tiers carry their own baked wheels.
- **Wheel simplification** protects the outer tyre band; tiny budgets are soft and Import details reports actual cost. `wheel_blur` is a reserved auxiliary node excluded from detection in every mode (incl. None and Automatic). Verify automatic and authored modes at swap speed; body decimation is independent.
- **Textured vehicles**: `vehbake::Result::textures` holds bin-relative names + PNG bytes; `bakeProject` and `vehicleRefreshBake` both write them. The viewport resolves `ModelPart::bakedTextureRel` per draw (never a cached GL name). Palette UV fixup visits only palette parts (real UV V=-1 is valid). A wheel/body image + Kd match permits textured wheels in body distance tiers. Check with the GGBot GLB in Motor District (PNG references, in-game texture, four detected wheels, distant silhouette).
- **These images are the one shipped model texture that does NOT pass through texbake** - anything texbake does must be redone here. `textureQuant` was missed (a 4-bit project shipped a 256x256 RGBA32 car = a third of the texture heap, docs/gs-vram.md): `bakeProject` runs `pngquant::quantizeRGBAToMemory` (in-memory: the bake content-compares before writing). The `-palette.png` ramp is exempt. Do not gate on the output FILE being smaller (GS cost is pixel format; dithering makes palettized PNGs deflate worse). **Palettizing is a TRADE**, gated on the project setting: +0.51 to +0.74 ms per pose on the Motor District (0.119 MB heap free, nothing evicted), with `finish_ms` rising on poses whose frames are byte-identical between arms - live hypothesis: shrinking an allocation moves every later address and changes GS texture-cache behaviour scene-wide (applies to ANY texture-size change; decisive test = pad allocations back and re-measure).
- A rebuild that REUSES a GeoPart (Repair Vehicle, damage re-bake) resets `envColors` to the 128 placeholder, so it must also clear `envPaintValid` and `paintMapSrc` (else the paint pass's quantized view key reads "same view" and the car shows full reflection until the camera turns).

## Vehicle runtime rules

- **Bank/suspension**: `vehiclesim::bodyRotation` / generated `vehBodyRotation` apply vehicle-local pitch and roll before heading, then convert to ordinary object XYZ Euler (use that conversion for body AND wheels; roll on world Z makes bank heading-dependent). Ground-plane fitting uses the hardpoints' projected spacing. Clearance probes are position constraints only (never spring target or velocity source). The wheel batch composes three transform columns per wheel outside its vertex loop. Keep vehiclesim.cpp, vehicle_ui.cpp and the runtime in step.
- **Sleep**: a grounded car sleeps only after 25 stopped updates, when not driven, no AI route, and all looping audio channels silent. Prompt/enter handling stays before the gate; car-to-car collision after it (the response assigns motion and wakes the car next frame). `Vehicles_update` and `Vehicle_sleep` hardware-trace scopes prove it.
- **Exit**: clamps the authored door-side offset outside half the track + tyre radius + player clearance, then floors the player at terrain height; Use and Exit Vehicle share `exitAtDoor`.
- **Damage** (1.138.0, "Damage"): `damageVisual` gates dents, loose pieces, broken lamps, damage dust, engine smoke (the meter still accumulates if mechanical is on); both off = skip impact tracking. `damageMechanical` gates power loss and wreck immobilisation (incl. AI and nitrous). `damagePerfCurve` shapes partial loss (`vehiclesim::damagePerformance` <-> runtime). These fields join tuning inheritance and the format.
  1. A hit = the velocity change the frame's collision stages imposed (`VehicleRt::dmgPreV` taken at loop top for sleepers and right after the drive integrates); `updateVehicleDamage` runs after the car-vs-car pass. Never write a non-collision speed change between those points (reads as a crash).
  2. Dents are a function of REST position only (welded corners cannot split); the rest copy lives in `VehDamageGeo`, re-captured whenever a part's `baseStamp` moves - so anything that bumps `baseStamp` without rebuilding is captured as undamaged.
  3. Dents write matrix-path LOCAL vertices via `BagArray::span` and bump `baseStamp`/`bboxVersion`; they skip lamp and glass colours (`renderVehicleGlow` owns lamp colours; `lampBroken` is how damage speaks to it). `damage*` DriveSpec keys show on the Damage tab and are skipped by Driving by that PREFIX - keep it.
- **Loose pieces** (1.139.0): a piece is a vertex RANGE of a body part's tier-0 array (`VEHICLE_PIECES`, measured into `VehicleDef::pieces`), safe to collapse only because the bake gave each piece whole strip runs. Anything re-ordering/re-stripping a body (new weld key, part merge, run packing change) must keep that (else a bonnet tears a fender triangle). `vehiclePiecesCollapse` runs after every write that could re-grow a lost piece (dent, re-capture). Debris: `vehDebris_`/`vehDebrisBatches_` (one world bag per texture, rebuilt only while dirty), kicked by cars, off collision boxes, deleted past 60 units. The same reorder puts a shiny textured part's matte (near-black texel) triangles LAST; `applyVehicleEnvLimits` shortens that part's env bag to the prefix every frame (`VEHICLE_ENV_LIMITS`; rebuild/tier swap resets it). The editor mirrors by splitting the part in `viewportBody`.
- **Exhaust pipes** (1.167.0): `vehbake::build` reads geometry-free nodes named `exhaust*` (case-insensitive) as {opening, direction} in the canonical body frame; direction = node +Y for glTF, +Z for FBX (measured); exactly vertical = unrotated empty = straight back. `adoptMeasured` carries `VehicleDef::exhausts` (format v93) into `VEHICLE_EXHAUSTS`; runtime `vehicleExhausts()` is the ONE pipe list (nitrous flame, upshift backfire, `updateVehicleExhaustSmoke`), falling back to two guessed rear pipes. `kVehExhaustMax` (runtime) >= `vehbake::kMaxExhausts`. Exhaust smoke rides the tyre-smoke pool: every spawn site takes `VehFx::takeSmoke()` (resets per-puff `smokeScale`/`smokeFade`; bumping `smokeNext` by hand inherits the last puff's size). `exhaust*` keys on the Effects tab (section "effects" in `visitVehicleTuning`). Headless refresh/build adopt markers in memory only; the GUI tick (or hand edit + `--resave`) persists.
- **Lamp glow** (1.141.0): lamps measured per LAMP (connected components -> `VehicleDef::lampGlows`), emitted as `VEHICLE_LAMP_GLOWS` only when `drive.lampGlow` > 0, drawn by `renderVehicleLampGlow` through `beamCoronaTex` - so `projectUsesBeams` is true for such projects (gates the `hud/flare-corona.png` bake and load) and must keep the texture for every vehicle project (the upshift backfire uses the same textured corona batch). Arrays are fixed-size, sized in `setupVehicles`, written by slot (a previous frame's DMA may still read them). Nitrous flame = extra quads (`VEHICLE_NOS_FLAME_USED`). `backfireT` must tick outside the skid-smoke branch (a handbrake slide froze the flash). `lamp*` keys on Effects.
- **Speed feel** (`feel*` keys, Look tab): `vehiclesim::speedFeel` <-> `updateVehicleSpeedFeel` (called from the driver-camera block; nullptr on foot eases everything back and restores FOV). Talks to the loop via `g_vehShake` (applied after Camera Shake) and `g_vehBlurFix` (floor under `g_motionBlurBase`); both game heads carry the consumers - edit as a pair.
- **RPM and sound**: `rpmFor`/`vehRpmFor` allow RPM up to `nosTopSpeed` x redline in final gear while the high-rev crossfade stays capped at full volume. `DriveSpec::powerFade` and the generated longitudinal step apply the same speed-squared fade incl. nitrous relief. The high-rev sound has its own onset and pitch endpoints in VehicleDef (keep serialization, inheritance, `VehicleDefData` and host audition in step); idle loop pitches from launch, the second loop fades in only above its onset. The high-rev enabled switch keeps the sample/curve but codegen emits a silent slot; host audition uses only idle. **Rev limiter** (`revLimiter`/`revLimiterRate`) is presentation only: the dip lives beside `rpm` (`limiterDip`), never subtracted from it (the gearbox reads smoothed rpm); audio, test-drive readout and audition subtract it.
- **Controls card** (1.169.0, "Controls card"): `VehicleDef::tutorialSeconds` (Driver tuning key, JSON `"tutorial"`, written only when non-zero, format v94) emits `tutorialFont`/`tutorialSecs` at the END of `VehicleDefData` (keep the empty `VEHICLE_DEFS` initializer in step). Runtime text; `kVehTut` is the ONE row table (role, fallback pad button, label) and must mirror the fallback buttons `updateVehicles` reads when an `IA_ROLE_VEH_*` is -1 (a new driving button needs a row). Glyphs from `g_inputBind` every frame; unusable rows filtered by `vehTutRowApplies`; stick glyphs via `menubake::optionalBuiltinIconNames()` + `project::ensureStickIcons`.
- `collideVehicleCamera` runs in both game tails after shake and separation, excluding the driven chassis.
- HUD fonts for driveable instances are prewarmed in `setupVehicles` (game-screens-menus-text.md).

## Tuning inheritance (1.153.0)

`Project::vehicleDefaults` is a singleton in `Section::Vehicles` (`writeVehicleArray`/`readVehicleArray`). `VehicleDef::inheritDefaults` is true for new definitions; pre-v85 files without an explicit flag stay local; vehicles-branch files with an explicit flag keep it (both branches reused v82/v83, so v85 unifies; normalization preserves tuning). `visitVehicleTuning` = shared registry of tunable fields and section ownership. `tuningOverrides` holds individual field keys (historical group keys expand during resolution; old "sounds" group overrides also expand to headlights). UI controls edit directly; diffing against the resolved pre-frame definition creates only changed keys. Section "Use defaults" clears its keys - skip those keys in the same-frame diff or the reset recreates them. Geometry keys stay local (`vehicleGeometryKey`). `applyVehicleDefaults` resolves at section-read, commit and codegen. Global asset refs join asset-browser and particle-effect renaming. Global UI reuses tuning tabs without import/test-drive tabs. Headlights belongs to Effects (UI and Use defaults).

## Vehicle Editor preview and sound

- Live preview = a separate lazily created `Viewport` owned by App: reuses cached vehbake models, previews wheel spin/steering and fast-wheel hysteresis, never moves scene entities. Replacing/clearing vehicle draws destroys their VAO/VBOs; the preview drops its private texture cache on bake changes (reused palette paths show edited colours). Shut the preview down before the GL context. Triangle budgets need an explicit editor-only unlock; reflection maps use project texture thumbnails.
- `audiopreview::EngineLoop` decodes samples off the audio thread and owns host audition (atomics carry pitch/revs/volume); stop audio before destroying callback state.
- Sound selectors list all project WAVs. Continuous roles (`engineSound`, `engineHighSound`, `screechSound`) declare encoded loop intent via optional `inc/vehicle_sound_loops.gen.txt` (from resolved definitions; refresh rewrites it and removes stale intent; always-overwritten list). Legacy `-loop.wav` still works.

## Roads

- **Lateral span reduction** (1.85.0, docs/roads.md "The lateral budget"): the roadgen/`buildRoads` twins sample every lateral height, then keep the horizontal collapse, or merge a non-flat span's lateral cells into MAXIMAL RUNS whose every dense sample lies within `kSpanFlatness` of an affine 3-D quad with parallelogram defect within `kSpanShear` (1e-5 and 0.05, roadgen.hpp). Never infer planarity from the shoulders (interior crowns/saddles keep samples). It used to be all-or-nothing and bought nothing (terrain cell 4 u vs 0.5 u lateral sample; all 26 cells of a 13-unit street survived). Lessons: test SUB-spans; and measure which gate fires (the UV budget, not the surface one, was blocking: a trapezoid's two triangles interpolate ST with different affine maps and every district street is curved).
- **Strips** (1.96.0): `roadgen::tessellateStrips` is a THIRD twin beside `tessellate` (triangle list; source of truth for viewport, picking and the align pass) and `buildRoads`. Both host emitters share `buildRows` and `spanCuts` (sampling, heights, texture arc length, lift, planar-span reduction in ONE place). `spanCuts` holds the greedy extension `while (j1 < crossSteps && spanIsExact(rows, i, j0, j1 + 1)) ++j1;` that `verify-road-twins.py` pins by TEXT (its dense reference deletes that line). templates.cpp carries both budgets as literals (raw-string code cannot read constants), held by a `static_assert` against roadgen.hpp at its top. Strips: 93,150 road vertices in 90 chunks vs 13,176 in all baked models; 0.355-0.374x vs models' 0.732x. Rules: dense spans strip ACROSS the road, collapsed full-width spans ALONG it (laterally a collapsed span is break-even and triples GS primitives - 1.000x on every flat fixture); only one interleaving reproduces the list's quad DIAGONAL; runs may not straddle chunks, so `kChunkSpans` (36) and `kChunkBudget` (1800) live in roadgen.hpp; the terrain builder strips **only with a terrain material** (the untextured checker is per QUAD colour).
- **Oracle**: `examples/vehicle-playground/authoring/verify-road-twins.py` compiles both implementations and compares strip output vertex for vertex and chunk for chunk, plus exact triangle-SET equality vs the list and the dense baseline. `ROADSTRIP`/`TERRAINSTRIP` in `bin/log.txt` carry each producer's surface triangle count (pipeline counters cannot compare across representations; docs/model-pipeline.md "What the triangle counters count"). ROADS logs emitted vertices and chunks. The district's seven-road network is an EE memory stress case.
- **Bounded V** (1.117): both emitters and `buildRoads` rebase longitudinal V by `floor(V at chunk start)` (texture-identical under REPEAT; keeps hardware ST bounded - topology was not the smear's cause). The oracle canonicalizes whole V repeats when comparing list vs strip (they may chunk differently); runtime-to-host strips stay exact per chunk. Since 1.117.2 `TYRA_STRIP_ROADS` defaults 1 (0 = diagnostic list arm): road-only district 63,966 vertices / 880 packages -> 24,576 / 347, same 21,322 surface triangles.
- **Sample step** (1.119): optional `roadSampleStep` (1..2, default 1) must reach `roadgen::tessellate`, viewport draw/pick and generated `RoadDefRt`/`buildRoads` alike; texture V still integrates at the original 1 m cadence (else lane marks slide). Motor District: Ring road and East crest at 1 m, other five at 2 m; don't make 2 m a universal default without crest/bend tests. `road-budget-sweep.py` (referenced by docs/roads.md; not in the repo) compared candidates against the dense surface.
- **Intersections**: Properties stores a material path in the legacy-named `roadTexture`/`roadIntersectionTexture`; `project::resolveRoadTexture` resolves the first `map_Kd` (direct PNG values still work). Every road at a node must name the same intersection reference; since 2.1.0 the footprint is a NODE ("Road network" below). Since 1.151.2 `roadgen::tessellateJunctionSurface` fits an adaptive conforming mesh against actual road triangles with 0.02-unit clearance at triangle intersection corners; codegen bakes XYZUV in `ROAD_JUNCTION_VERTS` (`buildRoads` only uploads). Generate source roads with the rendered terrain triangle sampler (`roadgen::terrainHeight`), not `project::heightAtWorld`'s bilinear. Never move pairing/fitting onto the EE.
- **Every crossing decision is `roadgen::planCrossings`** (1.145.0, "Junction overrides"): patch or not, who runs through, which spill survives, per-junction overrides (`SceneData::roadJunctions`, matched by road-id pair + nearest position) and winner OVERLAYS. Codegen, `Viewport::syncRoadDraws` and the test drive (`roadgen::addCrossingsToSurface`) only read it, over `project::crossingRoads`. Spills are filtered PER CROSSING (a triangle belongs to its pair's nearest crossing); overlay decals precede spills (the console reads all spill Y before adding chunks, so the overlay height reaches the spill via the row's `lift`, not `roadSurfaceAt`).
- **Road editing** (1.151.0): loops repeat the first XZ pair at the end of `roadPoints`; `roadgen::isClosed`/`controlCount` hide the seam sentinel; host and `buildRoads` wrap Catmull-Rom neighbours and final tangents together (no format field). `moveControl`/`removeControl` preserve closure and minimum counts. Properties: collapsible Crossings/Points + reversible Closed loop toggle; viewport Shift-click deletes, endpoint snap closes at release, one undo each. Outlines reuse `Viewport::RoadDraw` (full-width soft borders keep a separate outline). During viewport drag only, both crossing caches defer work to release. UI scripts can target `Road point N` handles and use `shiftclick`. Verify loop seams + open-road parity with the twin oracle.
- Road chunks opt out of occlusion culling and the whole-AABB frustum pre-test (lighting-and-bakes.md); roads receive baked shadows via `decalproj::Receivers::roads`; decalproj caches road triangles.

## Road network (2.1.0)

The pattern every feature below repeats: decisions are host-only and pure, each in its own `src/road*.cpp` (kept OUT of roadgen.cpp/roadtex.cpp so parallel road work merges); the codegen, the viewport, the test drive, `--road-crossings` and `--vehicle-check` call the SAME function; runtime hooks are text patches; tables and upload blocks exist only when a `projectHas*` predicate holds, so a project without the feature regenerates byte-identically. Chunk owners: -3 road/patch (in the height index), -4 kerbs + rails (in the index), -5 bridge structure, -6 details, -7 furniture, -8 free streaming slots.

- **Nodes** (docs/roads.md "Road nodes"): `roadgen::findNodes` clusters crossings at any angle, open ends resting on another road (T, fork) and shared ends (corners) into one node per place, with a filleted outline whose arm edges follow the road curves. `Crossing::roads` lists every road there; `c.a`/`c.b` are only the first two - a new consumer asks `c.has(road)`. `findJunctions` and `cornerXZ` remain only for the oracle's legacy cases. `tessellateJunctionSurface` also proves clearance over the terrain's own triangles and, where a fan cannot follow the ground, cuts the outline along the terrain grid - pass the scene's `roadgen::TerrainGrid` (`terrainGridOf`, `Viewport::terrainGrid`) or it falls back to 2-unit cells. Node MARKINGS (`roadgen::bakeMarkings`: edge lines round the fillets, stop lines, zebras; per-road `roadMarkings`) ride the junction table as one untextured row per scene (`RoadJunctionRt::rgb` non-zero = paint in that colour, no texture), so a new painted thing needs no new runtime path. A width change between two roads joined in line is a TRANSITION node (`Crossing::transition`, taper outline). Per-arm frames for anything drawn on a node: `Crossing::armList`; `Junction::outlineCap` says which outline segments are arm caps.
- **Kerbs** (format 123, "Kerbs") follow the patch pattern, not the tessellator's. Chain: `SceneObject::roadKerb/roadKerbHeight/roadKerbWidth` (+ `operator==`) -> `objectJson`/`readObjectsArray` (written only off-default) -> road section of `props_ui.cpp` -> `liveLinkRecipeHash` (mixed only when on) -> `project::crossingRoads` -> `CrossingRoad::kerb*` -> the crossing signature in `Viewport::syncRoadDraws` (kerbs are cut at the crossings, so they rebuild with them, not with the per-road draw). `roadgen::planKerbs` decides every kerb line from the crossing plan; codegen bakes them with `kerbStrips` into `ROAD_KERBS`/`ROAD_KERB_VERTS`, uploaded by `roadKerbsUpload` (spliced into `buildRoads` before `procFinishChunks`), all only when `projectHasKerbs`. Owner **-4**: `renderProcChunks` draws them with its draw distance (`renderRoadChunks` has none), and the road height index reads -3 AND -4, so a kerb top is ground for wheels, walkers (`walkGroundAt`, 0.5 step cap), blob shadows and light pools. The shadow bake's road hash (`decalproj.cpp`) leaves the kerb fields out on purpose: kerbs are not receivers, and adding them would stale every baked-shadow cache.
- **Pavements** (format 125) ride the kerbs with no table of their own. `SceneObject::roadPavement/roadPavementMaterial` take the kerb chain (the material is an asset path: `assetbrowser.cpp`'s usage notes and both rename swaps list it); `CrossingRoad::pavement` is set only for a kerbed road; `roadgen::planPavements` turns the SAME `planKerbs` pieces into textured XYZUV triangles, shipped as ordinary `ROAD_JUNCTIONS` rows, one per material and 32-unit cell (`rgb` = `kPavementRgb` when untextured) - owner -3 chunks culled, drawn and collided like a patch, no EE work, no new runtime code. The viewport and test drive (`addKerbsToSurface`) call the same function on the same pieces.
- **Rails and tram tracks** (format 126) ride the kerb pipeline and add no runtime table. Chain: `SceneObject::roadKind/roadRailGauge/roadTracks` (+ `operator==`, written only off-default), the Kind/Tracks/Gauge block of the road section (Kind = Railway calls `roadpresets::applyRailway`, moved there from props_ui: ballast materials, written from `roadtex::presets()` when missing, plus rank Track, no spill/kerb/markings), `liveLinkRecipeHash` (mixed only when kind != 0), `project::crossingRoads` -> `CrossingRoad::kind/railGauge/tracks` (it also FORCES a railway's kerb, markings and edge line off), the crossing signature. Geometry is all in `src/roadrail.cpp` (`planRails`, its own strip emitter with the kerbs' run contract, `addRailsToSurface`); roadgen.cpp only learned to skip markings at a node a railway is in. Rail strips are more `ROAD_KERBS` chunks (`projectHasKerbs` is true for a rail/tram road too); a vertex shade of 2+ names a `ROAD_KERB_PALETTE` entry (printed from `roadrail::kPalette`; the upload's `put` lambda and `roadrail::shadeRgb` are the two readers - change both).
- **Bridges** (format 128, `src/roadbridge.cpp`) are host-baked and the EE twin does NOT carry them. A `roadBridge` road is left out of `ROAD_DEFS`; its deck becomes `ROAD_JUNCTIONS` rows (owner -3, in the height index), its parapets/underside/piers/abutments `ROAD_BRIDGES` rows (owner -5, drawn by `renderProcChunks`, NOT in the height index). Rules for anything new that reads roads: (1) the DRAWN surface of a road is `roadbridge::drawnRoad`, not `roadgen::tessellate` (tessellating a bridge glued draws it on the ground); (2) node patches, kerbs and markings fit the GLUED roads (a bridge's ground self), or a node under a deck is pulled onto it; (3) a ground query that must not snap onto a deck overhead passes `maxY` (`roadSurfaceAt`/`groundSurfaceAt` on the console, `roadgen::Surface::at` on the host): wheels use the car's y + 1.5, walkers feet + 0.5, blob shadows the caster's base + 0.5. `CrossingRoad::elevation` tells the planner a bridge's height (`project::crossingRoads` takes the scene's bare-terrain HeightFn for it); `findNodes` and the kerb planner skip anything more than `roadgen::kOverpassClearance` apart vertically. `roadHeights` follow the points through `roadbridge::onPointInserted/Removed/Reshaped` - every point-edit site calls them instead of clearing the vector.
- **Road details** (format 127): `SceneObject::roadDetails/roadDetailSeed` take the kerb chain (`CrossingRoad::details/detailSeed`, crossing signature, `liveLinkRecipeHash` only when on). Everything else is `src/roaddetail.cpp` (placement, the surface-following decal bake, the atlas generator); codegen, viewport, `--road-crossings` and `--vehicle-check` call `roaddetail::build` with the scene's roads, plan, patch triangles and node paint. `ROAD_DETAILS`/`ROAD_DETAIL_VERTS`/`ROAD_DETAIL_TEX` + `roadDetailsUpload` (spliced after the kerbs') only when `projectHasRoadDetails`. Owner **-6**: out of the height index (paint, not surface), drawn BLENDED by `renderRoadChunks` after the -3 chunks - a blended chunk drawn from `renderProcChunks` lands BEFORE the interleaved road bags and the asphalt covers it (the two owner tests are string-patched in `fill()` only when details exist). `refreshGenerated` writes the atlas (`roaddetail::ensureAtlas`) only when missing, so a repaint survives builds.
- **Street furniture** (format 129; Properties = `App::drawRoadFurniture`, `src/roadfurniture_ui.cpp`) keeps its settings in ONE struct: `SceneObject::roadFurniture` is a `roadfurn::Settings` (`src/roadfurniture.hpp`: three `Line`s - lamps, trees, bollards - plus seed, signs, signals and their models), so the chain is one line per consumer: `roadfurn::toJson`/`fromJson` (non-default keys only), defaulted `operator==`, `roadfurn::signature` in the crossing signature and `liveLinkRecipeHash`, `roadfurn::modelPaths` in the asset browser's usage notes and rename swaps. Placement takes the roads with a PARALLEL settings vector (no CrossingRoad fields), the plan, patches, paint and `planPavements` output; codegen, viewport, `--road-crossings` (`roadfurn::prepare` rebuilds those inputs) and `--vehicle-check` (`roadfurn::check`) all call `roadfurn::build`. Its sign rule is a TWIN of `bakeMarkings`' giving-way rule (the check proves every sign stands at a painted stop line). `ROAD_FURN*` + `roadfurn::uploadSource` (spliced before `procFinishChunks`) only when `projectHasRoadFurniture`. Owner **-7**: merged untextured vertex-colour chunks drawn by `renderProcChunks`, poles and trunks as owner -7 `procColliders`; the height index never reads -7. An `.obj` model's texture is SAMPLED into the vertex colours at bake (no VRAM, no texture-atlas trap).
- **Road streaming** (format 130, docs/roads.md "Road streaming") is CUT, not retyped. `ProjectSettings::roadStreamRadius` > 0 swaps `buildRoads` for `roadStreamSetup` + a per-frame `roadStreamUpdate`; `roadstream::emit` (`src/roadstream.cpp`) builds that runtime out of the non-streaming text - buildRoads' per-road loop (patched to plan or replay one chunk: the plan pass records each strip chunk's slice of the road's band plan in `rsPlanBytes_`, because `roadPlanBands` is a fixpoint over the WHOLE road, and a replay rebuilds only its bands' rows from the recorded arc state) and the band planner block itself (a streaming build emits no buildRoads), the junction/spill/edge uploads, the kerb/bridge/detail/furniture upload blocks and procFinishChunks' per-chunk body - each cut at fixed anchors. **Editing any of those texts can break an anchor**: `--vehicle-check` "road streaming" generates a project with every road feature and fails on a miss, and the generated source gets an `#error` naming it. Three shared hooks are string-patched in `fillTemplate` only when streaming is on (`roadstream::patchTemplate`: roadSurfaceAt's lookup, the update after the terrain ring, the far-car freeze), so radius 0 is byte-identical. The pure part (item boxes, coarse grid, per-chunk height index, ring) is `src/roadstream_core.inl`, ONE file compiled into the editor (namespace roadstream) and pasted verbatim into the generated class (embedded by CMake via `embed_binary.cmake`): structs and member functions only, no includes, no `/* */` comments (`ROADS_IMPL` also lands inside one in the collision TU). Streamed chunks live in procChunks slots tagged `instance = -2 - item`, free slots are owner -8, and anything that erases procChunks is caught by the tags (`roadStreamRemap`). Fixed alongside, patched only where they apply: auto-stream layer zones focus on the DRIVEN car in vehicle projects (they read the parked walker before), and auto-stream projects log `LAYER n load|unload`.
- **Tables on disk** (format 132, "Tables on disk"): a streamed project (unless `ProjectSettings::roadStreamEmbedTables`) emits no per-vertex `ROAD_*_VERTS`/`ROAD_FURN_RGB`. The scene-data codegen feeds each streaming item's rows - every value parsed back from the literal the embedded table would have printed, so bit-exact - into `roadfile::Builder` (`src/roadfile.cpp`), which writes `.res-baked/roadfile/roads.bin` (a generated `templates::File`, copied to `bin/roadfile/` by the Makefile's resources step - NOT straight into `bin/`, which `--rebuild` drops after the refresh) and the `ROAD_FILE_ITEMS` directory in scene_data.hpp. `roadstream::emit` with `Params::tablesOnDisk` splices a reader thread, a slot queue, an LRU read-ahead cache and the directory-driven plan in at anchors of its OWN text (`kDisk*`); the cut upload blocks read rows through a local pointer named like the old table, so the cut text is unchanged. buildRoads is not compiled in that mode. Header layout + checksum = `RsFile` in roadstream_core.inl (host and console share them). texbake's sweep skips `roadfile/`; refreshGenerated deletes a leftover file; `--vehicle-check` "road tables on disk" proves item k's bytes equal the embedded slice. The EE side uses ONE semaphore and ONE thread for the whole game - kernel semaphores are scarce (see instance sharing in runtime-rendering-and-meshes.md); never one per item.
- **Traffic** (format 134, docs/traffic.md) is the streaming arrangement a third time. `ProjectSettings::traffic` (`TrafficSettings`, an object of non-default keys, in `operator==` and `liveLinkContextHash`) turns it on. `roadlanes::build` (`src/roadlanes.cpp`) is the ONE lane graph - the codegen's road pass (it already holds each scene's roads, plan and furniture result), View > Lanes (`src/traffic_ui.cpp`), `--road-lanes` and the check all call it; priorities come from `roadgen::giveWayArms` and signals from `roadfurn::nodeSignalled`, the very functions paint and furniture use - never re-derive either. The cars are Vehicle objects APPENDED in `templates::generate` (`roadlanes::withTrafficCars`, id prefix `~traffic-`, `VEHICLES.wpFirst == -2`, live-link id hash 0 - the scroller-clone idea). Runtime = `src/traffic_core.inl` (pasted verbatim, class-body rules) + `roadlanes::implSource`, appended to `roadsImpl` OUTSIDE the tables-on-disk early path (that early return is how a streamed city first linked without it), plus six hooks string-patched into the vehicle runtime by `roadlanes::patchTemplate` (setup, the per-frame ring, the driver branch, the far-car path, the sleep exclusion, traffic headlights without a pool). A new anchor needs a mark in `kHookMarks` - the check fails on a hook that did not land. Off = byte-identical. Signal PHASES = `roadfurn::signalPhase(arms, arm)` (four-way: arm % 2; otherwise one phase per arm) - the lane graph's connection groups, the `TRAFFIC_LAMPS` heads and the phase count in `TRAFFIC_NODE_SIGNAL` all read it, so a new phase plan is ONE function plus the core's `light()`. A junction's `JunctionOverride::control` (format 136) reaches `nodeSignalled` via `Crossing::control` (copied by `planCrossings`); it must never touch `giveWayArms`. Lane changes live entirely in the core (`route`/`adopt`/`considerChange`/`gapClear`/`laneStep`/`pose`) on the lanes' `inner`/`outer` links (`TrafficSegData` is 13 ints). The player's red runs reach the flow graph through `ScriptContext::redLightRuns`/`Node`/`Speed` (On Red Light Run watches the count - the OnCreditsEnd shape).
- **Weather and lit street lamps** (format 135, docs/weather.md; `src/roadlight.cpp` + `weather_core.inl`). roadlight is host-only (no GL, no ImGui; `project.hpp` only for its --vehicle-check codegen block): `lampsOf` finds each furniture lamp's head (the built-in lens by its unshaded colour), `bakePools` lays the surface-following additive pool quads (asymmetric sink/float budget, depth 2, raise-at-cap over kerbs) chunked by 96-unit cells; codegen also emits `ROAD_LAMPS`. Three things to know: (1) the pools are FURNITURE rows (`roadfurn::Tables::lit`, a `light` column, UV packed in the colour word) - never give them their own table or streaming item kind: riding in RS_FURN is what makes them stream and page into roads.bin with no roadstream change. A lit project prints `struct RoadFurnRt { ...; int light; }` and roadfile's check reads the row width from that line. (2) `Tables::source` has a local lambda called `lit`: the member must be spelled `this->lit` there (the lambda converts to true and once gave every furniture project the light column). (3) Every hook is a text patch in `roadlight::patchTemplate` (zero-cost-gated: `ProcChunk::lampLight`, procFinishChunks' additive pool bag and the asphalt wet tint, renderRoadLamps/renderRain/updateWeather, loadScene's `weather::reset`), applied LAST in fillTemplate - the roadstream cutter reads the RAW procFinishChunks, and the replaceAll at the end patches both copies. Neither lamps nor weather = byte-identical. `weather_core.inl` is the roadstream_core arrangement (the editor compiles it, CMake embeds it, `weatherHeaderSource` pastes it into `inc/daynight.gen.hpp`; no block comments, no includes); it also holds the puddles' `weatherPuddleLevel`/`weatherPuddleColor` and the cars' `weatherCarStreaks` (the console's renderRoadLamps and --vehicle-check call the same function); the car block (`kCarStreaks`) is spliced into renderRoadLamps only with vehicles AND weather (`Gates::vehicles`). The Set Weather node writes `weather::request` directly (not ScriptContext); `SceneData::weather/weatherIntensity/streetLamps` are staged in Scene Preferences.
  - **Puddles** (docs/weather.md "Puddles") are road DETAILS: `roaddetail::build` places them in a second pass AFTER every other decal (so gaining weather never moves a manhole - keep it that way), into `Result::puddles`/`puddleTris`/`puddleChunkSizes`; codegen appends their chunks as `ROAD_DETAILS` rows with a `wet` column that exists only when `projectHasPuddles` (weather + details). The two upload lines that read it (`c.puddle = dr.wet`, the `ROAD_PUDDLE_TEX` lookup) must stay INSIDE the roadstream cuts ("detail texture", "detail upload") - that is what makes a streamed puddle chunk exist; roadfile's check reads the detail row width from the struct line. The puddle colour is one `roadPuddleColor_` per frame (alpha = wetness); never write puddle vertices. Car-light streaks are generic on purpose: every VehicleRt whose lamps are on, whoever switched them on (traffic lighting at night belongs to the traffic code).
- **Breakable street furniture** (format 137, docs/roads.md "Breakable furniture", `src/roadfurnbreak.cpp`). Settings in `roadfurn::Settings` (`breakable`, `brk[kind]`, `breakSound`); table `roadfurn::Tables::pieces` (`ROAD_FURN_PIECES`, one row per box: ROAD_FURN row + vertex range, lamp, pool range, sound, threshold, keep). The file is the generated runtime as a text patch (`patchTemplate`, gated by `projectHasBreakableFurniture` = vehicles + a breakable road), the host twins `breaks`/`touches`, and `--vehicle-check` "breakable furniture" (a host vehiclesim drive into a lamp, the piece table, the collapse, the codegen hooks counted through `kHookMarks`).
  1. **The patch runs after the lamp patch**, at the very end of fillTemplate, because it reaches into renderRoadLamps (a dark lamp's halo) and into both copies of the furniture upload (buildRoads' and the streaming cut). The cut copies take the same replacements because they target lines INSIDE the cut (`c.owner = -7;`, `sb.owner = -7;`); the streaming case only gains the locals those lines use (`const int fi = it.a;`, `const int bi = it.a;`). fillTemplate runs once per generated FILE, so a missed anchor is not an error there - `--vehicle-check` counts `kHookMarks` over the whole project. Without a vehicle or a breakable road the project generates byte for byte what it did before (the two struct fields, `ProcChunk::furnRow` and `StaticBox::furn`, are patched in too).
  2. **Never erase a broken box from procColliders**: the sub-step gather cache (`VehGatherCache::proc`) and the streaming tags hold INDICES into it; `furnBoxInert` moves the box out of reach in place. An erase makes a car's next sub-step read the wrong boxes.
  3. **The piece table is keyed by the BOX index** (= the instance index, the order `roadfurn::build` sorts its instances into). A piece's vertex range is RELATIVE to its ROAD_FURN row (`Tables::add`/`addLight` compute it with `rowOf`), so re-chunking the furniture or reordering its rows keeps it right by construction; changing the order of `boxes` vs `instances` breaks it (the check compares every range).
  4. **Broken flags belong to the scene, not a chunk**: `furnBroken_` is reset in the scene setup (`roadsSetupCall` prefixes `furnBreakReset()`, after setupVehicles so the debris reservations survive its `d = VehDebris()`), and every chunk or box the road stream builds re-applies them. Collapsing writes the chunk's vertices through `BagArray::span` (a content stamp) and bumps `bboxVersion`; never rebuild the chunk for it.
  5. **Debris is the vehicles' debris pool**, untextured (`tex == nullptr`, its own batch created at reset), shared with lost car panels: a change to `VehDebris`, `updateVehicleDebris` or `renderVehicleDebris` changes both. The speed loss is written between `dmgPreV` and `updateVehicleDamage`, so it reads as an impact (vehicle damage rule 1) - a big loss can dent the car, which is intended.
- **Road Texture Generator** (`src/roadtex.cpp` + `roadtex_ui.cpp`, docs/road-textures.md): host-only (no GL, no ImGui, no `project.hpp`) and deterministic. `generate(RoadTexParams)` makes asphalt / setts / gravel / dirt / paving slabs / brick pavers RGBA (the `Surface` enum is stored by number in recipes: append only) with per-line-type markings (centre, dividers, edges: style, colour, width, dash/gap) laid out ACROSS U, periodic noise, and dashes that divide the 4-unit V repeat (`quantizeDash`); the intersection variant is isotropic and tiles in U too (32-unit world mapping), and `pavement=1` is the same on a 2 x 2-unit tile (slab grid snapped by `slabGrid`). `writeAssets` writes `res/materials/roads/<stem>.png` + `.mtl` + the editor-only `.roadtex` recipe (key=value, `toText`/`applyKey` - the CLI parses the same keys; texbake skips `.roadtex`, `assetSidecars` carries it). `seedProject` is called by `project::create` (six presets, incl. `pavement-slabs`), and Insert > Road defaults to `road-2lane`/`road-junction` when they exist. *Tools > Road Texture Generator* (window key `roadtex`); its Apply buttons set the selected Road's `roadTexture`/`roadIntersectionTexture` through `commitChange()`. Headless twin: `--road-texture`.
- **Draw road tool, road presets, bridge height handles** (`roaddraw.cpp` + `roaddraw_ui.cpp` + `roadpresets.cpp`, docs/roads.md "Drawing roads", "Road presets", "Height handles"). The roadtex rule: EVERY decision is host-only and pure - `roaddraw::Snapper` (snap to a road end, a centre line, a 15-degree step from the previous segment or from the snapped road, the grid; centre lines sampled exactly as `findNodes` samples them, so a T end lands ON the polyline the planner tests), `finish` (a new road, or a road END carried on in line with the same look), `commit` (the object, the preset, on-demand materials, bridge heights shifted on an extension), `verticalHandleY` (the handle drag) and `roadpresets::apply`/`fromRoad`/`ensureMaterials` - shared by four callers: the viewport tool (`App::roadDrawViewport`, which only maps the mouse and draws), `--draw-road`, the AI tool `draw_road` (chat_ui.cpp) and `--vehicle-check` "road drawing". Presets are DATA (the built-in table in roadpresets.cpp, plus `ProjectSettings::roadPresets`, format 133 - project.hpp includes roadpresets.hpp for it, so roadpresets.hpp must never include project.hpp). A preset never overwrites a material file that exists. Two traps: the Preferences window keeps a COPY of the settings and writes it back whenever it differs, so "Save preset" updates `prefSettings_` too, or an open Preferences window silently drops the preset next frame; and the tool must veto the picker and the rubber band (`roadDrawOwns`/`bridgeHot` in app.cpp), or the click that places a point also deselects the road.
