# AI features: flow-graph generation, the AI Assistant, AI support files

Read when you touch `aigen.cpp`, `aichat.cpp`, `chat_ui.cpp`, `aisupport.cpp`, `ai-support/`, add an Assistant tool or `set_object` property, or a CLI flag for agents (`--dump`, `--list-nodes`, `--dump-graph`, `--apply-graph`, `--ai-graph`, `--add-ai-support`, `--chat-prompt`, `--search-docs`; docs/ai-tools.md).

## Flow-graph generation (`aigen.cpp/.hpp` ~1.1k+160, docs/ai-flow-graph.md)

- `systemPrompt()` is built live from `flowAllNodeTypes()` + the project's referencable names (new nodes self-document: pins/params from registry flags, semantics from `FlowNodeType::desc` and the tips). `nodeCatalog`/`nodeCatalogLine` are the catalog.
- `Generator` runs the backend (claude/codex/copilot CLI via a stdin temp file, OpenAI via a curl config file), each as ONE completion with its own tools, session files and project instruction files OFF, from a neutral CWD (the prompt is the whole contract). Claude and Codex CLIs are asked for JSON/JSONL event output so `Usage` carries the model's OWN token counts (and Claude's cost), raw text as fallback when an envelope changes shape. **The Codex reply arrives in a FILE** (`-o`; stdout is progress), so it must be read before `cleanup()` deletes the temp files - a trap for any future backend answering into a file on a worker thread inside a kill-on-close Job Object (cancel kills the tree).
- `parseGraph()` extracts/validates with the same link pin rules the editor prunes by (incl. `flowExecOutCount`) + auto-layout; `appendGraph()` merges. `aigen::repairJson` (below) lives here.
- Config = `aigen::Config` on `EditorConfig` (editor.ini `aiBackend`/`aiModel`/`aiThinking`); modal `App::drawAiGenerateModal`.

## The AI Assistant's brain (`aichat.cpp/.hpp` ~2.1k+380, docs/ai-chat.md)

Host-only (no ImGui/GL/App), so prompt, parser and read tools run from a harness.
1. **The skills are `docs/*.md` themselves**: every page is embedded by `cmake/embed_docs.cmake` into `docs_gen.hpp`; the prompt carries only an INDEX (H1 + first sentence, `describeDoc`) expanded with `read_doc` (a ~21 KB prompt does the work of ~780 KB). A page joins by existing; the only constraint is the `)TYRAXDOC"` raw-string delimiter.
2. **The write surface is the project's OWN serialization**: `get_section`/`set_section` = `project::sectionJson`/`applySectionJson` (all sections - 26 today - readable/writable with no per-collection tool; a new section is covered automatically); `set_object_json` uses `objectJson`/`parseObject`. A blob is TOTAL, so `shrinkReport` refuses a write that makes any top-level ARRAY shorter unless confirmed (pure JSON; knows no section).
3. **`tools()` is the ONE tool table** (prompt catalog, `validate()`, both executors). `ToolKind` splits them: Read tools here (`runReadTool`, pure function of `const Project&`), Edit/Command tools in chat_ui.cpp. `objectProps()` is the same for `set_object`'s property list.
4. **Tiered search** (`searchDocs`): lines holding every term, PLUS lines of PAGES holding every term somewhere (capped per page), and only if both are empty any line with any term (labelled loose). Page name/title matches get a large bonus (otherwise "VRAM budget" answered with one docs-index line while gs-vram.md was never reached).
5. **`parseReply` never fails** (three tiers): a non-envelope reply is prose; an envelope that will not parse is REPAIRED first (`aigen::repairJson` re-escapes any `"` not followed by `, } ] :` plus lone backslashes, run on the WHOLE reply because the stray quote also unbalances `extractJsonObject`'s brace scan); `salvageSay` reads the prose out and drops the calls as last resort. `json::parse` did NOT reset its output value (a retry appended to the abandoned attempt - fixed in json.cpp; a trap for every retrying caller). Repair only text a MODEL wrote - an unparseable project file is reported, never guessed at.
6. **Procedural tools** (`get_proc_graph`/`set_proc_graph`/`list_proc_nodes` + `bake_volume`): `procNodeCatalog` derives from `procNodeTypes()` (`.desc` + every `.tip`); wire format `project::procGraphJson`/`parseProcGraph`; `add_object` type `scatter` routes through `App::addScatterVolume(false)`.
- **Context accounting/compaction**: `overBudget` must be decided on the UNTRIMMED conversation (`transcript()` trims to just under budget by construction, so comparing its output never fires); `contextStats` renders twice (sent vs full) and `transcript` reports dropped messages. `compactableCount` picks the latest User index that leaves a tail (falls back to the last one) - walking down from the tail found index 0 in a one-turn conversation and never compacted. The CURRENT turn is never trimmed or compacted.
- **Chat store** (`chatDir`/`saveChat`/`loadChat`/`listChats`/`pruneChats`): one JSON per conversation under `<configDir>/chats/<projectId>/` (machine-global: a conversation is the person's, not git's or the collaboration wire's). No timestamp in the file (mtime -> `chatAge`); written temp-then-rename (saved after EVERY turn). Tool arguments stored as VALUES (`json::write` exists only for this).
- `projectSummaryJson` = what `--dump` prints. Value coercions `numberOf`/`boolOf`/`stringOf` are shared with the property executor (a model's `detail: "4"` once read as no value).

## The acting half (`chat_ui.cpp` ~1.8k)

- Owns the step loop (`aiChatTick` from `drawUI`: consume a reply, run its tool calls, hand results back, up to `kChatMaxSteps` (8) rounds per user turn) and every Edit/Command tool (needs `project_`, `commitChange()`, selection, window flags).
- One tool call = ONE undo step ending in `commitChange()`, never `saveAll()` (`save_project` is the only writer, only when asked). Use the editor's own verbs (`addObject(type, false)` / `addModelObject(..., false)` for snap and naming; `deleteSelectedObjects` - it takes a volume's baked chunks; the Project panel's scene-switch sequence; a tool standing in for a menu item calls that item's verb with `commit = false`). A tool that cannot comply REPORTS WHY with names that would work (`aichat::noSuchObject`).
- **`build_game` PARKS the turn**: `runChatTool` starts the Runner and sets `chatBuildWaiting_`; the loop does not send the next request; the top of `aiChatTick` polls the Runner each frame and appends the outcome (+ tail of `logOut_.text` on failure) to the tool result before resuming. Any long-running tool wants this shape. A `run` build parks TWICE: build, then until `bin/livedbg.bin` appears (not `bin/log.txt`, whose first lines are engine init). `refresh_generated` needs no gate; `press_pad` uses `livepad::parseScript` + `padScriptTick`. The game-is-up wait uses `LLONG_MIN` for absent file times (devkit-runner-and-network.md).
- **Cost readout**: `ctx` is an ESTIMATE (4 bytes/token) of a request not yet sent; session totals are `aigen::Usage` from the backend; a backend reporting nothing (Copilot CLI) shows "reports no usage". Compaction is its own request (`chatCompacting_`, own small prompt); its reply is never appended as an assistant message; a failure is non-fatal.
- History: `aiChatPersist()` after every turn + the `##chathistory` popup; `chatFile_` is the current conversation's file (later turns overwrite it); `aiChatReset`/`aiChatOpen` persist before replacing. `chatAllowEdits_` (editor.ini) = read-only switch (non-Read tools refused, model told).
- **Clipboard**: text = `aichat::messageText`/`conversationText`, NOT `renderMessage` (model-addressed). Gesture = click on the message: `clickToCopy` draws the body in a group, puts a full-width `InvisibleButton` labelled `"Copy message"` over it (a `##` label is untargetable by `--ui-script`), paints `theme::hoverAnim` UNDER it via an `ImDrawList` channel split; the acknowledgement is keyed by the hit box's ImGui id (one Tool message draws several).
- A request in flight when a project closes is harmless: every tool checks `hasProject_`; the tick is the only place chat data meets `project_`.

## Adding an Assistant tool or property

Two edits, never one: a row in `aichat::tools()` (name, `ToolKind`, prose, args - the row IS what the model is told; write for a reader who has never seen the editor) + a branch in the executor its kind selects (`aichat::runReadTool` for Read; `App::runChatTool` for Edit/Command). A `set_object` property = a row in `aichat::objectProps()` + a branch in `App::applyChatObjectProp` (a row without a branch is reported as unhandled - honest, still a bug). Maintenance-free and to be kept so: the documentation index, the object type list (`primitiveTypeName` over `kPrimitiveTypeCount`), and the two node catalogs (`aigen::nodeCatalog`, `aichat::procNodeCatalog`) - hence mandatory `.desc` + tips. A tool handing the model an editor structure uses the project's serializer (`objectJson`, `sectionJson`, `procGraphJson`). Check with `--chat-prompt` (prints exactly what the assistant is told).

## AI support files (`aisupport.cpp/.hpp` ~130+35, docs/ai-support.md)

Installs AI-assistant files into projects: content authored in `ai-support/` (markdown, single source), embedded by `cmake/embed_ai_support.cmake` into `ai_support_gen.hpp`, `{TYRAX_EXE}` substituted at install; rewrite gated by a "Generated by TyraX" marker in the file head (below SKILL.md front matter), searched in the first **4 KB** (at 512 B a long `description:` pushed a marker to byte 829 and the skill silently stopped refreshing). Hooked into the New Project modal, Project Preferences and `--add-ai-support`. **Codex is a second DESTINATION for the Claude files** (`.agents/skills/` + `AGENTS.md` with self-references rewritten, like this repo's mirrored skills), never a second copy under `ai-support/`. **When the generated-project format, flow-graph model, menu stylesheets or CLI change, update `ai-support/` in the same commit.**
