# Devkit hooks in the engine: VU1 packet tap, EE crash handler, free-RAM probe

Read when: you touch `stapip_vu_tap.*`, `debug/crash_handler.cpp`, `Info::getFreeRAMSize`, or need to capture/decode VU1 traffic or an EE exception. Docs: docs/devkit.md. The GS-pass probing method is in gs-state.md.

## VU1 packet tap (`renderer/3d/pipeline/static/core/stapip_vu_tap.{hpp,cpp}`)
- Engine side deliberately tiny: a **null function pointer** `Tyra::g_vuPacketHook` and the branch testing it in `StaPipQBufferRenderer::sendPacket()` (once per bag flush, never per vertex). Capture lives in the generated game's devkit TU → release builds link none of it.
- **`g_vuMemHook`**: called after the send once VIF1 and the program are idle, with all of VU1 data memory — how the editor reads what the program PRODUCED (GIF packets staged for XGKICK). Costs a pipeline stall → devkit installs it for one frame and uninstalls from inside the callback. VU1 memory holds only the **last** MVP uploaded, and one flush carries several meshes in one chain → pairing input with output needs a single-bag flush plus the object-data chain (not done yet; was PROGRESS 196).
- Chain walking: REF tags are ONE quadword (advance 1), inline `cnt`/`next` advance `1 + qwc`; the hook copies each referenced block along (dereference on the EE while live). See submission-dma.md.
- The tap names the program each mesh runs (`program @<addr>`), useful for shrinking the resident set (vu1-microprograms.md).

## EE crash handler (`debug/crash_handler.cpp`, `crash_handler.hpp`)
Turns a CPU exception into a report. Built on ps2sdk **libeedebug** (`ee_dbg_install` + `ee_dbg_set_level1/2_handler`, hands a C handler the whole `EE_RegFrame` — no hand-written stub).
- **Own TU, linked only when someone calls `CrashHandler::install()`** (devkit layer does). `libtyra.a` is an archive → games that never install carry zero bytes. No global constructors, no references from other engine code.
- **Minimum work in exception context**: copy the frame, scan the stack for plausible return addresses, set `frame->epc` to a trampoline, return. The report is written from the trampoline (stdio + IOP-served `host:` work again). File I/O inside exception context turns a crash into a hang.
- **Install LEVEL 1 ONLY.** `ee_dbg_install(2)` never returns (drops interrupts, rewrites the error-level vector at 0x80000100 under the running machine) — froze every debug build with it on, hardware and PCSX2, nothing logged. Level 2 is only NMI/cache error.
- **The install hooks causes regardless of your handler table**, and a hooked cause without a handler loops forever. From disassembling `libeedebug.a` (no sources): `ee_dbg_install(1)` routes causes **1..3** via `SetVTLBRefillHandler` and **4..7 + 10..13** via `SetVCommonHandler`; its vector **always ERETs** (never chains to the saved kernel handler — that copy is only for `ee_dbg_remove`). Unhandled hooked cause = return to the faulting instruction unserviced; fatal for TLB refill. So the handler hands causes 1..3 straight back with `SetVTLBRefillHandler` after installing. Causes 0 (Interrupt), 8 (Syscall), 9, 14, 15 are never routed (narrowing the registered list alone never fixed anything). `ee_dbg_set_level2_handler` bounds-checks `cause < 4`.
- **A crash takes the screen** (`init_scr`/`scr_printf`) before idling: an assertion may halt quietly (editor surfaces it), an exception may not (frozen frame = hang).
- Verified on hardware 2026-07-29: forced signed-overflow `add` → `CRASH: Arithmetic overflow`, `bin/crash.txt`, `--symbolize` hit the exact source line. **PCSX2 cannot produce EE exceptions** (overflow, illegal opcode, write to 0, misaligned load all pass) → catching is hardware-only.
- An exception taken with `Status.EXL` set happened inside interrupt handling; EPC names the interrupted main-thread instruction (submission-dma.md, ISR experiment).

## Free-RAM probe (`Info::getFreeRAMSize`) — a measurement, not a sensor
Only way to ask this allocator what's left: claim every free block until malloc refuses, sum, free the chain. It used to start at the TOP BIT of `size_t` (malloc 2 GB on the EE: eight refusals first), free the block that worked, refine upward, allocate the refined size AGAIN; when that failed, recovery cleared the LOWEST SET BIT — zero for a single-bit size → "no block", sum stopped at the first → HUD `MEM 32.0/32 MB` with 13.6 MB free, Debugger *Measure now* showed nothing. Now starts at the console's 32 MB and keeps the block that worked (1.85.1). Prove such probes against a plain `malloc`/`free` ladder logged at the same instant; report a 0 as a failure.
