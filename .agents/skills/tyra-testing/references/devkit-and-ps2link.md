# Devkit channels, real-PS2 / ps2link, debug-state, release audit

Read when: you need "what is the owner debugging", probe the Live Debugger snapshot from a script, deploy/stop on a real console (or ps2link in PCSX2), a console hangs or a channel goes dead, or you prove a release build is devkit-free.

## What is the owner debugging? `--debug-state`

Never guess project paths or `Get-ChildItem -Recurse` the disk.
```powershell
build\tyrax-editor.exe --debug-state [--verbose] [projectDir]
```
Per project, live devkit artifacts in `bin/` with age, decoded inline (`vucap.bin` → *"frame 661, flush 2/9, 16 mesh(es), 94 tris in, 512x448"*; `livedbg.bin` → *"frame 1111, scene 0, HALTED"*); last line = freshest artifact on the machine. Then `--dump-vucap <dir>` or `bin/log.txt`. Also lists every `ps2client` with its console (`-h`) and game (`execee host:<name>.elf`).

Sources:
- **Running editors publish themselves** (`devsession.hpp`): `%LOCALAPPDATA%\tyra-editor\sessions\<pid>.ini` (`$XDG_STATE_HOME/tyra-editor/sessions/` off Windows): open project, build profile, live/halted + frame, **transport** (`pcsx2`/`ps2link`). Liveness = heartbeat (~4 s); a stopped one shows as `stale`, not hidden.
- `editor.ini` recent list (`%LOCALAPPDATA%\tyra-editor\editor.ini`, machine-global): entry 0 = last OPENED; `--new`-only projects absent; once missed an open project (unreproduced).
- Default projects folder (`~/TyraProjects` unless moved). Anything else: pass `projectDir`.
- A running game beats all of it: `Get-CimInstance Win32_Process -Filter "name='pcsx2-qt.exe'" | Select-Object CommandLine` → `-elf <projectDir>\bin\<name>.elf`. The editor's command line carries its project; `MainWindowTitle` = `TyraX - <project>`.
- **Never kill pcsx2/tyrax-editor by name** — the owner may be using it (`cannot open output file tyrax-editor.exe: Permission denied` = an editor is open; ask, or link a check binary under another name). `platform::killByName` is gone; use `platform::processesNamed(name)` + `platform::killProcess(pid)` and decide by command line (unreadable command line = never a target; cwd would be sharper but Windows can't read it).

## Live Debugger as a test instrument (docs/live-debugger.md)

- Debug build + *Live Debugger* on: game writes `bin/livedbg.bin` every 6 frames (25 over ps2link): node hit counters, recent-fire ring, flow variables, save values, halted flag; reads `bin/livedbg.cmd` (breakpoints, halt/step, force-fire). Layouts in `src/livedbg.hpp`; key → object/node map in `src/gen/livedbg.sym`. Editor and a probe must not both drive `livedbg.cmd` (editor rewrites it when missing/changed).
- **Prefer a C++ probe linking `src/livedbg.cpp`** (host-harnesses.md link line): `loadSymbols` + `readSnapshot` → per-node hits with ids/types, watch variables BY NAME, armed timers; `hashMatch` = ELF symbol table matches. A hand-rolled Python reader can disagree with the format. Pattern (84-node expansion, entry 231): wire each mechanism to an unattended trigger writing a **distinct predictable integer** into a flow variable, read all back at once. Write commands to prove Pause freezes counters, Step advances exactly one frame, force-fire runs a branch (entry 191).
- Not bugs: a trigger with an **unwired** exec output has hit count 0 (empty chains aren't instrumented) though its outputs work; an event payload trailing the live counter by one = **one-frame bus latency**.
- Snapshot **v4** ends with a 64-byte stats block (FPS, flushes/qw/verts to VU1, GS VRAM free/low-water/largest/resident, object counts, free EE RAM) + one 8-byte row per bag flush (qw, unpacks, verts, program) (PROGRESS 205; verified by a ~60-line Python probe cross-checking VRAM figures against `VRAMSTAT` and flush-map vertex counts against `--dump-vucap`). With the server yours and the editor closed, a probe can pin each flush in turn (traced "my model shows 2 meshes" to a bag flush full of terrain, PROGRESS 204). v3 still parses (no stats) → missing stats = "was the GAME rebuilt?". Free EE RAM only when asked (flags **bit 5**; allocates every free block). Command flag bits: 3 = arm VU1 capture, 4 = flush index in bits 8–23, 5 = free RAM, 6 = capture frame.
- Devkit cadence overrides: round-trip all five cadence fields incl. missing/default/out-of-range; generate automatic, overridden, disabled and release variants; overrides gate host I/O only, never graph execution or replay/pad updates. Preferences input/save/reopen, boot the debug game, verify snapshot frame deltas, halt/resume, capture at a slow command interval; longer report intervals must not repeatedly flag a live game as hung.

## Script debugger (docs/script-debugger.md)

Never launch PCSX2 through the Runner for this (a visible window on the user's screen): run an ISOLATED hidden instance with PINE on a private slot (`pcsx2-capture.py`'s `prepare_datapath` + `hide_windows_hook`, slot e.g. 28311) and **close your own PINE socket** after the boot check - PCSX2 serves one PINE client, and a held one reads as "PINE closed" to the server. Then:
- `tyrax-editor --debug-serve <dir> --pine-slot 28311` (prints state lines; `[gdb] waiting for GDB: ...` = ready).
- GDB batch inside WSL against `127.0.0.1:<port from .vscode/tyrax.json>`: start the script with `maint set target-async off` or `continue` returns at once ("Cannot execute this command while the target is running"). `break motion_math.cpp:31`, `continue`, `info locals`, `next`, `print *this`, `set var`.
- GDB/MI the way VS Code drives it: `-gdb-set mi-async on` before `-target-select`, then `-exec-interrupt` must stop with `signal-received` in `tyraxScriptDebugPoll`. MI emits no `*stopped` after `-target-select`.
- The real thing without a window: drive `~/.vscode/extensions/ms-vscode.cpptools-*/debugAdapters/bin/OpenDebugAD7.exe` over DAP (initialize, launch with the config `debug.js`'s `toCppdbg` produces, setBreakpoints with the WINDOWS path, configurationDone, stopped, stackTrace/scopes/variables, next, pause, disconnect). A failed `launch` RESPONSE carries the reason - print failed responses, not only output events.
- Step speed: a DAP bench that times N `next`s plus the stackTrace/scopes/variables VS Code asks after each (median F10 ~0.1 s; was 1.8 s before range stepping). `TYRAX_GDB_TRACE=<file>` on the server gives per-packet and per-stop timings. A hidden rig that stops advancing is often PCSX2 PAUSED: the user ini pauses on a gamepad disconnect ("System paused because controller XInput-0 was disconnected" in emulog) - `pcsx2-capture.py` now writes `PauseOnControllerDisconnection = false`; PINE `MsgStatus` (15) tells.
- The F5 decision flow without a VS Code window: a Node harness that `require`s `tools/vscode-tyrax/debug.js` with a stubbed `vscode` (withProgress runs the callback, showInformationMessage answers) and calls `new Provider().resolveDebugConfiguration(...)`. Keep the harness alive after it resolves (it owns the spawned `--debug-run`). Measured 2026-10-29: open editor + debugger off -> enabled, rebuilt, ready in 48 s; no editor + off -> asked, enabled + saved, ready in 44 s; second F5 10 s; changed code with the editor serving -> rebuilt + relaunched, ready in 25 s; changed code with a headless server -> old one killed, ready in 24 s. Prove the NEW code runs: add `volatile int tyraxProbe = 42;` and look for it in the DAP locals. These runs open a VISIBLE editor/PCSX2 - only with the user's OK.
- **Real VS Code**: `node tools/vscode-tyrax/test/integration/run.js <projectDir>` (F5 -> breakpoint -> rewrite `tyraxProbe` -> restart -> PASS when the new session stops with the new value). Run the MATRIX: `TYRAX_IT_RUNNING=1|0` x `TYRAX_IT_RESTART=workbench.action.debug.restart|tyrax.rebuildAndRestart`, and check the session count in the log - a restart of a RUNNING game was the one users hit (VS Code cancels it), a parked one is what a naive test does. Traps: a fresh profile's workspace-trust dialog blocks F5 forever (the runner turns trust off); stable VS Code refuses extension tests next to a running instance unless `--user-data-dir` differs (it does); read the test's own log, not Output panels; a LEFTOVER PCSX2 of another project on PINE slot 28011 makes the server wait forever on the wrong game - the server now says "not this build" (1024 .text words compared). Opens visible windows: only with the user's OK.
- Fixture: a copy of examples/script-cookbook with `"scriptDebugger": true` under settings; EaseShowcase::onUpdate (motion_math.cpp:31) runs every frame. Release audit both ways: debug ELF has `TXDEVKIT-scriptdbg`, release copy is clean and has no `script_debug.gen.cpp`.

## Release audit: `--audit-release <dir>`

Reads the built ELF: exit 0 clean / 1 leaked, prints text/data/bss. Every release build runs it. **Negative-test**: a DEBUG ELF must fail and name findings (entry 193). Also flags a **measurement build** (1.123.2): scans `.rodata` for `FTCLIP`, `FTPKT`, `STAPIPRET`, `STAPIPMISS`, `STAPIPBAKE`, `VRAMRES`, `VRAMEVICT`, `ROADINDEXVERIFY`, `WHEELBAKE` → `measurement build - .rodata`. Negative-test: build with `TYRA_WHEEL_REBUILD_REPORT=1` (generated game) or `TYRA_FRAME_PROFILE=1` (engine) → finding appears, then disappears. **Add the tag when you add a gate.**

## Real PS2 over ps2link

- Prefer `--build <dir> --run-ps2 <ip>` (creates the marker, spawns the file server). The `ps2client` the RUNNER spawns IS the `host:` server: closing the editor freezes every devkit file at its last write and `livedbg.cmd` is never read (symptom: `livedbg.bin` stops while the console answers `ping`). Fix = redeploy (*Run on PS2*, F6).
- A missing first `[ps2]` line doesn't prove `execee` failed (tty reply may be lost): Runner waits 15 s, reports an unconfirmed launch, keeps `ps2client` alive. Never kill it to "clean up" — removing `host:` from a running game gives checkerboard text, missing models, silent audio. Use *Stop on PS2*.
- Since 1.22.0 deploy/stop/clean reap only servers the Runner owns (own handle; a stale one of the SAME project by command line; an orphan no editor claims) and **refuse**, naming the holder, otherwise (docs/ps2link-setup.md "One file server at a time"). Before, a machine-wide `taskkill /IM ps2client.exe` killed other sessions' servers while `[ps2]` UDP log lines kept arriving (UDP bypasses the file server — the live transport hides the dead one).
- **Host the server yourself** for scripted probes (editor closed, no two writers on `livedbg.cmd`). A still-running game needs no redeploy — it blocks on `host:` and resumes:
```bash
cd <projectDir>/bin && ../../tools/ps2client/bin/ps2client.exe -h <ps2-ip> listen
```
  (Verified: 20-minute orphan came straight back.) Game actually gone: `ps2client -h <ip> -t 10 reset`, then `ps2client -h <ip> execee host:<name>.elf` with cwd `<project>/bin` (that process = the session's file server). Use the **main checkout's** ps2client (a worktree path is a new binary to Windows Firewall → unseen prompt).
- **Don't send ps2client COMMANDS at a console with a game loaded**: any connecting client is conscripted as file server; `reset`/`dumpmem` returned -1; with a `listen` attached a command got through and froze the game. Reliable: nothing attached, `reset` (exit 0 only when free), `execee`. On the pinned build `dumpmem` → `EE: pkoDumpMem() write failed` (zero-byte file) and `scrdump` exits 0 writing nothing — want them? patch ps2link (`tools/ps2link/` clones pinned upstream, applies `tyrax.patch`, builds with the editor's native toolchain (WSL on Windows) or Docker via `build.sh`/`build.ps1`; revision = `TYRAX_REV` in the patch's `ee/Makefile`; docs/ps2link-setup.md). Rejected theory (don't retry): EE passing newlib `O_*` where the wire wants `FIO_O_*` (`O_RDONLY` = 0, `FIO_O_RDONLY` = 1) — asset `fopen("rb")` works through the same path.
- ps2link r2: fixed host: thread spin on closed socket, stream desync, inverted `SifIopSync()` in `pkoReset()`. **r3** adds `spu2Silence()` → *Stop on PS2* no longer deploys `tools/silencer/silencer.elf` or sleeps ~7 s (silencer = manual fallback for pre-r3). Check banner `TyraX ps2link r3` and log `SPU2 silenced`.
- **SPU2 startup hang (r8)**: `spu2Silence()` establishes SPU2 bus mapping/timing before accessing sound registers; PS2Link does not load `libsd` first. Verified on SCPH-70004 via FreeDVDBoot/uLaunchELF: startup, game audio, Stop and redeployment, with no leftover audio. For changes here, check both startup and Stop/redeployment: audio must stop and return in the next game.
- **ps2link in PCSX2**: a second, `-portable` emulator (own `inis/bios/logs`) with **DEV9 bridged** to the LAN boots `ps2link.elf` and answers real `ps2client` (`reset`, `execee`). Wedge = `Stop-Process`. Measured 2026-07-31: r4 falls to BIOS browser and drops off LAN, r6 comes back. Gotchas: `[DEV9/Eth]` section, `EthDevice` = bare adapter GUID, `host:` served by PCSX2 HostFs relative to `-elf` dir (NOT ps2client), ping proves nothing (docs/ps2link-setup.md "Testing a change without a console"). Cannot produce EE exceptions (r4 `BadAddr 8` replayed fine) — faults/`crash.txt` stay hardware tests.
- **ps2link unit layer**: `tools/ps2link/test/run.ps1` (`run.sh`) compiles the REAL patched `build/iop/net_fio.c` against stubs in `test/shim/` with a scripted fake socket (framing, EOF, short reads, buffer clamps; `#include "net_fio.c"` to reach static `pko_fileio_sock`). `-Pristine`/`--pristine` runs the same tests on untouched upstream, which must FAIL (7 of 18; three spin past a 2000-call `recv()` ceiling). Use for any `host:` protocol change; threads/SIF/GS stay console-only.

### Manual launch: require the resident-IOP marker

If launching by hand, first create and verify an **absolute** `PROJECT/bin/ps2link.run` containing `ps2link`; cwd = `PROJECT/bin` (a cwd already ending in `bin` must not get another relative `bin/`). `-ps2link` on execee alone is insufficient with this crt0. Missing marker resets the IOP, removes host fs/network, may need a physical reboot (UDP poweroff can't repair). Don't chain a failed marker write into `execee`; PowerShell: `-ErrorAction Stop` + `Test-Path -LiteralPath`. **`--build --run` (PCSX2) deletes `bin/ps2link.run`** — recreate (`printf 'ps2link' > <project>/bin/ps2link.run`) and keep `execee` inside the script that checks it (an `exit` guard in a `;` chain is bypassed). Stop an emulator serving the same project before hardware captures (its fresh `livedbg.bin`/`frame.tga` disguises a disconnected console).

### Two console failures that look alike

- **Empty ps2client log, not even `loadelf:`** = RACE: ps2link reboots the IOP on `reset`, an `execee` sent in that window is a lost UDP packet. Kill the client, resend `execee` WITHOUT another reset. Recipe: `reset`, wait ~8 s, `execee`; empty after ~20 s → kill + resend `execee`.
- **`freepad: DMA Busy ... ret = 0` repeating** (or empty log, `livedbg.bin` stuck at frame 1) = IOP wedge; only a power cycle clears it. Frequent from 2026-09-22 when resetting a console running a DEBUG build (suspect: reset during devkit `host:` I/O; root cause unknown — don't write one). After a power cycle send a **bare `execee`** (probe-reset + launch-reset failed twice). Budget one clean boot per power cycle for debug builds; measure on devkit-off builds (reset cleanly, and are the player's frame).
