# Code generation and generated-file ownership

Read when you touch `templates.cpp`, `game_templates.inc`, `project::refreshGenerated`, add a generated file or a bake output, change `.gitignore` templates, or need to know what a generated project contains.

## Where codegen lives

- `templates::generate(Project)` (templates.cpp, ~34.9k lines) returns `vector<File>` (relativePath + content): scene tables, game sources, flow-graph compilation, Makefile/compose, `.vscode/c_cpp_properties.json` (always overwritten), `.vscode/extensions.json` (recommends `tools/vscode-tyrax`), `THIRD-PARTY-NOTICES.txt` (attribution a shipped game carries; see LICENSE-EXCEPTION.md).
- Game implementation templates: `src/game_templates.inc` (~27.6k lines, included by templates.cpp), split into the shared runtime header `TPL_GAME_RUNTIME_HPP`, the two main heads `TPL_GAME_MAIN_ORBIT` / `TPL_GAME_MAIN_FPP`, and five shared subsystem bodies `TPL_GAME_SCENE` / `_LIGHTING` / `_COLLISION` / `_VEHICLES` / `_PHYSICS` (the split is for parallel compilation, not by topic: e.g. `updatePlayerWalker` and `buildStaticBatchList` sit in `TPL_GAME_COLLISION`, `renderScene` in `TPL_GAME_PHYSICS`). The game header is still two copies in templates.cpp: `TPL_GAME_HPP_ORBIT` and `TPL_GAME_HPP_FPP` - a struct member is added to BOTH.
- Generated project layout: `src/terrain_game.cpp` (the marker-owned main) + `src/gen/game_{scene,lighting,collision,vehicles,physics}.gen.cpp` + `inc/game_runtime.gen.hpp`. A loop-level fix usually has two homes (ORBIT and FPP heads).
- Shared helpers/types use named namespaces; mutable cache/state is C++17 `inline`; exported globals are defined once in the main. Generated table arrays used by inline pointer tables/helpers must have shared identity (`inline constexpr` / `inline const`), never private per-TU data. Keep preprocessing guards on moved methods (including the road oracle).
- The main stays marker-owned. An owned legacy monolith receives no shards; an owned split main must keep its shared-header include. `refreshGenerated` always refreshes all emitted shards/header and removes stale shards when a project returns to an owned legacy monolith. Historical example snapshots were split without migrating their manifests.

### Scene object data TU

- Authored object values (incl. baked scroller clones and empty-scene placeholder rows), object counts / identity hashes and conservative visibility proxies are defined once in `src/gen/scene_objects.gen.cpp`. `inc/scene_data.hpp` exports unsized `extern const` arrays + an extern count table with the same names/accessors.
- Moves, colours and ordinary object add/remove change only the data TU; features, scene-count changes and other derived tables can still invalidate consumers.
- Use `SCENE_OBJECT_COUNTS[scene]` / the scene-offset count, never `sizeof`/`std::size` on an unsized array. Arrays/counts are runtime read-only data, no longer `constexpr`: custom code using them at compile time must read at runtime. Keep `OCCLUSION_CULLING` constexpr.
- Preserve byte-identical writes and the object row emitter; no dynamic initialization; do not change layout/index order. Remaining runtime-setting work is measured in `docs/native-toolchain.md`; `make -j` already uses all logical cores.

## `project::refreshGenerated()` (project.cpp)

Runs at the start of every build (and `--refresh-gen`). Per file:

| Category | Marker / rule | Files |
|---|---|---|
| Always overwritten | first line `// Generated by TyraX. Do not edit - regenerated on every build.` | an EXPLICIT path list: `Makefile`, `docker-compose.yml`, `src/main.cpp`, `inc/terrain_config.hpp`, `inc/scene_data.hpp`, `src/gen/scene_objects.gen.cpp`, `inc/game_runtime.gen.hpp`, the five game shards, `.vscode/c_cpp_properties.json`, every devkit runtime, `src/gen/blss_interlock.gen.cpp`, `inc/daynight.gen.hpp`, `inc/vehicle_sound_loops.gen.txt`, ... plus `isVuGenerated()` VU outputs (stale ones are swept: Makefile.base globs `src/**.vclpp`) |
| User-ownable | first line `// Generated by TyraX. Delete this line to take ownership of this file.` | `src/terrain_game.cpp`, `inc/terrain_game.hpp`, `inc/controls.hpp`, `inc/scripts/script.hpp`, `inc/scripts/flow_nodes.hpp` - regenerated only while the marker line is intact |
| Written if missing | no marker (format has no room) | `THIRD-PARTY-NOTICES.txt`, `run.ps1`, `run.sh`, `windows-pcsx2.ps1`, `.gitignore`, `bin/.gitignore`, `obj/.gitignore`, `.gitattributes`, `COLLABORATION.md` - created once, never clobbered (authors append credits to the notices) |
| Merged | | `.vscode/extensions.json`: `templates::vscodeExtensionsMerged` ensures the editor's recommendations exist, keeps user entries, skips an already-complete file |
| Never written | | `user.mk`: the generated `Makefile` does `-include user.mk` AFTER `include $(TYRA_MAKEFILE)` and its extra-flags lines (so user `CFLAGS +=` beats the engine's `-O3`), and makes `$(OBJECTS) $(OUTPUT)` depend on it. `-std=gnu++NN` comes from `ProjectSettings::cppStandard` (`{{BUILD_CFLAGS}}`); `extraCompilerFlags`/`extraLinkerFlags` are emitted as `CFLAGS +=`/`LINKFLAGS +=` after the engine include (`{{EXTRA_FLAGS}}`); the same standard feeds `c_cpp_properties.json` |

Rules:
- **"Always overwritten" is a hand-written LIST, not a suffix rule.** A file added to `templates::generate()` and nothing else is written ONCE by `project::create` and never refreshed - it keeps creation-time settings. The Remote Pad's `live_pad.gen.cpp` shipped the devkit runtime into a RELEASE build this way (caught only by `--audit-release`). Add every new generated file to the list in the same commit as its generator.
- **A file in NEITHER list reaches only projects created after it existed.** `run.sh` was missing from 21 of 34 example projects that way. Anything every project should have belongs in write-if-missing.
- **"Rewritten" means "rewritten when bytes differ".** `writeFile` compares content first; that is what makes the game build incremental (a fresh mtime on `scene_data.hpp` recompiles most of the game). Never remove the check; never embed volatile content (timestamps, random ids, unordered-container order). **Binary bakes too**: `res/save/list.icn` went out through a raw `ofstream` and got a fresh mtime every build. Route new bakes through `writeFile` (bytes as `std::string`).
- **A baked asset folder needs a `res/.gitignore` rule AND a migration.** `TPL_RES_GITIGNORE` only covers new projects; the append-if-missing block at the end of `refreshGenerated` fixes existing ones (`/models/*.tmdl`, `/credits/pages/`, `/save/` arrived this way). The top-level `.gitignore` has the same block (`_backup/`, written by `--migrate`). `res/save/` is ignored (rebaked every build) while `res/hud/save-busy.png` is written only when missing and stays tracked/user-replaceable.
- **`.res-baked/gi/` is NOT an artifact** - only an explicit minutes-long bake produces it; codegen/texbake/viewport only read it. `TPL_GITIGNORE` spells `/.res-baked/*` + `!/.res-baked/gi/` (git cannot re-include inside an excluded directory, so plain `.res-baked/` makes the negation impossible).
- **A `res/.gitignore` of `*` + `!.gitignore` swallows the project** (it was the `--new` scaffold's rule once): invisible locally, "material file missing" on a fresh clone; 9 of 34 examples shipped zero tracked assets and `examples/mirror-room` lost `res/models/wobbler.glb`. After any `res/.gitignore` change verify with `git ls-files examples/<name>/res`, not `ls`.
- A conditionally emitted file is DELETED by `refreshGenerated` when it stops applying (e.g. `blss_interlock.gen.cpp`; menu state/list/description textures). Makefile.base globs `src/**/*.cpp` and the container rsync uses `--delete`, so the sweep reaches the build.

Consequences:
- Anything the game must know goes through codegen in `templates.cpp`, never by hand-editing a generated file.
- New generated files use `.gen.hpp` / `.gen.cpp`.
- Never make a template emit something that breaks projects where the user owns `terrain_game.cpp`: data into always-regenerated headers, behavior into ownable sources. A behavior switch that lands in ownable sources (e.g. `presentExtrapolatedFrame`, two heads + two header declarations) never reaches owned projects - correct, but say so in the doc.
- When something that was always scene 0 / always one value becomes configurable, grep the generated templates for OTHER uses of that constant (the boot path had scene 0 baked into `init()`'s player spawn and the boot loading screen, not only `loadScene`).

## Generated-output hygiene

- Output must stay `git diff --check` clean: emit optional comments/separators conditionally, no trailing spaces or blank lines when an empty table has no label/registration block.
- `examples/script-demo/` is a checked-in generated project; its generated files are only as fresh as its last rebuild. Regenerate (load + save + `refreshGenerated`, or `--build`) before trusting it as a reference.
- **Byte-identical regeneration** is the compatibility test for any codegen change that should not affect existing projects: build the previous binary into the SAME directory as the new one (`c_cpp_properties.json` and `docker-compose.yml` embed the editor's vendor path, so a baseline exe elsewhere shows two false diffs), `--refresh-gen` the same fixtures with each, diff the trees. Emit a new feature's constants only when it is ON (even `FEATURE = 0` changes every project's `scene_data.hpp`).

## Data-file twins (custom content loaded by `project::load`)

- `flownode.cpp`: `<project>/flow-nodes/*.flownode` -> global `customFlowNodes()` (`flownode::loadForProject`, called by `project::load` BEFORE graphs are parsed). Manifest: title/category/params, `in`/`out` pins, `exec_out`, `call`; behavior is an inline C++ snippet or `call = fn` into `inc/scripts/flow_nodes.hpp`. `writeExample` scaffolds the starter. docs/custom-flow-nodes.md.
- `screenfx.cpp/.hpp`: `<project>/screen-effects/*.screenfx` -> `customScreenEffects()` (`screenfx::loadForProject`, before placements are read). Manifest (title + up to four numeric params) + raw GS-blit C++ body. A `Project` references one only via `ScreenFxPlacement` (key + stack `layer` + `enabled` + params), placed in the UI Editor screen stack, codegen'd to `src/gen/screen_fx.gen.cpp` (`screenFxSource`/`screenFxHeader`), run via `RendererCore::applyCustomPostFx`. Unknown-key placements are dropped on load. docs/custom-screen-effects.md.
- **Header keys / `{placeholder}` / `{pN}` of both formats are mirrored in the VS Code extension's `SPEC` table (`tools/vscode-tyrax/extension.js`) and grammar** - change both (docs/vscode-extension.md). **A `tools/vscode-tyrax` change is not done until the `.vsix` is repackaged** (the committed package is what the editor installs; nothing rebuilds it): bump `version` in package.json, run `python3 tools/vscode-tyrax/package-vsix.py`, let it delete the old file, read the language list it prints.
- `ai-support/` is the content installed into projects (aisupport.cpp): **when the generated-project format, flow-graph model, menu stylesheets or CLI change, update `ai-support/` in the same commit.**
