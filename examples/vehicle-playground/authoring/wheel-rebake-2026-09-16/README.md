# Wheel re-bake skip — arms, harnesses and raw rows (2026-09-16)

The measurement archive behind [docs/wheel-rebake-skip.md](../../../../docs/wheel-rebake-skip.md).
Read that page for what the change is; this directory is what it was measured
with, so a re-run that disagrees can be explained rather than argued about.

## The two native harnesses

Neither links the editor or the engine. Both are plain C++ and run in seconds,
which is the point: they answer the two questions an emulator boot answers
badly — is the lifted arithmetic bit-identical, and is a skip a no-op.

```sh
g++ -O2 -std=c++17 -o equiv wheelbake_equiv.cpp && ./equiv
g++ -O2 -std=c++17 -o churn wheelslots_churn.cpp
./churn                            # random schedule,      shipped logic
./churn --no-trim                  # random schedule,      MUTANT
./churn --adversarial              # adversarial schedule, shipped logic
./churn --adversarial --no-trim    # adversarial schedule, MUTANT
```

`wheelbake_equiv.cpp` transcribes both bakes — the per-wheel one from
`vehicles@c4407798` and the hoisted one — and compares the raw quadwords over
200 000 random rigs, then replays 4 000 scripted frames against a full-rebake
oracle. Expected: `PASS (0 mismatching)` and `PASS (0 stale, 3049 rebuilt,
951 skipped)`.

`wheelslots_churn.cpp` models the bookkeeping instead of the arithmetic: cars
entering and leaving, slots reassigned, the vertex vector grown and trimmed, LOD
source swaps, checked against the same oracle plus the stamp contract (a stamp
may only be reused when bytes, length and address are all unchanged).

**The `--no-trim` mutant is why the `--adversarial` schedule exists.** On the
random schedule the mutant passes — the coincidence it needs never comes up in
60 000 frames — so a green run there proves nothing. The adversarial schedule
oscillates the participant list between three cars and one with nothing ever
moving, which produces it on demand:

| | random, 60 000 frames | adversarial, 2 000 frames |
| --- | --- | --- |
| shipped | PASS, 0 stale | PASS, 0 stale |
| `--no-trim` | PASS, 0 stale | **FAIL, 999 stale** |

999 of the 1 000 frames where the slots regrow, i.e. one frozen car per frame.

## The emulator arms

Two fixtures, two arms each. The arms differ in **one file** — the generated
`src/terrain_game.cpp` and its header — and in nothing else: every arm is
regenerated by the editor under test, then the control arm has that one file
replaced with the pre-change generation, so the baked assets, the scene, the
route data and every other generated source are common mode.

```powershell
# parked (deterministic - this is the fixture the pixel A/B runs on)
python ..\benchmark-district.py $env:TEMP\tyra-editor-test\whA --profile debug
python ..\benchmark-district.py $env:TEMP\tyra-editor-test\whB --profile debug
# moving (AI drivers driving; NOT deterministic, counts only)
python ..\benchmark-district.py $env:TEMP\tyra-editor-test\whAm --profile debug --keep-routes
python ..\benchmark-district.py $env:TEMP\tyra-editor-test\whBm --profile debug --keep-routes
```

`--profile debug` is required: `--capture-frame` needs the Live Debugger, which
`quiet-debug` and `release` switch off.

Each arm is then compiled with `tools\toolchain\native-build.ps1` **directly**,
not with an editor `--build`, because `--build` regenerates the generated
sources and would put the change back into the control arm.

**No frame times are recorded in this directory.** They are being taken on the
physical console; PCSX2 models no EE data cache and cannot price the trade.

## What the arms showed

Counts only; see the doc page for the readings and the driven oracle.

**Submission is unchanged - no counter moves at all.** One project directory,
release profile, two compiles swapping only the generated terrain_game, FTCLIP
armed. Triangles 40502 / 41176 / 16386 / 16720, vertices submitted 55602 /
57624 / 18057 / 19059, flushes 120 / 142.5 / 44 / 48, and packages cull / clip /
guard / out - identical to the digit, all four poses, 29 pose-aligned FTCLIP
lines matching line for line. Emulator saving from the same two runs: -2.20 ms
garage day, -2.21 garage night, -0.07 / -0.07 outer.

Read the counters APART, not as one total: `trianglesCull` counts a strip
package as `size - 2` and its guard-band subset as `size / 3`
(stapip_telemetry.hpp records the defect), so a package changing ROUTE moves the
triangle total with nothing drawn differently. `verticesSubmitted` is the
representation-independent one and it did not move either.

**THE TRAP THAT NEARLY MADE THAT A LIE.** The first run of this A/B returned a
perfect null - 0.0 delta on every counter - because `Copy-Item` carries the
source file's TIMESTAMP across, the swapped-in generated source landed older
than the object make had already built, make did nothing, and both arms ran the
same ELF: byte-identical, from sources differing by 332 lines. After swapping a
generated file, stamp it, delete the matching .o in the project AND the build
cache, and HASH THE TWO ELFs before reading anything. Here they are 7ADCF03D...
against 9A6786F9..., and the two runs also differ in frame time, which is the
second way to see that two builds happened.

**The skip, parked:** 0 of 900 car-submits rebuilt once the suspension settles,
0 of 900 stamped. The settling window rebuilds 172 wheels for 43 cars, 4.0 per
car - the per-wheel split never fired.

**The skip, driven:** 300 of 300 frames rebuilt while moving, all four wheels
every frame; 0 of 300 once stopped.

**The retained hit rate, parked garage:** 590/279 -> 646/223 and 614/295 ->
677/232, i.e. 67.9% -> 74.3% and 67.6% -> 74.5%, with identical totals. The
outer-road pose does not move by one package because it submits no wheel bag.

**`--keep-routes` did not deliver moving traffic here.** The benchmark's four
frozen poses never look at the two routed rivals while they are close enough to
draw a wheel bag - one that does come into view sits at LOD tier 2 with its
wheels baked in. The flag is necessary and still right; the fixture needs a
camera pose aimed at a route, which it does not have. The driven numbers above
come from the plain example driven with the Remote Pad instead.
