# Raw evidence: the baked VIF stream spike (2026-09-16)

The measured half of [docs/baked-vif-stream.md](../../../../docs/baked-vif-stream.md),
which is the format-and-cost spike behind the central change of
[docs/ee-submission-rearchitecture.md](../../../../docs/ee-submission-rearchitecture.md):
a wholly visible static mesh's whole per-frame VIF1 command stream emitted once
and replayed by a single DMA `REF` tag.

**No console was touched.** Everything here is PCSX2 counts and pixels, which is
all this question needs — the format is a correctness claim and the memory is
arithmetic. The milliseconds belong to a later round, and no number in this
directory may be turned into one.

## The knob

`TYRA_STAPIP_BAKED_STREAM` in
`vendor/tyra/engine/inc/renderer/3d/pipeline/static/core/stapip_qbuffer_renderer.hpp`,
**0 against 1**, one worktree, one project directory. Ships at 0.

Both arms additionally carry, identically:

| macro | file | arms | why |
| --- | --- | :-: | --- |
| `TYRA_FRAME_PROFILE` | `vendor/tyra/engine/inc/debug/frame_profile.hpp` | 1 | the `FTCLIP` line |
| `TYRA_STAPIP_BAKED_REPORT` | `stapip_qbuffer_renderer.hpp` | 1 | `STAPIPBAKE` / `STAPIPMISS`, and `chainQw` — which is compiled into the CONTROL too, or there is nothing to compare |

All three are measurement flips and all three ship at 0. Revert them before
committing; a `host:` write with a period inside a sampling window is noise with
a period.

## The recipe

```powershell
# 0. the editor, FROM THIS WORKTREE - see "The fixture trap" below
./build.ps1

# 1. the fixture, regenerated by the editor that will build both arms
python examples/vehicle-playground/authoring/benchmark-district.py `
       $env:TEMP\tyra-editor-test\bakeab
#    then copy in a .res-baked/ and bin/aomap, bin/aoatlas you already have,
#    so the first build is not a full asset bake

# 2. one arm at a time: flip the knob, build, keep the ELF
build\tyrax-editor.exe --build $env:TEMP\tyra-editor-test\bakeab

# 3. boot it yourself - NEVER --build --run, which reaps other worktrees'
#    emulators - and drive it with the pose file
powershell -File run-arm.ps1 -Elf <arm>.elf -Tag <arm>
```

`run-arm.ps1` is in this directory. It copies the arm's ELF into `bin/`,
**deletes every devkit artefact the previous arm left** (a leftover
`livedbg.cmd` is applied at boot and eats the first capture; a leftover
`frame.tga` is what the next `--capture-frame` reads back), launches PCSX2 on an
absolute path, waits for `bin/district-benchmark.csv`, holds garage day through
`bin/district-benchmark-pose.txt`, takes three `--capture-frame` images and
copies the game's `log.txt` out.

**The pose file is only read after the fixture's own 1 440 sampled frames, and
the CSV is written at exactly that moment** — so the CSV appearing is the "it is
safe to write into `bin/` now" signal, and nothing disturbs the sampling window.
Garage day (phase 0) is the pose to compare pixels at; the two NIGHT poses have
authored lamp flicker and twinkling stars and never settle.

## The fixture trap this round actually hit, and it is worth reading

The first pass of this A/B was run with the editor binary sitting in the **main
checkout's** `build/`. Its arms were internally consistent and its conclusions
survived — but its `FTCLIP` line read `cull=40175 … verts=55332` where
[`../package-ceiling-75-2026-09-16/ftclip-arms.txt`](../package-ceiling-75-2026-09-16/ftclip-arms.txt)
records `cull=38750 … verts=55836` for the same pose at the same engine tip.

The cause was **a stale editor binary**, which is the trap `tyra-testing` spells
out and which is invisible in every log: that binary predated the 72 → 75
package-ceiling change, so the fixture's generated `src/terrain_game.cpp` came
out carrying `stripRun = 72u`, and the roads and the terrain were tessellated
into 72-vertex runs. One grep settles it:

```bash
grep -n "stripRun = 7" <fixture>/src/terrain_game.cpp
#  stale editor:  const unsigned int stripRun = 72u;
#  this worktree: const unsigned int stripRun = 75u;
```

and the scene-load producer lines say the same thing out loud —
`ROADSTRIP … packages 526` / `TERRAINSTRIP … vertices 591 packages 9` for the
72-run scene against `470` / `588 packages 8` for the 75-run one.

**The thing that made it hard to see is the part worth remembering.** The
control capture hashed to `415f970f…73f1e` — *exactly* the hash the
package-ceiling round recorded for this pose — which reads as "same scene,
confirmed". It is not: that round's own evidence shows **both** its arms hashing
to that one value, because changing the strip run changes how a surface is cut
into runs and not which pixels it covers. So a matching capture hash is
**not** a fixture check. The counters are. Read `ROADSTRIP` and `stripRun`
before believing two runs are the same scene.

Everything in this directory was taken after rebuilding the editor from this
worktree and regenerating the fixture with it.

## `block-size.cpp`

The arithmetic half, and the reason `docs/baked-vif-stream.md`'s per-class table
is re-runnable rather than transcribed:

```bash
g++ -O2 -std=c++17 -o block-size block-size.cpp && ./block-size
```

It derives `getMaxVertCount` per program class from the same constants the
engine uses, prints `blockQw = 3 + streams * (1 + n) + 1` for each, and puts the
result beside what those same vertices already cost as source arrays — which
**nothing can free**, because the bbox cacher, the clip route and the generated
game all still read them. Nothing is read from the tree, so it keeps working
with the spike compiled out. Re-run it after any edit to `getMaxVertCount`, to a
cull program's `addProgramQBufferDataToPacket` (the stream count) or to the VU1
double-buffer size.

The headline it prints, at the package size the Motor District pins:

| class | streams | qw | bytes | baked B/vertex | arrays B/vertex |
| --- | ---: | ---: | ---: | ---: | ---: |
| `cull_tc`, `cull_tce`, per-vertex colour | 3 | 232 | 3 712 | 49.5 | 48.0 |
| `cull_c`, or a textured single-colour bag | 2 | 156 | 2 496 | 33.3 | 32.0 |
| `cull_td`, per-vertex colour | 4 | 308 | 4 928 | 65.7 | 64.0 |

i.e. **a baked static vertex costs about as much again as it already cost.**

## `ftclip-arms.txt`

The measured half: both arms' ELF hashes, all six `--capture-frame` hashes, the
scene-load producer lines, the `FTCLIP` windows of the held pose and every
`STAPIPBAKE` / `STAPIPMISS` window.

The headline, garage day, held pose, four stable windows per arm:

| | control (switch 0) | candidate (switch 1) |
| --- | ---: | ---: |
| DMA chain quadwords per frame | **9 146** | **6 705** (-26.7 %) |
| `REF` tags per frame | 0 | 59 (6.4 packages each) |
| package blocks re-baked per frame | 0 | 64 |
| arena | 0 | 1 431 KB |
| cull / clip / guard packages per frame | 775 / 36.5 / 238.5 | identical |
| submitted vertices per frame | 55 836 | identical |
| packet flushes per frame | 120 | identical |
| `--capture-frame` sha256 (x3 each) | `415f970f...73f1e` | identical |

**Six captures, one hash.** That is the byte-identical-picture claim
demonstrated rather than argued: the VIF1 word stream really is the same stream
whether its VIFcodes arrive in a chain tag's upper half or inside a referenced
payload.

**And the FTCLIP line is, digit for digit, the garage-day row
`../package-ceiling-75-2026-09-16/ftclip-arms.txt` records for its "after"
arm** - `cull=38750/2031525 clip=1825/16525 guard=11925/605925 out=46125
flush=6000 strip=24250 sexp=100 verts=55836`. That is the check that says this
is the same scene as the rest of the branch, and it is the one a capture hash
cannot do for you.

### Why the candidate rebuilds 64 blocks a frame at a frozen pose

`STAPIPMISS` tallies one reason per cache invalidation, and the held pose reads
the same line in three consecutive windows:

```
new=0 bbox=300 prim=600 streams=0 program=0 size=0 incomplete=0 over 300 frames
loudest bag count=2280 packages=31 reason=primState
```

Per frame that is **one** `bboxVersion` bump (a caller claiming its buffer's
contents changed, on a scene that is not moving) and **two** prim-state
collisions (one vertex array submitted twice with different prim state, so the
single entry the cache holds per (array, package size) is thrashed). Nothing
else fires at all. Three bags, each large - the loudest is 2 280 vertices in 31
packages - is the 64 rebuilt packages, to the package.

The outer-road day window is the control for that: `new=0 bbox=0 prim=0 …
built=0` with `refs=19`, i.e. **every drawn direct bag replayed and nothing
rebuilt**. The cache converges; the garage view contains something that lies to
it.

## Limits

- **PCSX2 only.** It emulates no EE data cache, and this change trades computing
  bytes for reading them out of a cold arena, so even if a millisecond were
  taken here it would be an upper bound on a hardware saving and nothing else.
  None was.
- **The spike is not the prize.** It keeps the per-package classification and the
  16-group qbuffer flush cadence, because `packetFlushes` is one of the counters
  this gate pins. The `chainQw` figure is the input to the later question, not an
  answer to it.
- **Only the direct, wholly-visible cull route is baked.** Partial bags, the clip
  route, copied and strip-expanded buffers, billboards and any game-supplied
  program override take the path they always took.
